## 2. 问题清单

### P1 · 会话读取可能读到别的会话（最高危）

**现象**：monitor 读 Buyer_anon_846be5fc 得 424 行，同一时刻页面上可见 wrapper 只有 20 个；两个不同会话连读得到 449/448 行、结尾内容相同。

**已验证的硬结论**

1. **读取是全页查询，没有容器限定（确定）**：[monitor.ps1:282](scripts/monitor.ps1#L282) `document.querySelectorAll('[class*=message-item-wrapper]')`。函数只校验页头名字，从不校验"这批行属于谁"。
2. **膨胀读数必然含目标会话之外的内容（确定，排除法）**：全量 246 条 `MSG-SCHEMA` 统计 —— Buyer_anon_62db210c 16..452（buyers 最多 201）、Buyer_anon_b64634c0 11..421（189）、Buyer_anon_846be5fc 17..427（188）、`Buyer_anon_5300658b` 0..416（185）、Buyer_anon_e828eacd 6..19（8）；**相邻两条不同买家、行数差 ≤2 的情况出现 50 次**。单会话最多 ~20 行，400+ 行不可能来自一个会话。
3. **是页面侧现象、reload 可清零、约 5 分钟内复发（确定）**：
   ```
   06:23:26 Buyer_anon_62db210c msgs=425 anomaly=True
   06:23:32 Buyer_anon_846be5fc  msgs=427 anomaly=True
   06:23:33 | Forced page reload (30m, busy) - RELOADED
   06:23:50 Buyer_anon_846be5fc  msgs=17  anomaly=False
   06:23:52 Buyer_anon_62db210c msgs=16  anomaly=False
   06:28:58 Buyer_anon_62db210c msgs=428 anomaly=True
   ```
   monitor 进程 PID 3284 全程未重启 ⇒ **不是 PowerShell 变量累积**。
4. **干净态读写完全正常（只读实测）**：页面上 `.content-header` 1 个、`.message-container` 1 个（且是 `.content-header` 的父节点），17 个 wrapper 全在其中；把**生产抽取器原样**打上去得到 15 行、**15 行全带 `@@MT`**，另 2 个 wrapper 因**没有 rich 节点**被抽取器自己丢弃（[msg_extract_js.ps1:82](scripts/lib/msg_extract_js.ps1#L82)）。那 2 个是：
   - `class="message-item-wrapper messenger"` = "由于您介入该会话，自动接待将不再触发。"
   - `class="message-item-wrapper"` = 页脚 "在Alibaba.com平台聊天和交易，享受安全保障。"

**未定论的一跳**：膨胀态里多出来的 ~410 个节点具体是什么、谁追加的。
- 现有数据**无法**定案，而且**将来也拿不到**：[monitor.ps1:1456-1458](scripts/monitor.ps1#L1456) 在 `Anomaly` 时直接 `return`，落盘在 [1486](scripts/monitor.ps1#L1486) **之后** ⇒ 每次膨胀的原始读数都被丢掉。磁盘上 85 个 `msgs_*.txt` 全是 6..22 行的干净读数。
- 一个反常细节：06:28:52 Buyer_anon_846be5fc 干净（17）、6 秒后 06:28:58 Buyer_anon_62db210c 膨胀（428）⇒ 不是"整页一个共享池"这么简单，与"读的那次点击后容器状态"有关。

**对已提出的三条修复方向的裁定**
| 方向 | 裁定 |
|---|---|
| 只轮询 `.content-header` | 必要，但**修不了这个**：膨胀态页头是对的，照样通过 |
| 面板两次采样一致才读 | **修不了**：膨胀态在两次采样间是稳定的，正好会通过 |
| 跨会话读数重复检测 | **能抓到**，是这一形态唯一的在线检出。**坑**：`@@META` 每行含 `at: new Date().toISOString()`（[msg_extract_js.ps1:177](scripts/lib/msg_extract_js.ps1#L177)），逐字节比较永不相等；指纹必须用去掉 `at` 的投影（现成 `StableId` 序列） |

**真正的第一性修法（原报告未列）**
1. 把查询**限定在当前会话容器内**（今天实测容器 = `.content-header` 的父节点 `.message-container`）。
2. **容器身份校验**：要求容器与页头属于同一会话。
3. **多容器 fail-closed**：页面上 `.content-header` / `.message-container` 多于 1 个（或可见的 >1 个）时，本轮拒绝该会话，不猜。
4. **P1b 两个独立缺陷**：[monitor.ps1:245-250](scripts/monitor.ps1#L245) 在整个列表项文本里做子串匹配、取第一个命中；[monitor.ps1:263-272](scripts/monitor.ps1#L263) 候选名从模糊选择器里凑并**取最长** ⇒ 页头未换、列表项先命中就 break。

**离线失败反例的现成机制**（不需要真页面、不需要授权）
[tests/message_order.tests.ps1:61-79](tests/message_order.tests.ps1#L61) 已用 AST 抽出 `Open-ConvoAndGetMessages`、把生成的 JS 写到临时文件、交给 [tests/message_extract.fixture.js](tests/message_extract.fixture.js) 在 **Node + vm 的假 DOM** 里跑。在 fixture 里造"两个会话的节点同时在 DOM / 容器与页头不是同一个会话"，当前实现必然返回别人的行 → 红灯。

### P2 · 顺序门禁把平台卡片噪声当致命异常 → 会话被永久挡住

**现象**：Buyer_anon_62db210c 读到 452 行、只有 16 行带逐条时间 → `MSG-ORDER-UNVERIFIED`，永远进不了生成/发送。

**根因（比"样本选错"更靠下）：项目里有两套行解析器**
- [msg_events.ps1:185](scripts/lib/msg_events.ps1#L185) 早已定义 `IsNoise = StructureType in @('flow','summary','noise')`，收据 / 发送尝试 / 事件层都在用它过滤。
- [msg_norm.ps1:101-203](scripts/lib/msg_norm.ps1#L101) 的 `ConvertFrom-MsgRawLine` **根本不读 `@@META`**（只正则 `@@TS/@@MT/@@MID/@@OT/@@CARD`）⇒ 平台卡片在它眼里是"完整消息" ⇒ [msg_norm.ps1:222](scripts/lib/msg_norm.ps1#L222) `$stamped.Count -ne $arr.Count` 必然触发。

**⚠️ 不做就会出事的耦合（原报告未提）**：[msg_norm.ps1:285-291](scripts/lib/msg_norm.ps1#L285) `$buyers = $list | Where Role -eq 'buyer'`、`LatestBuyer = $buyers[-1]`。膨胀态里 `buyers=189`，真实买家行只有 7 条。今天靠 `Anomaly` 挡住；**一旦只放宽顺序样本、不把噪声行移出"消息集合"，LatestBuyer 会落在别的会话的行上 → 机器人照着别人的话回话**。

**因此：P2 必须与"噪声行退出消息集合（LatestBuyer / BuyerCount / 账本 / 模型上下文）"同批做，且不得早于 P1 的容器限定上线。**

**判据边界（业主问的第 2 项）**：同意"不做文本猜测"，但**只豁免 `flow-message-item-wrapper` 不够** —— 上面实测抓到的两条非消息 wrapper 都不含 `flow`。真正的结构特征是：**没有 `.item-base-info`、没有 `item-left/item-right`、没有平台 ID、没有 rich 节点**。建议在抽取器里落成一个显式 `st` 值（如 `notice`），来源必须是结构，不是正文正则（现在 [msg_extract_js.ps1:111](scripts/lib/msg_extract_js.ps1#L111) 的 `summary` 恰是文本正则，买家说一句"进展…"会被误伤）。

**回归约束**：[tests/message_order.tests.ps1:47](tests/message_order.tests.ps1#L47) 的 `missing-interior-clock-unverified` 用的是无 `@@META` 的 legacy 行 —— 只要规定"`@@META` 缺失的行一律仍按真实消息处理（不豁免）"，该断言继续绿。

## 7. 一句话总结

**"能不能回"和"不许说什么"是硬的、可核对的；"该说什么、说多长、语气如何"没有生效规则（generation 阶段登记数为 0）。**
而今天最贵的问题不在回复内容，而在**证据链**：读取归属没有容器校验（P1）、顺序证明用错了样本集合（P2）、失败样本被代码自己丢掉（§3 末行）——三者叠加，才让"平台卡片噪声"既挡死了正常会话，又掩盖了真正的串台。
