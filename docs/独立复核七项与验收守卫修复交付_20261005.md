## 2. R1 + R4：统一请求解析，逐项核对角色与字段

**根因**（独立复核 §2/§5）

1. `Test-ContactAsk` 按"小句里有没有独立请求动词"判定，`and` 切开后只剩
   `contact details so we can reach you` 时整个跳过检查 ⇒ 无角色联系方式请求被放行。
2. `Test-ContactRoleProvided` 把 `recipient_name` 与 `recipient_contact` 合并成
   "该角色资料已提供" ⇒ 已有收货姓名反而阻断合法的电话询问。

**实际消费者**
`Test-ContactRedline`（初稿/一次重写/固定回退/直接事实/最终发送都调用）与
`Test-AskFieldConformance` 现在消费**同一份** `Get-ReplyRequestItems` 结果；
具体字段键（recipient_name / recipient_contact / delivery_address / supplier_contact / supplier_address）
分别核对"本轮已提供"与"本轮授权"。`Get-ContactClauses` 保留给兼容消费者。

**关键行为**

* 并列请求允许省略/继承**动作**，但**动词继承 ≠ 角色继承**：独立用途从句
  （`for packing` / `so we can reach you`）、新的请求动词、新的所有者、人称代词与句界
  都会结束角色作用范围。
* collect 顺序：规范键 → 该项已有有效 provided 事实则拒绝重复索取 → 该项 AskFields 授权 → 角色/用途成立。
  授权不能覆盖"已经提供"。
* 新违规代码 `CONTACT_ASK_UNAUTHORIZED_FIELD`（角色已授权、但该具体字段未授权），
  与 `CONTACT_ASK_ALREADY_PROVIDED` / `CONTACT_ROLE_UNCLEAR` 分工明确。
* 兼容：`supplier` → `supplier_contact`；`address`/`recipient_address` →
  `delivery_address`；粗角色名 `recipient`/`consignee` 只映射到最保守的
  `recipient_name`，**不**展开成整组资料；`recipient_contact` 覆盖 `recipient_name`
  （姓名属于同一联系资料块），反向不成立。

**同输入失败→通过**

| 输入 | 基线 | 修复后 |
|---|---|---|
| Please share the supplier's contact details for packing and contact details so we can reach you. | Ok=true（放行） | Ok=false / CONTACT_ASK_NO_ROLE |
| 真实事实模型 Consignee name: Alex. + AskFields=[recipient_contact]，Please share the recipient's phone number for delivery. | Ok=false / CONTACT_ASK_ALREADY_PROVIDED | Ok=true（合法电话询问放行） |

**测试**：`tests\third_fix_contact_fields.tests.ps1`（pure，37 断言，C01–C12 + 交叉），
`tests\second_fix_contact.tests.ps1`、`tests\contact_redline.tests.ps1` 保持全绿。

## 3. R2：展示用待办与对外行动授权分开

`Get-ActionEvidenceForBuyer`（该买家最近一条待办），`Generate-Reply-LLM` 与发送前也存在

**改动**

* 生产生成、重写、回退与发送授权**一律**不再调用 `Get-ActionEvidenceForBuyer`；缺确切任务 ⇒ 空行动证据。

  唯一一条 `awaiting_contact` 的"待供应商联系人"流程引用；**多候选无明确关联 ⇒ ambiguous**，
  不取最近、不取列表第一条、不借另一供应商。

"供应商已确认尺寸"照样放行。

**改动**

* `human_tasks` 在同一原子任务存储里新增**结构化行动/回复记录**

  来源白名单（manual-entry / owner-ui / operator-entry / legacy-import）拒绝 monitor/LLM 自设
  已联系/已回复/已确认；内容不足（无原文且无确认字段）不落盘。保存后重新读取验证嵌套记录与

  新确认更正旧值时把同字段不同值的旧有效记录标记为 `superseded`，保留来源历史且不再被引用。

## 5. R5：同一快照统一来源分类，索引只用于证据对齐

**根因**：`Get-InterventionEvents` 的人工分支下标恒为 -1
（`if ($Unknown) { $idx = IndexOf }`），已确认的机器人消息（有发送记录、缺 @@TS）
因此被当成人工回复并暂停 5 分钟；重复行还会用 `IndexOf` 借到第一条的发送证据。

**改动**

* 人工 / unknown / bot 三类改用**同一次带下标的 for 遍历**，按当前 Lines 的真实下标取 SentMatches；
  下标只服务本次快照的证据对齐，不进入持久 Identity（Identity 仍是规范化原文 + 可靠逐条时间）。
* 新增兼容更正：同一持久事件现在有**确切 bot 证据**时更正该事件分类，并按其余真实人工/unknown 事件
  **重算**有效截止；没有任何真实事件时只解除该买家这一个暂停，绝不全局清暂停、
  绝不删另一条真实人工造成的暂停、绝不延长（S07-correction-is-idempotent）。
* 保留：绝对 UTC 回复时刻 +5 分钟、持久首次观察锚点、历史去重、unknown 有界等待、异常未来时间、
  存储失败拒发。生产状态本轮不迁移（只在 TEMP 夹具里验证修复/兼容）。

**同输入失败→通过**：`[ME] Confirmed automated answer @@MT:...` + `SentMatches[0]=true` +
后接买家 → 基线 HumanPauseActive=true / Sends=0；修复后不暂停、不 hold、合法自动回复到达发送桩。

**测试**：`tests\third_fix_pause_source.tests.ps1`（isolated，36 断言，S01–S07）。

## 6. R7：澄清绑定具体歧义和来源

**根因**：`which` / 句首关键词 + "字段有 conflict 布尔"就放行 ⇒ 真实冲突 20/24 时可以编造
999/1000，而合法的 `confirm whether ... 20 or 24` 反被判 ASK_OUT_OF_SCOPE。

**改动**

* `facts_engine` 的冲突项新增**结构化候选**
  （`Conflicts[].Candidates`：Value/Unit/Scope/SourceRefs，保留 Key/Values 兼容字段）；
  候选在提取阶段就带单位、范围与消息/记录来源。

  与真实目的地候选导出；`ClarifyFields` 只是字段索引，单独存在不授权任意数值；场景名
  `address_clarify` 也不是凭空歧义证据（按真实目的地候选/缺失项构造）。
* `Test-AskFieldConformance` 先核对候选真实性、再判授权：句中每个数值都必须匹配一个真实候选
  （单位/范围一致；只有明确换算依据的单位才归一化；三维尺寸按整串比对），
  没有可枚举候选时只能使用不编造选项的受控开放澄清。
* 保留 which 定语从句阻断、per carton 单位修饰语、真实目的地澄清与追问次数限制。

## 7. R6：每个时间声明绑定地点/时区/时刻，逐目标检查覆盖

**根因**：完整检查只把正文里的时刻与 `expectedValues`（分钟值集合）比对，没有把"哪个地点的几点"
绑定起来 ⇒ "It's 1:00 PM in China (UTC+8). It's 12:00 PM in Japan (UTC+9)." 因两个数值都在集合里而放行；
China+Singapore 同钟点时只答 China 仍 Ok；Atlantis+Elbonia 只澄清 Atlantis 仍 Ok；
只写 "The shipment is going to Atlantis." 也能通过 Atlantis 的时间澄清检查。

**改动**

* 新增 `Get-TimeExpectations`：从**完整 TimeTargets 与同一份 RuntimeContext** 导出每个目标的
  原始/规范地点、有效时区、实际 UTC offset、当地时刻/日期与目标 Id（同点名地点可归并；
  同钟点/同 offset/同 Zone 的**不同点名地点不合并**）。
* 新增 `Get-OutputTimeClaims` + `Test-OutputTimeClaims`：全文每条当前时间声明提取输出区间、
  句子范围、时刻、12/24 小时形态、声明的地点/时区与 offset，逐条绑定到目标身份；
  12 小时无 AM/PM 的裸时刻不猜；未解析目标必须被**明确的时间地点/时区澄清**点名
  （澄清块 = 澄清问句所在句 + 紧邻前一句，容纳程序受控话术），
  纯地名陈述（无任何澄清问句）一律判未澄清。
  业务时间（预约/排期/截止/时长）与"现在几点"分开，不误判为当前钟点。
* ReplyComposition：程序事实片段按 Fact/TargetIds 记录，发送锁内用**一份新鲜 RuntimeContext**
  同时刷新时间片段与全部 TimeExpectations，再与独立业务正文**重新组合**（不叠加旧答案、
  不对全文做字符串替换猜前缀、其他身份事实片段继续保留）。
  发送锁内不调用模型、不重置整轮重写预算；整条复核仍检查模型正文，程序片段来源不提供正文豁免。
* 多城市同国家/同钟点时渲染点名城市，避免只显示国家名导致两个目标互相覆盖。

**同输入失败→通过**（注入 UTC 2026-10-05T04:00:00Z）

| 输入 | 基线 | 修复后 |
|---|---|---|
| 请求 China+Tokyo，正文 1:00 PM in China … 12:00 PM in Japan | Ok=true（并原样发送） | 阻断（FACT_TIME_MISMATCH）；真实入口最终文字为中国 12:00 PM / 日本 1:00 PM |
| 请求 China+Singapore，只答 China | Ok=true | FACT_TIME_TARGET_UNANSWERED |
| 请求 Atlantis+Elbonia，只澄清 Atlantis | Ok=true | FACT_TIME_TARGET_UNCLARIFIED |
| 请求 Atlantis，正文 The shipment is going to Atlantis. | Ok=true | 阻断（未澄清） |

## 8. G1：核查生产变化，保证验收结论与证据一致

详见 [生产路径审计证据](verification/architecture_opt_20261005/review_fixes/third_fix/production_path_audit.md)。要点：

* **证据记录**：精确路径、前后指纹（大小 + 最后写入时间 + 内容 sha256）、变化分类
  （file-content / file-time / dir-metadata / created / removed）、采样区间、当时测试文件、
  进程线索（锁持有 PID、monitor/watchdog、Chrome）与每个测试文件的差异明细，结构化写入
  `<LogFile>.production-audit.json`。目录时间变化单独标为 metadata，不混写为"已证明内容改写"。
* **越界排查（只读）**：48 个测试文件中**没有**以程序方式运行 `monitor.ps1`（引用全是 AST 抽取），
  没有启动生产 watchdog/chrome_ensure/Chrome；`Start-Process` 只启动临时根内的辅助脚本；
  真实发送出口在隔离模式下抛 `ISOLATION-VIOLATION`。未发现越界，故未修改测试路径，也未放宽守卫。
* **归因口径**：进程存在 + 路径在输出根**不构成**写入归因证据。runner 不再写
  "attributed to the live writer"，改为"并发变化、来源未证实"。
* **分层结论与退出码**：分开报告 LogicTests / IsolationChecks / ProductionPathAudit / Overall；
  退出码 0/1/2/3（3 = 环境未验收，来源未证实的并发变化）。未证实来源的差异**不得**被用来宣称
  "生产零写入 / 已证明测试完全未越界 / 完整验收通过"。
