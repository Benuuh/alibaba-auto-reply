## 3. 代码已确认的缺口

### 新消息时间门禁已离线修复，等待上线验收

此前 `Test-ShouldReply` 的新消息放行被 monitor 随后的 `RATE-SKIP` 覆盖。2026-10-05 工作区已修正为唯一时间策略，并补齐冷却期周期读取及可信新消息证据约束；普通消息五分钟配置不变。

现状：真实生产函数在模拟页面/模型/发送边界下已通过入口行为验证，运行进程尚未重新加载。20 秒是成功发送间隔与读取调度目标，受串行扫描及模型/附件耗时影响，不是平台端到端 SLA。`HASH|count` 无法证明窗口截断后等条数同文的新消息，未扩展或清空账本。

### 人工待办与通知交接尚未接通

决策对象返回 `NeedHumanTodo` 和 `TodoKind`，monitor 目前仅将它们用于上下文/日志，没有创建待办、通知结果与完成状态的闭环。

影响：一些固定话术写着正在交给团队或正在核实，但没有对应实际动作。不能将询盘提醒、报价提醒或白名单视为这套交接的替代证据。

### 语料规则没有完整接入回复请求

monitor 读取 `reply_rules.json` 并将对象传入生成器，但生成器仅使用部分字段，没有注入完整 corpus；回复路径没有生产消费 `reply_rules.always/never` 与 `data_to_collect`。系统提示词仍说 corpus 在下方，代码却未发送该语料块。

影响：向 never 数组应用建议只证明文件改变，不能证明该条规则影响模型或发送检查。需明确规则消费方式，并验证修改前后的行为。

### 期限承诺与追问范围缺少对应输出校验

决策层和上下文要求禁止无依据的具体期限、限制可追问字段，固定话术也依据决策选择。`Test-TimeCommitment` 已定义，但没有接到当前生成/发送检查调用链；最终内容检查也未核对模型实际追问是否符合 `AskFields`。

影响：不能宣称模型输出的具体期限或追问次数已被代码全面强制保证。即使提示词要求如此，实际输出仍需校验。

### 其他维护问题

- monitor 的 `pageDownStreak` 在同一轮的不同位置仍可能重复递增，自愈节奏需进一步验证。
- UI 噪声过滤和会话名称提取仍有多处实现。
- `backup.ps1` 与 `sync.ps1` 的过滤模式 `^apply_.*\.ps1$` 会排除当前 `apply_suggestion.ps1`；两者也不覆盖完整项目与运行数据，不能认定为完整部署备份或镜像。
- `brand.company_name` 为空；当前不存在完整品牌语料注入，填公司名后也需核对实际消费链。

上述为本次文档核验发现或复核的问题，本次仅记录，未改动业务实现。
