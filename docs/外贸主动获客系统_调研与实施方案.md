# 外贸主动获客系统 — 调研报告与实施方案

> 目标：对标**网易外贸通「拓客Agent」**的主动获客能力，构建自有的获客链路。
> 调研日期：2026-09-25 ｜ 结论基于 GitHub API 实测 + 网易外贸通前端产物实扒 + 本机能力实测。

---

## 一、先看清对标对象：网易外贸通「主动获客」是什么

扒完官方产品页（[拓客Agent 解决方案](https://waimao.163.com/solutions/acquisition-agent)、[客户发现](https://waimao.163.com/funpage/customs)）后，能力可以拆成三段：

| 段 | 平台在做什么 | 平台自己的数据底座（官方口径） |
|---|---|---|
| ① 找客户 | 多源挖掘潜在买家：全球搜索、海关数据、社媒、谷歌地图、搜索引擎、展会数据 | 60 亿+ 海关数据、1.2 亿企业数据、2 亿+ 海外企业联系方式，覆盖 230+ 国家 |
| ② 建联筛意向 | AI 以企业主营行业+产品资料为条件，7×24 主动触达，多轮沟通剔除同行/僵尸号/无效咨询，提炼采购需求并分级 | — |
| ③ 接管成交 | 高意向会话+买家画像推到对话框，业务员"一键接管"，继承全部上下文，不用重新铺垫 | — |

**关键判断：这套东西的护城河在「数据层」，不在「代码层」。** 平台卖的核心是那 60 亿海关数据 + 2 亿联系方式，AI 只是它上面的编排器。这决定了我们自建的策略必须是——**不跟它拼数据广度，而是把它的数据合法地用起来 + 在 AI 环节做得比它更贴合你的业务。**

## 二、GitHub 调研结论（实测，非猜测）

全部数据取自 GitHub REST API（`stargazers_count` / `spdx_id` / `pushed_at`），快照时间 2026-09-25，stars 为近似值。

### 2.1 一句话结论

**8 个模块里 6 个能复用现成开源件，2 个必须自建**：买家发现的数据层、真正的冷邮件序列器 —— 这两个开源生态基本是空白，恰恰是价值所在。

### 2.2 核心发现

1. **不存在成熟的开源冷邮件序列器**。检索 `cold email outreach self-hosted` 全库仅 **26 个**结果，几乎都是 0–20 stars 的个人项目；Instantly / Smartlead / Lemlist 级的多步序列、邮箱轮换、warmup、回复即停、A/B —— 开源侧没有。
2. **美国提单级海关数据开源为零**。UN Comtrade 只到「国家 + HS 编码」粒度（[uncomtrade/comtradeapicall](https://github.com/uncomtrade/comtradeapicall)，161★，MIT），**不含公司名**，做不了买家名单。⚠️ 注意同名陷阱：`dparrini/python-comtrade` 解析的是电力暂态录波文件，跟贸易无关。
3. **LinkedIn 自动化在开源侧是空白**。只有抓取库（[joeyism/linkedin_scraper](https://github.com/joeyism/linkedin_scraper)，4,542★，GPL-3.0，且最后推送 2026-04），**没有任何活跃维护的开源加好友/私信序列器** —— 因为 LinkedIn 用户协议明文禁止自动化。
4. **外贸获客 Agent 是 2026 年的新热点，但都很轻**。中文生态出现一批 10–40★ 的"外贸获客 Skill"（Codex / Claude Code 形态），**多个无 license**。最值得读的是 [xiongQvQ/AI_Find_Customer](https://github.com/xiongQvQ/AI_Find_Customer)（178★，MIT，FastAPI + LangGraph + React），有完整的"公司理解→关键词生成→网页搜索→线索抽取→联系方式发现"链路设计，**建议作为架构参考而非依赖**。

### 2.5 逐模块裁决

| 模块 | 裁决 | 理由 |
|---|---|---|
| 买家/公司发现 | **自建发现逻辑 + 复用抓取底座** | 抓取引擎全复用；"找谁"的行业知识是护城河 |
| 邮箱富集与验证 | **复用验证 + 自建推断** | 验证本次已自建完成；姓名→邮箱排列组合无成熟开源件 |
| 海关数据 | **采购 or 放弃** | 开源只到国家+HS 粒度，做不了买家名单 |
| 冷邮件外发 | **复用底座 + 自建序列引擎** | 投递层用 postal；序列/warmup/轮换必须自建 |
| LinkedIn 外联 | **不自动化，仅信号采集** | 协议明文禁止，封号是常态 |
| AI 个性化/打分 | **复用框架 + 自建业务逻辑** | LangGraph / Instructor / litellm 直接复用 |
| CRM | **直接复用** | Twenty 或 EspoCRM，自研性价比极低 |
| 反爬基础设施 | **直接复用 + 代理只能采购** | Playwright + Camoufox；住宅代理无开源替代 |

## 三、关键发现：你有比"爬公网"更好的路线

### 3.1 实扒网易外贸通前端，拿到了真实接口

我下载并分析了 `waimao.office.163.com` 的 webpack 产物（`app-*.js` 6.5MB），**确认了平台内部 API 的存在与命名**：

```
/api/globalSearch/factory/leads/list        ← 线索列表
/api/globalSearch/factory/leads/dict        ← 筛选项字典
/api/globalSearch/factory/leads/dispose     ← 线索处置
/api/globalSearch/factory/leads/desc/batch  ← 批量描述
```

更关键的是 `globalSearchApiImpl` 类暴露的方法名，直接说明了平台能力：

```js
deepGrubByDomain(e)      // 按域名深挖企业   → source:17
deepGrubContact(id)      // 深挖联系人
deepSearchContact(id)    // 联系人深挖
dcmGetContactPage(...)   // 联系人分页列表
getBackgroundInfo(...)   // 企业背调
getSimilarCompanytable() // 相似企业推荐
addCustomer(e)           // 发现的线索直接写入 CRM
```

**这对你的意义**：你已经有网易外贸通账号，那么「找客户 + 挖联系人 + 背调」这段能力**平台已经付费给你了**，不需要自己从公网爬。正确做法是——**用你自己的登录会话，把这些能力接进你自己的流程**，把精力放在平台没做好的地方（多语种开发信、意向筛选规则、企微承接）。

> 需要清醒认识：这属于**用你自己的账号访问你自己的数据**，比爬公网合法得多，但**自动化访问仍可能触发平台风控/条款**。见 §5。

### 3.2 平台有明确的反自动化风控

前端里写死了一段 429 提示：

> "操作频繁，系统已触发安全保护，请稍后再试或检查是否存在**多人共用此账号、使用自动化工具**等情况"

**结论：绝不能高频轮询。** 必须低频、有人工节奏、有间隔，并监控 429。这是设计约束，不是建议。

## 四、推荐架构

核心思路：**平台数据（合法获取）+ 自建富集验证 + 自建 AI 编排 + 复用你已有的企微承接**。

```
┌─ 数据层 ────────────────────────────────────────────────┐
│ A. 网易外贸通(CDP 复用已登录会话, 端口 9224)              │
│    客户发现 → 线索列表 / 深挖联系人 / 背调 / 写入CRM      │
│    ⚠️ 低频 + 429 监控 + 人工节奏                         │
│ B. 公网补充(Playwright + Crawlee)                       │
│    官网 / 目录站 / 谷歌地图 / 展会名录                    │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ 富集层(已交付) ─────────────────────────────────────────┐
│ tools/email-verify : MX + SMTP RCPT 验证                 │
│    → ok / invalid / risky(catch-all) / unknown           │
│ 待做: 姓名→邮箱推断、SPF/DKIM/DMARC 检测、去重            │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ 触达层(待做) ───────────────────────────────────────────┐
│ 多步序列引擎(自建): 节流 / warmup / 轮换 / 回复即停       │
│ 投递底座: postal 或自有企业邮箱                          │
│ AI 个性化: DeepSeek(已有) + 多语种开发信                 │
│ 合规: 退订链接 + suppression list + 实体地址             │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─ 承接层(复用已有) ───────────────────────────────────────┐
│ 回复意图识别 → 高意向推企微(wecom-connector) → 人工接管   │
│ 与现有 alibaba-auto-reply / OKKI 链路共用状态与去重       │
└─────────────────────────────────────────────────────────┘
```

**为什么复用你的现有资产是最大优势**：你已经有 CDP 桥、单实例锁、幂等状态、企微推送桥、LLM 封装、质量闭环、守护进程、测试框架（296+46+63 例）。新项目不需要重建这些，只要接上去。

## 五、风险与合规（必须前置确认，不是免责声明）

| 风险 | 具体 | 缓解 |
|---|---|---|
| **平台风控/条款** | 自动化访问网易外贸通可能违反其服务条款，账号可能被限流或封停；已确认存在 429 反自动化保护 | ① 严格低频（建议 ≥3s/请求，单次任务限量）② 复核 429 ③ 优先走平台官方导出功能 ④ **明确接受"账号风险自负"** |
| **登录态抓取的合法性** | 登录态自动化在多国可能触及"规避技术措施"条款 | 仅访问**你自己账号下的数据**；不绕过任何权限；不抓取非授权数据 |
| **GDPR（欧盟）** | B2B 冷邮件也适用：需合法性基础（正当利益须做 LIA 评估）、告知义务、反对权 | 保留数据来源与时间戳；首封即含身份信息与清晰退订；维护 suppression list；做 LIA 文档 |
| **CAN-SPAM（美国）** | 要求真实发件人/主题、物理地址、显著退订、10 日内执行 | 模板强制含公司实体地址 + 一键退订；退订自动全局抑制 |
| **CASL（加拿大）/ 澳 Spam Act** | **选择加入制**，冷邮件基本不可行 | 这两个市场只做 opt-in，或直接排除 |
| **域名信誉** | 自建发信 IP 无声誉 → 进垃圾箱甚至被 RBL 拉黑 | SPF/DKIM/DMARC + PTR/FCrDNS + 按域限速 + 先 warmup 小流量 + 监控 RBL |
| **硬退信** | 发到不存在地址会直接损伤域名信誉 | 已交付的 email-verify 就是为这个：**invalid 必须剔除** |

> 我的建议：**先把「找客户 + 富集验证」做扎实，把发信量控制在小批量人工确认级别**，等 SPF/DKIM/DMARC 和退订机制就位后再放量。一口气群发是最容易把域名发废的路径。

### 7.1 网易外贸通 CDP 桥 + 接口侦察器

| 文件 | 作用 | 验证情况 |
|---|---|---|
| `scripts/waimao/waimao_cdp.ps1` | 网易外贸通专用 CDP 桥（端口 9224，独立 profile），支持 eval / navigate / tabs / ports | ✅ 真实 Chrome 实测通过 |

**侦察器怎么用**（这是 P1 的钥匙）：

```powershell
# 1. 启动带调试端口的 Chrome(独立 profile,不动你现有实例)
# 2. 登录网易外贸通,进入「客户发现」
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\waimao\waimao_recon.ps1 -Action install
# 3. 在浏览器里正常操作:搜索客户、筛条件、点联系人、点挖邮箱
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\waimao\waimao_recon.ps1 -Action dump
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\waimao\waimao_recon.ps1 -Action report
```

它会输出接口清单 + 每个接口的请求体样本，并**标红命中的 429 风控次数**。安全设计：只记 path 与请求体，**不记 Authorization/Cookie**；全程只读页面，不点击、不提交、不写平台数据。

### 7.2 邮箱可投递性验证引擎

`tools/email-verify/`（零依赖 Node）：DNS MX + SMTP RCPT 判定，**只做 RCPT 不发 DATA**，单域串行防灰名单。

自测：**10 passed / 0 failed**。真实端到端实测 8 条样本：

| 地址 | verdict | reason |
|---|---|---|
| `support@stripe.com` | risky | CATCH_ALL_DOMAIN |
| `zzz-not-a-real-person-9931@stripe.com` | risky | CATCH_ALL_DOMAIN ← 假地址也返 250 |
| `sales@shopify.com` | risky | CATCH_ALL_DOMAIN |
| `info@tesla.com` | unknown | PROVIDER_BLOCKS_PROBE(550) |
| `nonexistent-person-8821@siemens.com` | invalid | SMTP_REJECT_550 |
| `bad-syntax-email` | invalid | SYNTAX |
| `test@mailinator.com` | invalid | DISPOSABLE_DOMAIN |
| `nobody@no-such-domain-zz991.com` | invalid | NO_MX |

**这次实测暴露了一个行业普遍自欺的点**：Stripe / Shopify 这类企业用 Google Workspace catch-all，**真假地址都返 250**。工具如实标 `risky` 而不是假装验证成功 —— 这点很重要，否则你会以为名单"验证过了"，实际在赌退信率。详见 `tools/email-verify/README.md`。

## 八、需要你确认的决策点

1. **平台自动化的风险接受度**：是否接受"用自己账号低频自动化访问网易外贸通"潜在的风控/条款风险？若不接受，路线改为纯公网采集（成本高、覆盖窄）。
2. **发信基础设施**：是否已有可用于开发信的企业邮箱/域名？没有的话 P4 需要先解决 SPF/DKIM/DMARC 与 warmup。
3. **P1 是否现在启动**：需要你跑一次 `waimao_recon.ps1`，在浏览器里真实操作「客户发现」1–2 分钟，把抓包结果给我。
4. **目标市场合规**：欧盟需 LIA 文档，加拿大/澳洲冷邮件基本不可行 —— 是否需要按国家做发送策略分级？
