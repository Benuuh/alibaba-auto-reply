## 一、一句话说清这个系统在干什么

**它就是一个"盯着阿里国际站聊天窗口的机器人"。**

一个专门的 Chrome 登录你的阿里卖家账号,机器人每 9 秒看一次「待回复」列表:
有新消息 → 读出来 → 让 DeepSeek 写回复(写不出来就用固定话术) → 发出去 → 记在小本本上防止重复发。
客户信息凑齐了(重量+尺寸+地址),就通过企微提醒你去报价。

**最重要的一句话:整个系统的"大脑"只有一个文件 —— `scripts\monitor.ps1`(1671 行)。**
其他所有东西都是围着它转的"保姆"和"工具"。

## 二、两个目录(这是最容易懵的地方)

| 目录 | 放什么 | 打比方 |
|---|---|---|
| `<部署根>\` | **代码 + 配置**。git 仓库在这 | 厂房 |
| `<部署根>-runtime\` | **所有运行数据**:日志、买家快照、Chrome 登录态、报告 | 仓库 + 档案室 |

**所以你在工作区(`alibaba-auto-reply`)里永远找不到 `logs\`、`data\` —— 不是丢了,是搬走了。**

搬走的目的是"代码和数据分开",换机器只改 `scripts\config.json` 一个文件。

> **反查判据**:如果工作区里**又长出** `logs\` / `reports\` 目录,说明某个路径键没配对,
> 不是正常现象(见 `docs\KNOWN_EXCEPTIONS.md` E-17)。

## 三、谁在跑:3 个常驻进程 + 6 个闹钟

### 常驻进程

```
计划任务 AlibabaAutoReplyWatchdog  (每分钟触发一次,只负责"确保它在")
        │
        └─► watchdog.ps1   ← 保镖,每 30 秒巡一次
                 │
                 └─► monitor.ps1   ← 真正干活的,每 9 秒一轮
                          │
                          └─► Chrome (CDP 端口 9222,独立 profile)
```

**反直觉但很重要:monitor 不是自己起来的,是 watchdog 拉起来的。**

所以 **绝对不要**自己用 `Start-Process` 去起 monitor —— 代理会话启动的常驻进程会被系统回收。
要启动就走计划任务:

```powershell
Start-ScheduledTask -TaskName 'AlibabaAutoReplyWatchdog'   # 拉起 watchdog,它再带起 monitor
```

### 6 个闹钟(计划任务)

| 任务 | 频率 | 干什么 |
|---|---|---|
| `AlibabaAutoReplyWatchdog` | 每分钟 | 确保 watchdog 活着;watchdog 再确保 monitor 活着 |
| `AlibabaAutoReplyHealth` | 每 15 分钟 | 体检 7 项;发现 watchdog 死了就自动拉起来 |
| `AlibabaAutoReplySummary` | 每 4 小时 | 生成对话总结 |
| `AlibabaAutoReplyQuality` | 每天 05:00 | 分析昨天的回复质量 |
| `AlibabaAutoReplyOptimize` | 每天 05:30 | 让 AI 自己提炼规则,改 `reply_rules.json` |
| `AlibabaAutoReplyWeekly` | 每天 08:00 | 周报 + 唤醒沉睡买家(内部幂等,一周只真跑一次) |

**所以是三层守护套娃:计划任务看 watchdog → watchdog 看 monitor → Health 看 watchdog。**

> `Get-ScheduledTask -TaskName AlibabaAutoReply*` 看实时状态(计划任务清单的权威就是它本身,文档不列死)。

## 四、monitor 每一轮(约 9 秒)做什么

```
每一轮 Invoke-ScanRound:
  1. 抢锁 onetalk-write          ← 防止和别的脚本同时操作页面
  2. 处理"补发队列"              ← data\pending_retry.json
  3. Get-Snapshot()              ← 读「待回复」列表
  4. 读去重账本 state.json        ← 读不出来就整轮不发(宁可不发,不可重发)
  5. 整轮硬门禁:
       · OneTalk 页面在吗?
       · 页面健康吗?(Test-PageHealth)
       · 是不是冷启动第一轮?(只观察不发)
  6. 对名单里每个会话:
       · 在人工接管白名单里?     → 跳过
       · 冷却中?                 → 跳过
       · 打开会话 + 校验是不是本人 ← 校验失败 = 整轮中止(防发错人)
       · 读消息 → 判"该不该回"(Test-ShouldReply)
       · 让路检查:老板已经人工回过? → 不插话
       · 生成回复:DeepSeek → 失败回退规则引擎(19 类场景)
       · 发送(发送前再校验一次会话名)
       · 存买家档案 / 消息快照 / 报价提醒
  7. 收尾:页面不健康就升级自愈;空闲满 3 分钟就刷新页面防止列表失活
```

### 两个容易误解的点

**① "Scan cycle done" 刷屏 ≠ 故障。**
待回复列表为空时,monitor 每轮只写这一行,并且空闲满 3 分钟刷一次页面防止列表失活。
**这是设计好的正常空转**(代码注释写明"列表为空 `[]` 是正常'无待办'状态")。

**② 打开会话这个动作本身,会把会话移出「待回复」板块。**
「待回复」= 待办队列,**读过/回过就会从板块消失**。所以"列表里没有"通常意味着"已经处理过了",
不等于"漏了客户"。

### 自愈分两级

- **轮内自愈**:CDP 连续 3 次出错 → 跑 `chrome_ensure.ps1 -ForceRestart` 重启 Chrome 并自动登录
- **轮外自愈**:watchdog 兜底,monitor 进程没了就拉起来

## 五、数据都存在哪

| 文件 | 作用 | 打个比方 |
|---|---|---|
| `scripts\state.json` | **去重账本**:会话名 → `消息hash\|买家消息条数` | "我回过谁、回到哪句" |
| `runtime\data\pending_retry.json` | 发送失败待补发队列 | 待办便签 |
| `runtime\data\manual_override.json` | 人工接管白名单(不自动回) | 黑名单 |
| `runtime\data\health_state.json` | 体检各项状态 | 体检报告 |
| `runtime\data\buyers\`、`msgs_*.txt` | 买家档案 + 每轮消息快照 | 档案室(PII,只在本机) |
| `runtime\logs\monitor.log` | 主日志 | 行车记录仪 |
| `scripts\monitor.pid` / `watchdog.pid` | 进程号 | 门牌号 |

**路径的唯一来源是 `scripts\config.json`。** 换机器/搬数据只改它,代码不动。

## 六、术语对照表(看日志时最需要)

| 日志里看到 | 人话 |
|---|---|
| `Scan cycle done` | 这一轮结束(列表空时只有这一行,正常) |
| `PROCESS convo from pending-list` | 开始处理某个会话 |
| `SHOULD-REPLY ... Reply=False` | 判据认为"不用回" |
| `LEDGER_COUNT_MATCH` | 理由:账本记的条数 = 现在数到的条数 ⇒ 认为已回过 |
| `ALREADY-REPLIED-WAIT` | 已回过,等 3 分钟再看 |
| `TEMP-SKIP ... dedup cooldown` | 冷却中,先不碰 |
| `SKIP ... cannot open convo` | 打不开这个会话 |
| `RETRY-OPEN ... NOT_FOUND` | 找不到这个会话,切标签重试一次 |
| `REPLIED to X: FILLED \| CLICKED \| SENT_OK` | **真的发出去了**(三重校验通过) |
| `ROUND-SEND / ROUND-DONE` | 本轮生成+发送耗时 |
| `HUMAN-REPLIED-SKIP` | 老板已人工回过,机器人让路 |
| `PAGE-DOWN / PAGE-RECOVERED` | 页面数据面断了 / 恢复了 |
| `PAGE-HEAL` | 页面不健康,升级到重启 Chrome |
| `ABORT-WRONG-CONVO` | 发送前校验发现不是本人 ⇒ 拦下(保护正确) |
| `COLD-START observe-only` | monitor 刚重启,第一轮只看不发 |
| `LOCK-BUSY` | 有别的脚本在操作页面,本轮跳过 |

## 七、这个项目为什么"感觉乱"—— 五个真实原因

### 1. 文档故意分成 5 份,还规定了"谁说了算"
`docs\文档权威约定.md` 按问题种类分权威。好处是防止同一句话写多处而互相矛盾;
代价是想搞明白一件事得翻 3 个文件。**本文就是为这个补的导读。**

### 2. 历史层层叠加,留下"已死但还在"的东西
- 两套企微桥梁(`wecom-connector`、`control-agent`)已于 2026-09-26 **物理删除**(约 4000 行)
  —— 但文档里到处还在讲它们的历史
- `runtime\data\alert-channel.handover.json`("交接门"标记)**已作废**,文件还在
- Accio(只读增强)、okki(小满 CRM)、waimao(网易外贸)、gonghai(阿里公海)
  —— **四条并行业务线**,其中 gonghai 是 2026-09-27 新加的,还没提交

### 3. 同名文件陷阱(最坑)
`scripts\cdp.ps1` 和 `scripts\lib\cdp.ps1` **是两个不同的文件**:
- 前者是命令行入口
- 后者是被 monitor 加载的库(真正干活的 `Get-Page` / `Test-PageHealth` 在这)

这是**刻意拆分,不是待清理的重复文件**。但改错文件 = 白改。
两者的 `Get-Page` 必须逐字一致,有 `tests\page_select.tests.ps1` 锁住。

### 4. "改了不生效"陷阱
**`monitor.ps1` 只在启动那一刻加载一次库文件。**
所以改完任何 `lib\` 里的东西,**必须重启 monitor 才生效**。
(2026-09-27 12:25 那串 `Get-HumanInterjectionProbeLines is not recognized` 报错就是这个成因 ——
代码改了但 monitor 还跑着旧的。)

### 5. 工作量确实大
`scripts\` 75 个文件约 11800 行,`tests\` 31 个测试文件。
`.opencode\`、`tools\` 里大部分是 node_modules,**不是业务代码**,别被文件数吓到。

## 八、日常怎么用

```powershell
# 完整体检(最常用,先跑这个)
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\status.ps1

# 全套回归测试
powershell -ExecutionPolicy Bypass -NoProfile -File tests\run_tests.ps1

# 单跑一个测试(更快)
powershell -ExecutionPolicy Bypass -NoProfile -File tests\page_health_verdict.tests.ps1

# 重启监控(走计划任务,不要 Start-Process)
Start-ScheduledTask -TaskName 'AlibabaAutoReplyWatchdog'

# 人工接管白名单(不让机器人回某个客户)
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\whitelist.ps1 -Command '白名单 列表'
powershell -ExecutionPolicy Bypass -NoProfile -File scripts\whitelist.ps1 -Command '白名单 添加 John Smith'
```

> ⚠️ 本机执行策略限制:`.ps1` 一律用 `powershell -ExecutionPolicy Bypass -NoProfile -File <路径>` 调用。
> ⚠️ 改完 `.ps1` 后复验前三字节是不是 `239,187,191`(UTF-8 BOM)。
> 编辑工具剥掉 BOM 会让 PS 5.1 按 ANSI 解码 ⇒ 中文全乱、判据恒真。

## 九、出问题先看哪

| 你怀疑 | 先看 |
|---|---|
| 系统还活着吗 | `scripts\status.ps1` |
| 机器人到底发没发 | `runtime\logs\monitor.log` 搜 `REPLIED to` |
| 为什么没回某个客户 | 同日志搜客户名,看 `SHOULD-REPLY ... Reason=` |
| 是不是在空转 | 日志只有连续的 `Scan cycle done` ⇒ 待回复列表是空的(正常) |
| 页面/CDP 出问题 | 搜 `PAGE-DOWN` / `CDP error detected` / `PAGE-HEAL` |
| 有没有发错人 | 搜 `ABORT_WRONG_CONVO`(出现=保护生效,没发出去) |
| 告警通道通不通 | `status.ps1` 里的「告警出口(dsh-im)」项 |
