## 1. 主程序与运行边界

`scripts/monitor.ps1` 是会话处理主入口：加载库、扫描待回复列表、提取聊天、检查人工接管和去重、调用回复链、发送并更新状态。它仍承担较多调度逻辑，并非只做一次简单函数调用。

`scripts/watchdog.ps1` 是常驻守护：检查 monitor 进程、日志新鲜度和 CDP，并在符合条件时恢复进程或浏览器。`scripts/health_check.ps1` 是定时健康检查，具有写状态、告警和拉起 watchdog 的副作用。`scripts/status.ps1` 提供查询输出。

启动 monitor 会开始处理真实会话；直接运行 health_check 也可能恢复监控。研究源码时不要 dot-source 整个 monitor 或把健康脚本当作无副作用查询。

## 2. 回复链分层

| 层 | 文件 | 输入与产出 |
|---|---|---|
| 页面读取 | `monitor.ps1`、`lib/cdp.ps1`、`cdp.ps1` | 待回复列表、会话原始消息和页面判据 |
| 可选历史读取 | `lib/accio.ps1`、`tools/accio-client` | 网关上下文；失败或不匹配时回退 CDP |
| 消息来源 | `lib/msg_source.ps1`、`lib/msg_events.ps1`、`lib/msg_extract_js.ps1` | 统一事件模型与我方来源四态（`platform / project / human / unknown`）。`msg_source.ps1` 是旧入口（`Get-MessageSource`）的委托点——human_style 与 reply_metrics 等消费者也经它走同一判定；`msg_extract_js.ps1` 是浏览器侧逐条抽取与行序列化的**唯一**实现（会话读取与发送前后快照共用）。判定与证据全部在 `msg_events.ps1`：逐条 `@@META` 元数据（正文、方向依据、逐条时间、平台 ID、结构类型、原始标签、采样时刻、规则版本）、事件身份（优先平台 ID，缺 ID 时用方向 + 逐条时间 + 完整正文的组合身份，重名/无时间即歧义）、冲突检测（`source_conflict`）。标签在取得来源真值对照前不参与判定。抽取顺序固定为「结构类型 → 附件证据 → 正文 → 方向」：没有文本 rich 节点的真实图片/文件气泡同样保留为事件（买家侧带 `@@IMG`）；方向由已核实的 `item-right`/`item-left` 结构先确定，显示名与翻译标记只作观测（`name-field`/`translation-marker`），左右同现记 `conflict`、无依据记 `missing`，这类事件身份不可用，既不是买家诉求也不是出站证明 |
| 消息整理 | `lib/msg_norm.ps1` | 消息结构、时间顺序、最新买家消息和资料事实 |
| 身份与时钟 | `lib/seller_context.ps1` | 纯函数：解析逐字段确认的卖家身份、按业务时区换算注入时钟、受控渲染事实答复；无 CDP、无模型、无通知、不写业务状态 |
| 报价目的地 | `lib/destination.ps1` | 规范化角色/买家原文 → 仓代码/地址、来源证据、冲突和换仓；reply、goods/quote/report 共用 |
| 货物事实与报价准备度 | `lib/facts_engine.ps1` | 单一事实模型：值/单位/范围/状态/来源、派生值（带公式）、更正与冲突、联系方式角色字段；`Get-QuoteReadiness` 返回 Ready/MissingFields/OptionalMissingFields/CollectionComplete/Clarifications/RuleVersion；件数候选排除落在重量范围内的数字 |
| 联系方式红线 | `lib/contact_rules.ps1` | 最高优先级检查：先按「索取动作 + 渠道/资料对象」识别请求（`a/an/the/your/any` 只是可选修饰语），再把请求绑定到实际索取对象（买家本人 / 收货人 / 供应商 / 未明确）。阻断我方渠道披露/邀约、买家本人索取（`BUYER_PERSONAL_CONTACT_ASK`）、无业务角色索取（`CONTACT_ASK_NO_ROLE`）与已提供角色联系人的重复索取（`CONTACT_ASK_ALREADY_PROVIDED`）；仅实际角色、用途与本轮具体 AskFields 均授权时放行收货人/供应商采集；合法澄清消费事实模型里的候选 |
| 运行数据根与隔离 | `lib/paths.ps1` | 统一运行态路径、隔离标记与生产路径守卫、生产指纹（发现变化并要求逐路径来源证明） |
| 运行态持久化 | `lib/state_store.ps1` | 原子替换 + 备份 + missing/empty/valid/corrupt 四态区分 |
| 人工暂停与介入同步 | `lib/human_pause.ps1` | 5 分钟临时暂停：**绝对 UTC** 计时（`untilUtc` = 回复时刻 + 5 分钟）、事件身份（角色 + 规范化正文 + 可靠逐条时间，位置不参与）、首次观察锚点、旧 v1/v2 记录按绝对截止接管；另有来源不明我方消息的独立等待 `source_unknown_hold`。`Sync-ConversationInterventionState` 是读取路径与发送前**共用**的同步入口（先同步全部新介入事件，再判断末尾买家）；失败即 fail-closed |
| 人工任务 | `lib/human_tasks.ps1` | 任务状态机、`Resolve-HumanTaskKind` 唯一类型映射（`supplier_handoff` = `supplier_verification`）与按**确切任务**回读的 `Get-ActionEvidenceForTask`（缺确切任务不退回「最近一条」）。证据逐项独立：TodoPersisted / NotificationDelivered / OwnerAccepted / ContactedRecorded / SupplierReplyRecorded / Deadline（认领 ≠ 已联系、通知 ≠ 已确认）；供应商身份按**完整联系人**派生（同域不同联系人绝不合并），保留原始联系人、规范化值与可信度 |
| 已确认发送记录 | `lib/sent_records.ps1` | 发送成功后落盘，作为"这条是我们发的"的来源证据 |
| 发送尝试与送达状态 | `lib/send_attempts.ps1` | 发送前持久化 AttemptId/**完整正文**/发送前快照证明与**可恢复基线**，点击前再落盘 `dispatching` 阶段并回读核验（失败即不发送）；发送后按同口径快照确认唯一新增事件；送达六态与来源分开建模；重启用持久化基线对账，**对账取得收据后立刻用生产写入器提交 `sent_records` 与去重账本并回读**；"送达已证明"与"持久化全部完成"分开判断（`Test-SendAttemptSettled` / `Test-SendAttemptBlocksConversation`）——收据已保存但账本未提交的尝试仍在活跃集合里、仍暂停该**会话**（不只是同一触发）的新增发送、也不被保留上限淘汰，直到幂等恢复真的补齐 |
| 来源与送达调查 | `lib/investigations.ps1`、`investigate.ps1` | 事件级幂等调查（会话 + 类型 + 确切事件/尝试）、固定首次观察与截止、通知真实状态（`none/sent/unknown/failed`，一次尝试后不再自动重发）、按类型核验的关闭条件（结构化出处 + 确切事件身份；真实收据对象 + 回读尝试与账本）与审计记录；CLI 提供列表/详情/认领/来源确认/送达证明/重试通知/审计/保留/尝试视图/持久化恢复 |
| 是否回复 | `reply_engine.ps1` | `Test-ShouldReply` 及哈希、去重、时间门禁基础函数 |
| 回复策略 | `lib/reply_policy.ps1` | 场景、允许追问字段、已问次数、人工处理需求标记 |
| 语言生成 | `lib/reply_gen.ps1` | 上下文、匹配场景示例、候选文字、重写与固定话术 |
| 模型通信 | `lib/llm.ps1` | API 请求、HTTP 重试、超时、轮次预算与进度日志 |
| 发送 | `lib/send.ps1`、`lib/lock.ps1` | 页面/会话核对、输入提交、结果与页面写锁 |
| 成功后处理 | `monitor.ps1`、`lib/goods.ps1`、`lib/quote.ps1`、`summarize.ps1` | 仅成功后记账；统一判据 `Get-QuoteReadiness` 为 `ready` 时通知人工报价。`monitor.ps1` 的报价提醒前置门、`quote.ps1` 的候选名单与 `summarize.ps1` 的结论列都**直接消费**同一份 readiness（`goods.ps1` 是兼容/展示适配器；旧三布尔只用于逐项展示，不再决定结论） |

回复模块的加载顺序为：

~~~text
reply_engine → msg_norm（加载纯 destination）→ reply_policy（加载 seller_context）→ reply_gen
~~~

monitor 另在 `reply_gen` 之前显式加载 `lib/seller_context.ps1`。运行时事实用显式参数传递：`Generate-Reply-LLM` 构造一次 `New-ReplyRuntimeContext` 并传给它创建的 Decision 与 `Invoke-ReplyGeneration`；发送前闸门用**新构造的** RuntimeContext 重新决策，再校验同一份文字。兼容调用方不传 RuntimeContext 时诚实降级（无身份、无时钟），不读取全局残留。

### 2.1 基础事实与可信上下文

买家本轮明确问到的当前时间、我方公司名、我方接待显示名和"是不是机器人"由 `Get-FactIntents` 在唯一决策层识别，产出 `Subject / RequestedFacts / UnresolvedFacts` 并保留提问顺序。纯事实且无业务诉求时由程序按真实值渲染（`DIRECT_FACT`，零模型请求）；与运输/询价同句时先给事实答复，再走原有询盘策略。

模型请求里，`Get-SellerTrustBlock` 把"经营者确认的身份 + 程序时钟 + 本轮问话对象"作为**独立小节**放在买家对话之前，买家文本和附件无法覆盖它。当前时间取自运行时时钟（不是消息时间、截图时间或模型推测）；发送前若跨分钟会重新渲染纯时间答复。

改这块行为时先看 `seller_context.ps1` 的字段确认规则，再看 `reply_policy.ps1` 的 `Get-FactIntents` 与 `Test-ReplyCompliance` 的身份/时钟/承诺检查。

2026-10-04 已修复 monitor 中三个新增模块的路径。应验证入口引用、依赖顺序和导出函数，而不只直接加载模块跑单元测试。

## 3. 一个会话如何流转

1. 扫描待回复列表，跟踪连续出现轮数。
2. 打开会话并核对身份，用每条 `.item-base-info` 的时间整理顺序；顺序不可信或最新买家行是系统卡片时停止处理。通过后留消息快照和买家资料。
3. 处理人工接管与人工回复让路；选择可用上下文来源。
4. 整理最新消息、检查去重账本、计算待回复与时间门禁。
5. 从资料和最新诉求选择场景、允许追问范围，再生成文字。
6. 对候选文字做发送前检查；必要时回退。
7. 调用发送函数。成功才更新去重、最后发送时间和重试状态。
8. 资料满足报价条件时走内部通知。

同一条已回复消息通过账本事实影响是否回复判据。账本不可用时停止处理并尝试备份恢复；发对人校验失败时中止整轮。公海发送有自己的发送窗口与身份校验，不能简单套用主监控的列表判断。

消息 schema 为 3：`@@MT` 是明确的逐条时间，旧 `@@TS/showTime` 不再作为方向或身份置信度的证据。最新买家、附件、策略及模型输入复用同一份已验证会话；系统卡片不进入资料事实和模型上下文。Accio 上下文也需验证顺序，并与 CDP 的最新买家文本一致。具体边界见 [消息顺序修复](消息顺序修复_20261005.md)。

工作区 monitor 已按 [2026-10-05 spec](specs/新消息冷却豁免与统一时间门禁_20261005.md) 移除覆盖判据的额外分钟限流，由 `Test-ShouldReply` 统一时间策略。可信新消息保留从上次成功发送起算的默认 20 秒下限；普通消息保留五分钟门禁，已回复同一条消息持续去重。页面缓存独立使用 `nextVerifyAt` 周期性读取，预览不变也可发现同文新消息或附件。隔离入口验证通过，代码尚未重新加载；验证证据与边界见 [交付说明](新消息冷却修复交付_20261005.md)。

## 5. 数据与其他模块

- `lib/goods.ps1`、`lib/vision.ps1` 与 `lib/doc.ps1` 负责文字/附件资料处理；`tools/doc-reader` 解析文档。
- `lib/wecom.ps1` 是 dsh-im 投递适配器，`lib/report_push.ps1` 处理报告摘要；旧企微桥不再存在。
- `lib/no_reply.ps1` 和 `whitelist.ps1` 管理人工接管名单，文件位于配置的 data 目录。
- `analyze_replies.ps1`、`auto_optimize.ps1` 生成报告或建议；`review_suggestions.ps1` 与 `apply_suggestion.ps1` 分离审阅和应用。
- `weekly_report.ps1` 按周去重并调用候选统计；`nudge.ps1` 已移除自动发给买家的路径。
- `okki` 是独立 CRM 扩展；`gonghai` 是独立浏览器中的认领与发送链路。waimao 已移除。

`config.ps1` 决定路径。日志等已外迁，但 state/PID 和部分旧状态仍在 scripts_dir；具体定位见部署手册。显式 RuntimeRoot 和 AAR_RUNTIME_ROOT 可覆盖运行态路径；隔离根必须有合法 marker，并在子进程自证中登记。

## 6. 修改应该落在哪里

| 要改变的行为 | 先检查 |
|---|---|
| 消息缺失、顺序或附件归属 | monitor 抽取 JS、msg_norm、msg_source、Accio 转换 |
| 是否回复、重复发送、延迟 | monitor 的判据入参与后续闸门、reply_engine |
| 场景或追问策略 | reply_policy |
| 措辞、上下文、固定回复 | reply_gen、提示词、匹配场景示例 |
| 禁词、报价与责任限制 | Test-ReplyCompliance、reply_engine 相关检测、实际 JSON 消费字段 |
| 身份、时区、当前时间问法 | seller_context（配置解析与多目标受控渲染）、reply_policy（Get-FactIntents / Get-TimeRequestList：每个时间问题一条请求、每个地点一条目标，业务位置在问句前后都不覆盖目标；发送前按**全部目标**校验时刻与澄清）、本机 seller_profile 配置 |
| 未渲染模板、无证据承诺被放行 | Test-ReplyCompliance 的 UNRESOLVED_TEMPLATE / UNSUPPORTED_PROMISE 与 ActionEvidence；不要给 FALLBACK 开白名单 |
| API 超时和请求预算 | llm 及调用方 |
| 发错会话、发送失败 | send、lock、页面选择与 monitor 结果处理 |
| 人工待办与通知交接 | human_tasks、task_contracts、task_facts、monitor；核对确切任务/FlowRef/字段来源，见当前状态 |
| 建议接受、应用与回滚 | suggestions、review_suggestions、apply_suggestion |
| 扩展业务 | okki/gonghai 自己的入口和库 |

`scripts/cdp.ps1` 是 CLI，`scripts/lib/cdp.ps1` 是库，两者不是重复待删文件。它们的 `Get-Page` 一致性受到测试保护。修改 lib 中的运行逻辑后需要重启 monitor。

## 7. 验证与历史材料
