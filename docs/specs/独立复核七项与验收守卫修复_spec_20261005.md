## 0. 目标、边界与必须保留的业务规则

本轮完整修复 R1–R7，并处理 G1 验收守卫的越界排查、证据记录和不实归因。不能只修前三项或只让七条探针变绿。
采用现有模块和小型共用接口，避免通过堆叠互相冲突的正则、扩大词汇豁免、停掉所有回复来掩盖问题。

允许：工作区源码、测试、规则登记和文档修改；虚构资料、模型/页面/发送/通知桩、TEMP 运行根内的隔离验证。
禁止：启动、停止或重启生产 monitor/watchdog/Chrome；改真实配置、凭据、生产账本/任务/暂停/提醒；操作真实页面；真实模型、客户发送、供应商联系、真实通知；提交、推送或批量迁移生产状态。
不要 dot-source 整个 monitor 或调用 health_check。遵循 PS 5.1，`.ps1` 保留 UTF-8 BOM。保留工作区原有改动，不重置无关文件。

以下规则持续有效：

1. 最高红线：不主动提供/邀请使用我方联系方式，不笼统索取买家个人联系方式。收货人和供应商资料只能按明确业务角色、用途、当前字段范围及已有事实询问。买家就是收货人时仍明确收货角色与用途；不新增客户主动询问我方联系方式时的自动披露授权。
2. 人工回复后暂停 5 分钟，以真实回复的绝对 UTC 时刻计时；新人工回复重置，同条重扫、买家补充、重启不延长。过期只解除门禁，不主动追发；显式人工接管名单优先。
3. 基础资料为货名/参考图、外包装件数、单件外包装重量和尺寸、供应商地址/联系方式、收货人姓名/联系方式/地址。报价最低条件为外包装件数、有效重量、外包装尺寸、可用收货目的地；辅助资料不阻断报价。明确总重可用；Amazon 目的仓代码可满足目的地。
4. 买家无法提供包装资料时索取缺失的供应商业务联系方式，保存核实待办，说明之后由人工向供应商核实，减少买家来回询问。任务保存、通知、人工认领、实际联系、回复、确认分别成立；不自动联系、不虚构已完成动作。
5. 不自动给价格/范围/优惠，不编造事实或时限，不承诺责任/退款/付款，不推给老板经理；客户拒绝后无新消息不追发。
6. 仅 SENT_OK 推进回复账本；UNKNOWN 先对账。任务独立于发送结果，FAILED/UNKNOWN 不删已成立任务。保持快照/生成锁外/最终复核锁内、原子状态、损坏账本拒发和隔离出口。

## 3. R1 + R4：统一请求解析，逐项核对角色与字段

当前入口：[contact_rules](../../scripts/lib/contact_rules.ps1)、[reply_policy](../../scripts/lib/reply_policy.ps1)。

### 3.1 请求项及继承边界

建议增加 `Get-ReplyRequestItems`，或在同一小型模块内完成等价职责：先识别动作及名词成分，再判断角色/字段。
原 `Get-ContactClauses` 可保留给兼容消费者；红线与 Test-AskFieldConformance 必须使用同一请求项列表，避免一个认定已提供、另一个认定未授权。

1. 同一次并列请求允许省略/继承动作：`share A and B` 中 B 仍是索取，不因没有独立 share/please 跳过；逗号清单、and、plus、also 等适用同一规则。
2. **动词继承不等于角色继承。** 角色只有直接所有格、of/for 绑定或紧密的同一名词清单可继承，例如 `recipient's name, phone number and delivery address` 分别绑定该收货人。
3. 新的请求动词、主语/所有者、personal/your phone、独立用途从句、句界等结束或重新建立角色作用范围。
   `supplier's contact details for packing and contact details so we can reach you` 后项继承 share，不能继承 supplier。
   `your phone` 不能继承前一供应商角色。买家明确表示自己是收货人时，当前请求仍须显式限定收货角色与派送用途，
   采用 `As the consignee, could you share the delivery phone number?` 等受控句式绑定 recipient_contact；不能凭买家显示名或泛化 delivery 词推定角色。
   personal/private 请求始终不因此放行。
4. 角色不能由全文出现 supplier/recipient 推导。用途不能代替角色；前半合法角色询问不能豁免后半个人或未指名请求。
5. 真请求但联系对象不明时阻断该文本，进入一次重写/受控替代；无请求动作且无继承关系的正常资料叙述不误拦。
6. 我方渠道披露/站外邀约独立检查，不依赖请求动词，也不受角色/用途授权豁免。
7. 名词清单中的 `per carton/each pallet` 继续作为重量/尺寸的单位修饰语；不能因为出现 carton 把它当新件数索取。
8. 不要求覆盖无限自然语言。支持已用受控句法和有限变体；识别不了的联系方式请求不能放行，应生成明确角色的可验证替代话术。

### 3.2 字段键与判定顺序

复用现有事实键，不再按“recipient/supplier 整组已提供”判定：

| 请求项 | 对应事实/授权键 |
|---|---|
| 收货人姓名 | recipient_name |
| 收货人有效派送联系方式 | recipient_contact |
| 收货地址/目的地 | delivery_address；旧 recipient_address/address 仅作同义适配 |
| 供应商业务联系方式 | supplier_contact；旧 supplier 明确映射到它 |
| 供应商地址 | supplier_address |

`recipient_name`、`delivery_address` 不授权 recipient_contact；supplier_address 不授权 supplier_contact，反向亦然。
仅有粗角色名的历史别名须列出明确映射，不可默认展开成该角色全部资料。
其他重量/尺寸/图等既有别名保持原有效语义，但在澄清时必须区分具体字段及单位/包装范围。

collect 请求的检查顺序：规范键 → 该项已有有效 provided 事实则拒绝重复索取 → 该项 AskFields 授权 → 联系角色/业务用途成立。
不能保留当前“authorized 直接 continue，因而跳过 provided”的旁路。
conflict/needs_confirmation 不当作已提供，也不自动授权重新索取；使用 §7 的具体澄清证据。

R4 的必过正例：`recipient_name=provided, recipient_contact=unknown`、AskFields 仅 recipient_contact 时，
`Please share the recipient's phone number for delivery.` 必须合法。反向电话已有、姓名缺失时，姓名询问仍合法。

本轮不将电话与邮箱拆成新的持久必填字段。recipient_contact 仍表示可用派送渠道；已有有效电话或邮箱通常已满足该项，不能为凑资料再索取另一渠道。
买家自己收货时，可用明确收货角色和用途的受控表达；不得用笼统 `your personal contact` 替代。

### 3.3 全链接入与失败处理

联系方式最高红线、字段范围、已提供、澄清绑定共用上述解析结果。初稿、一次重写、固定回退、直接事实和最终发送都执行统一完整检查。
不为 DIRECT_FACT/FALLBACK 增加豁免。用具体违规项指导一次重写；重写仍违规则使用与当前事实/授权字段一致的受控回退。
回退若还不合法才不发送并记录原因，不能让合法缺失资料询问永久哑火。

## 4. R2：展示用待办与对外行动授权分开

当前入口：[human_tasks](../../scripts/lib/human_tasks.ps1)、[monitor](../../scripts/monitor.ps1)、[seller_context](../../scripts/lib/seller_context.ps1)。

### 4.1 选择任务

1. 保留 Get-ActionEvidenceForBuyer 用于列表/摘要；**生产生成、重写、回退及发送授权不得从它取“最近任务”。**
   删除 monitor 在没有 kind、没有 TaskId 时的两处宽松回退，改为空行动证据或明确选择相关任务。
2. 本轮创建/更新成功时使用返回的确切 TaskId；既存任务须由当前业务流程与供应商身份/明确触发关联选择。
3. 选择优先级：本轮确切创建/更新结果 → 当前相关核实流程绑定的确切任务 → 当前确属该流程且只有一个相关候选时唯一选择。
   同买家只有一个待办不是充分条件；fulfillment_status、quote_status 等不能授权供应商计划。
4. 多任务/多供应商无明确关联时返回 ambiguous，不取最近、不取列表第一条、不借另一供应商。
5. 无相关任务返回空证据。不能因为模型输出了联系承诺而倒补一条任务，以使承诺合法。
   真实业务决策仍可创建正确核实任务；不要为通用 shipping 询问新建无依据的供应商任务。
6. 保留 Resolve-HumanTaskKind 的唯一映射；supplier_handoff/supplier_verification 按同一 canonical kind 判断。

### 4.2 确切回读契约

建议沿用 `Get-ActionEvidenceForTask`，明确返回：

```text
EvidenceOrigin = exact-task-readback
ExactTaskMatch
BuyerKey, TaskId, CanonicalKind, SupplierIdentity
TaskExists, IsOpen, TaskStatus, HasUsableSupplierContact, KeyEvidenceFingerprint
各行动记录及支持的事实（见 §5）
```

New-ActionEvidence、模型上下文、规则检查必须完整透传并核对这些字段，不能丢掉匹配结论后只剩 TodoPersisted=true。
供应商未来计划至少需要 canonical supplier_verification、确切回读匹配、本轮供应商流程关联及允许状态；泛化 TodoPersisted 不授权任何动作。
其他类型任务只能支持该类型确有记录的动作，不能替供应商动作或期限背书。

确切记录存在与任务仍开放分别表示。IsOpen 约束未来计划；resolved/closed 不再有未来行动授权，但已经记录且仍有效的可信事实不能随关闭消失。
过去回复/确认/完成声明只能依据本轮明确关联的确切记录，或 §5.4 当前有效事实携带的 TaskId/RecordId 来源选择历史任务，不能取最近已关闭任务。
同轮存在当前任务与既存确认事实时，可保留一个主任务 Ref 加事实来源 Ref 列表；按每项声明的来源分别回读，不把一份证据通配给所有任务。
旧 TodoPersisted 可保留兼容含义，但新的动作授权直接使用 TaskExists/ExactTaskMatch/IsOpen 与对应记录，不再用它单独决定“已完成事实是否可信”。
任务库读失败/损坏与合法空库分开处理；不能把读失败当成空库新建并覆盖，涉及本轮行动时按失败状态拒绝相关承诺/发送。

按要求匹配的供应商身份不能用任务空 supplierKey 通配。旧任务缺 key 时，只能从**该任务自身真实完整联系人**无歧义构造身份后比对；无法核实就不给身份授权。
awaiting_contact 的供应商身份尚未确定时，可使用该确切任务的“待供应商联系人”流程引用，**仅授权条件式下一步**，不把 unknown identity 当通配符。

### 4.3 发送前复核

每个会话重置主任务及事实来源 Ref/ActionEvidence；不跨会话泄漏。
只要回复涉及任务行动或任务来源的确认事实，就必须存在对应明确 Ref；发送锁内按同一 BuyerKey/TaskId/kind/supplier/RecordId 再读一次。
读失败、生成期间任务由开放变关闭、归属或供应商改变、支持该声明的关键记录/值变化，弃稿并下一轮重新决策。
下一轮可以根据已验证事实来源明确选择 resolved 记录回答已确认/完成的事实；不能对已 resolved 的任务重新许诺待执行计划。
没有 Ref 时不给旧 script 变量或会话级摘要授权。

关键指纹只包含身份、允许状态、业务联系人/缺口及本次声明所依赖的行动/确认记录；
通知尝试次数、普通日志时间等无关变化不应让所有回复反复弃稿。`updatedAt` 不能独自充当业务版本。
状态发生实际变化须重新核对动作权限；不得因为新的记录“看起来更强”就沿用无法证明一致的旧声明。

## 5. R3：声明动作逐项取证，补足真实回复记录

当前入口：[human_tasks](../../scripts/lib/human_tasks.ps1)的证据转换、[reply_policy](../../scripts/lib/reply_policy.ps1)的供应商声明检查、生成上下文及最终检查。

### 5.1 声明与权限表

| 对外表述 | 必要证据/条件 |
|---|---|
| 请给供应商业务联系人，拿到后我们会直接核实 | 本轮正确 awaiting_contact 任务、字段授权；保留“拿到联系人后”的条件 |
| 我们会直接联系供应商核实 | 匹配的开放供应商任务、可用联系人、业务关联及合理状态；不用通知成功代替任务事实 |
| 已通知人工 | 同一确切任务的真实投递成功记录 |
| 人工已认领 | 同一确切任务的真实认领记录 |
| 我们已联系供应商 | 对应供应商的实际联系记录；认领/投递不是联系 |
| 已联系，正在等供应商确认 | 实际联系成立；不夹带已确认或已回复声明 |
| 供应商已回复 | 对应供应商的回复记录及来源；联系状态不是回复 |
| 供应商确认了尺寸/重量/件数等 | 回复记录明确支持声明字段；带数值时值、单位及外包装范围也一致 |
| 已解决/已完成具体事项 | 对应事项有实际完成记录；任务关闭本身不能证明供应商已确认 |
| 某时限前完成/答复 | 继续满足已确认 Deadline、当前任务匹配及现有真实通知/认领等联合条件；输出时限不得超过记录授权 |

同句 `we contacted ... and your supplier confirmed ...` 分别检查两项，不能让前项合法豁免后项。
覆盖 I/we/our team、supplier/vendor/factory 及现用语态；不能仍用一个 claimAllowed 为所有过去动作背书。

### 5.2 记录来源与最小存储扩展

仅拆 ContactedRecorded/SupplierReplyRecorded 布尔不够：目前任意非空 resolution 都被当成供应商回复，必须同时修复来源。

复用 human_tasks 的原子任务存储，增加可选的结构化行动/回复记录；可扩展已有人工更新接口，或增加小型记录函数，无需新增完整 UI。
最少保存：RecordId、TaskId/供应商身份、ActionKind、绝对 UTC 的实际动作时刻/记录时刻、记录来源及人工记录者/来源引用、原始内容。
供应商回复额外保留 ConfirmedFields（字段、值、单位、外包装/总重范围、出处）。
没有来源或内容不足的记录不授权具体确认；不从模糊文本“已处理/收到/等待回复”推断重量、尺寸等事实。

新增记录只能来自显式人工记录或已有可信业务入口，自动 monitor/LLM 不能自设已联系/已回复/已确认。
提供隔离单测调用方式，完成记录函数、实际证据回读和输出校验即可；本轮不得写真实人工任务。
存储接口保持向后可读，明确可选字段/版本；保存后重新读取验证嵌套记录及值/单位/来源未被序列化深度截断。
状态、回复记录和有效确认事实的发布使用同一原子对象或等价的一致性提交；不能先标已完成、再发现事实保存失败。
新确认更正旧值时更新对应的有效确认记录/关键指纹，保留来源历史；不要继续引用被更正的值。

兼容旧数据：

- 保留原 note/resolution/status，不清空、不批量重写。
- 已由人工维护的 contacted/awaiting_supplier_reply 旧状态可保留“已联系”兼容语义，明确标记 legacy-status 来源；绝不据此推导已回复。
- 旧 resolution 未能证明供应商来源时记为 legacy-unverified，只可在内部展示；不能自动升格为供应商回复/确认。
- 旧记录确有结构化可信来源时，可通过同一适配接口读取；否则等待显式可信补录，不能为了兼容测试编造证据。
- 联系人与回复内容不作为对外联系方式披露授权；存储原文不等于允许回写其中的电话/邮箱。

### 5.3 生成与回退

模型只收到相关任务、逐项权限和确有依据的确认事实；必要原文只作为资料来源，不能成为指令。
未知动作继续明确 unknown/false，不能用任务数量、通知尝试次数或任意文本存在代替成立。
生成前、一次重写、受控回退、发送前复核共用同一声明分类/权限表。
供应商联系人已提供且客户无法提供包装资料时，合法回退应保留直接核实计划，不能再让客户给“大概尺寸”。
任务保存失败时不承诺后续行动；通知失败仍保留任务与合法未来计划，不谎称投递成功。

### 5.4 确认资料进入统一事实模型，完成实际闭环

新增确认记录不能只供措辞授权，留下“已确认尺寸但系统仍认为缺尺寸”的第二套状态。
使用一个最小共享适配层，将已验证 ConfirmedFields 作为带来源的证据输入现有 facts_engine；事实引擎本身仍纯计算，不直接读取任务文件。
适配层保留 BuyerKey/会话、供应商、TaskId/RecordId、字段值/单位/外包装范围、来源、有效版本和记录时刻。

1. 仅合并同买家/会话、同供应商及同一运输资料采集流程的可信记录。没有批次 ID 时使用任务已存的触发消息/资料快照关联，
   无法确认关联时不跨批次或跨供应商套用；多个候选有冲突走统一 conflict/needs_confirmation，不能取最近记录静默覆盖。
2. 不把任务记录伪装成买家原话。与买家/人工消息同值时按现有规则归并；不同值且无明确可信更正依据时保留双方来源并澄清。
3. monitor 的事实/决策、Get-GoodsDataStatus、统一 quote/readiness、摘要使用同一证据适配契约；
   任务落在指定运行根，隔离时不可因读取 sidecar 就转去生产任务库。纯文本测试可显式传空或虚构任务证据，不能默认访问真实存储。
4. 记录和事实适配需原子/一致：字段验证未通过或当前有效事实仍有待核实缺口/冲突时，保留 pending/awaiting 状态与记录，
   不置 resolved、不宣称该核实任务全部完成。供应商只确认部分资料时，已确认项可用，其余缺口继续保留。
5. 供应商核实任务 resolved 的依据是其原本待核实字段已纳入当前有效事实且没有未解决冲突，**不是要求所有辅助资料齐全**。
   QuoteReady 仍由外包装件数、重量、尺寸、目的地四项决定；confirmed 记录不能单独设置 Ready=true。
6. resolved 后可信事实按来源继续可读取；联系人缺失、旧 resolution 不可信或记录失效时不能伪造确认。
   明确新更正/新批次不再引用旧值。任务库不可读时不给任务来源证据；已有买家/人工消息资料仍按原模型计算，依赖任务证据的回复失败关闭。

必须验证“人工记录供应商确认 → 保存/重新加载 → 统一事实 provided → 不再补问同项 → Ready/摘要一致 → resolved 事实仍有效”的隔离正例，
以及部分确认、冲突、跨供应商/流程、存储失败和更正的负例。此处不授权本轮实际联系供应商或生产迁移。

## 7. R7：澄清绑定具体歧义和来源，不依赖句首关键词

### 7.1 从唯一事实模型导出 ClarificationRequests

建议增加运行时 `Get-ReplyClarificationRequests`：

```text
Id, FieldKey, ReasonKind(conflict/unit/scope/role/destination)
Candidates[{Value, Unit, Scope, SourceRefs}]
SourceRefs, AllowedOpenClarification, AllowedQuestionForms
```

从实际 CargoFacts.ByKey、Conflicts、Evidence 和目的地候选导出。必要时给 facts_engine 的现有 Conflicts 追加结构化候选信息，保留 Key/Values 兼容字段。
在提取候选阶段就保留单位、范围与消息来源，不依赖对自由文本 Clarifications 字符串反向猜测；不另建第二套事实模型。
ClarifyFields 仅是字段索引，单独存在不授权任意数值/单位。场景名称 address_clarify 也不是凭空歧义证据；根据真实目的地候选/缺失项构造具体请求。

### 7.2 按请求项区分 collect 和 clarify

1. 核对已有候选、归属、单位/范围歧义才属于 clarify；句首 which、what、confirm whether 等仅是句法线索。
2. 真冲突 20/24 cartons 可用 `Which carton count is correct - 20 or 24?` 或 `Could you confirm whether the carton count is 20 or 24?`。
   两种都应通过，而 999/1000、20 pallets、20 kg 等无来源替换不能通过。
3. 允许语义明确且有转换依据的单位归一化；不能凭数字相等推定同单位、同范围。总重与单箱重、产品件与外包装箱不相互冒充。
4. `Which carton count can you provide for the quote?` 是重新索取，按 collect 检查 AskFields/已有事实；不能借 conflict 状态绕过范围。
5. 没有可枚举候选但确有歧义时，使用不编造选项的受控开放澄清，例如“你给了两种箱数，我们应采用哪一种”。没有真实歧义时不能凭裸 ClarifyFields 新增候选。
6. 同一请求可包含一个合法澄清和另一资料索取；逐项授权，不能整句 continue。
7. 如 AskFields 也允许该字段，仍不能豁免所述候选/事实的真实性。授权新索取不等于允许编造已有候选。
8. 合法澄清优先使用程序从 ClarificationRequests 渲染的有限模板；自由模型文本识别不确定时回退该模板。

保持原 which 定语从句阻断、per carton 单位修饰语、真实目的地澄清和问题次数/追问范围限制。
旧测试若仅伪造 Status=conflict 而无实际候选/来源，应补真实夹具；不能把生产规则降为“有一个 conflict 布尔就允许说任意数值”。

## 8. R6：每个时间声明绑定地点/时区/时刻，逐目标检查覆盖

### 8.1 目标和期望

沿用现有 TimeRequests/TimeTargets 及三态地点解析；不要重写城市库或重新搜索整段业务文本。
从同一 NowUtc 生成每个目标的 TimeExpectations，保留 RequestId、TargetId、原始/规范地点、有效时区、实际 UTC offset、当地日期及钟点。
相同地点/别名的重复问题可归并并保留对应请求引用；同钟点、同 offset 或同 Zone 的不同点名地点不能靠这些相等关系合并覆盖。
地点别名与渲染显示名使用现有 Resolve-PlaceTimeZone 的可验证映射，不能仅凭时间数值认定属于某地点。
城市显示为国家名的兼容输出只有在目标映射明确且不造成多目标遗漏时可用；多城市同国家/同钟点需要点名对应城市或明确列出这些目标。

### 8.2 全文声明校验

1. 每条当前时间声明提取输出区间、PlaceRefs、Zone/Offset、Clock、Date/CrossDay 信息，与对应目标期望逐一比较。
   不得保留 expectedValues/statedValues 的分钟值集合授权。
2. 时刻正确但地点/offset 错也阻断；多目标裸时刻或 12 小时格式无 AM/PM 无法明确绑定时不猜，重写/受控回退。
   明确 24 小时格式可以按受支持句法归一化。
3. 同钟点的 China 与 Singapore 都需被明确回答；只有 China 不能覆盖 Singapore。
   一条声明可共同回答多地点，但须明确列出全部对应地点，且确实有相同时刻/offset；否则程序分别渲染。
4. unknown/multiple-zone 目标必须绑定到**明确的时间地点/时区澄清**。单纯提到 Atlantis、泛化全文某处出现 which city，不能算该目标已澄清。
   Atlantis + Elbonia 可分别澄清，或在一个时间澄清问题中明确列出两者；只澄清其一必须判漏答。
5. 判定对象是最终完整文本。正确程序前缀 + 错误模型正文必须被拦；正确前缀不能豁免正文，受控回退也不能免检。
6. 当前时间与运输时长/客户已经给出的预约时间区分。无依据的当前时间或新的时限承诺照常阻断；已有业务时间仅在能绑定可信资料且不冒充当前时刻时合法。

落地方式以现有确定性 renderer 的标准句法为主，增加小型逐声明解析/绑定，不要求支持全部英文时钟表达。
无法可靠绑定的模型时间声明先一次重写，再使用完整程序时间答案与合法业务回退。
可在混合生成上下文明确“时间事实由程序回答，业务正文不重复生成时钟”，但提示词不能替代全文校验。

### 8.3 发送前刷新

生成结果必须保留 ReplyComposition：程序事实片段（Fact/TargetIds/Text）与独立 BusinessBody，或等价的由组合器维护的来源区间。
片段来源只能由程序建立，不能由模型自报；兼容整条 Text/Source 等既有返回字段。
发送锁内重新检查快照与任务后，用一份新鲜 RuntimeContext 同时刷新程序时间片段和对应全部 TimeExpectations，
再与原独立业务正文重新组合。纯时间与混合时间/业务都适用；不叠加新旧答案，不对全文做字符串/正则替换去猜前缀，其他身份事实片段继续保留。
整条复核仍检查模型正文，程序片段来源不提供正文豁免。
锁内只允许纯程序刷新、受控回退和校验。若确需剩余的一次 LLM 重写，先释放锁，改稿后重新获取锁并完整复核快照、任务、事实及新鲜时钟。
整轮初稿/重写总预算不重置：已有一次重写则直接受控回退/弃稿，不加第三次调用；不得持页面锁等待模型。
请求/身份变化仍弃稿重决策。跨分钟、午夜、日期和夏令时 offset 使用时区实现，不手写固定偏移去迎合测试。
无地点按卖家时区、there/here/my local time、美国/澳大利亚多时区、纽约/悉尼、hamburg 大小写及身份问答回归保留。
