### 0.1 必须保留的业务规则

1. **最高红线**：不得主动提供我方电话、邮箱、微信、WhatsApp等联系方式或引导站外联系；不得笼统索取买家私人联系方式。只能按本轮明确字段、业务角色和用途询问供应商/收货人资料；买家本人收货也明确使用收货人角色。客户主动询问我方联系方式不自动获得披露授权。

3. 基础资料：货名/参考图、运输外包装件数、单件包装重量/尺寸、供应商地址/业务联系方式、收货人姓名/派送联系方式/地址。报价最低条件只有：有效外包装件数、有效包装重量或明确总重、有效包装尺寸、可用收货目的地。辅助资料不阻断报价；合法Amazon目的仓代码可满足目的地。
4. 客户给不出包装资料时，索取缺失的供应商业务联系人，保存核实任务，说明人工后续直接核实。联系人已有时不重复询问、不继续逼客户估算包装。任务、通知、认领、联系、回复、确认和完成分别取证。
5. 不自动给价格/区间/优惠；不编造事实、进度或期限；不承诺责任/退款/付款，不推给老板经理；拒绝后无新消息不追发。
6. 仅SENT_OK推进账本；UNKNOWN先对账，不能直接补发。任务独立于发送结果；FAILED/UNKNOWN不删除已成立任务。生成在页面锁外，最终快照/来源/任务/事实复核在锁内；全轮最多一次模型重写。

## 3. S1：存储、归属、确认及完成闭环

### 3.1 存储健康与原子写入（F06）

读接口返回可区分的 `Status/Data/Error/Version`。合法首次missing且无已有备份可初始化；corrupt、零字节/空白、schema-invalid、unreadable不能返回“合法空库”。合法空tasks集合与读取失败不同。

所有创建、状态更新、行动记录、通知更新及更正都先检查读状态，并在同一存储锁内读改写，防止并发丢记录。列表兼容接口失败时抛受控错误或显式返回失败，消费者不得catch后按空库保存。

读写使用完整存储对象及版本，保存任务列表不能丢掉新增的当前Flow索引、VerificationItems或历史引用。旧schema向后可读，新增字段的嵌套保存后重新读回核验，失败不报已发布。

坏主文件/备份不得被新建覆盖；如沿用已有恢复接口，须验证备份、保留原坏文件并独立报告恢复，不能把坏库伪装为首次库。写入失败不发布成功证据；任务证据不可读时阻断依赖它的行动/确认，独立买家资料仍按原事实规则计算。

### 3.2 持久货物流FlowRef与唯一供应商身份（F02/F07）

FlowRef至少包含 `Id/BuyerKey/SupplierIdentity/InitialTriggerRef/CurrentContextRefs`；可加在现有任务库对象中，持久保存买家当前货物流引用，不要求客户提供新的批次编号。

- 初始触发用可靠消息身份/原文哈希及时间建立不可变锚点；后续补充加入同一流。重启和窗口截断读取已存引用，不因初始消息不在窗口另造流。
- 明确新货物/新订单/新批次建立新FlowId。供应商变更必须重新核实归属，旧供应商确认不直接进入新身份；同供应商新批次也不能复用旧资料。
- 任务resolved/closed不自动结束当前货物流或清除FlowRef；新流只由明确新货物/订单/批次或可信人工关联建立。
- 同邮箱、仅一条open任务、旧触发仍在全文、显式TaskId，均不能单独证明当前关联；已有可信持久当前FlowRef及来源链时仍可正常关联。不能确认时返回ambiguous并给合法的货物流澄清，不能永久停止会话或要求所有客户必填FlowId。
- 同一关联契约同时限制**当前货物的买家/人工消息候选和任务确认候选**，防止仅挡住任务却从旧会话消息再次导入旧四项。seller身份/时间等非货物事实不按货物流清空。
- 选择、确切回读、task_facts和发送共用供应商身份适配。缺supplierKey只能从该任务自己的完整联系人无歧义导出；未知不通配。awaiting_contact可凭确切TaskId/FlowRef支持条件下一步，补齐联系人时保留同一流，不能借其他待办。
- 每项有效任务事实保留 `FactRef={FlowId,TaskId,RecordId,FieldKey,FieldVersion,SupplierIdentity,ValueHash}`；本轮主任务引用与历史事实引用列表分开。

旧无可信归属数据保留可读和内部展示，仅在确能关联时适配；本轮不批量改生产数据。

### 3.3 单一字段验证（F03）

在facts_engine建立纯字段验证/规范化函数，买家候选与任务ConfirmedFields共用。仅验证成功可provided；调用者指定FieldKey/Status不能绕过实际值、单位和范围检查。

| 字段 | 有效条件 |
|---|---|
| 外包装件数 | 正整数、明确箱/托盘等运输包装；产品件数/不明数量不冒充包装数 |
| 包装重量/明确总重 | 正有限数、合法质量单位、范围与字段一致；规范换算，产品净重/不明范围需核实 |
| 包装尺寸 | 三个正有限边长、合法长度单位、明确运输包装范围；两维/商品尺寸/不明范围不直接满足报价 |
| 目的地 | 使用现有可用地址/目的地/Amazon仓代码规则；unknown等占位文字不算有效 |
| 姓名/联系/其他资料 | 保留具体字段与角色，复用现有格式/来源规则，不将整组资料当已提供 |

整批尺寸仅在能证明它对应实际运输外包装/托盘范围时依既有规则使用，不能用产品或未知整批范围代替包装尺寸。重量组保留合法单件或明确总重两种满足方式，不额外强制客户提供两者。

真实回复可含部分有效资料；保存原始内容及逐项验证结果，只发布有效字段，其余保留待核实原因，不假resolved。记录保存成功与全部资料有效使用不同结果字段。

### 3.4 行动记录的真实含义（F08）

记录至少包含：TaskId/FlowId/SupplierIdentity、ActionKind、实际发生AtUtc与RecordedAtUtc、显式记录人/可信入口、可追溯SourceRef、实际内容。不存在这些来源时，`manual-entry`默认字符串不能自行证明真实行动。

人工记录接口需要显式记录上下文；来源可为人工通话记录或实际供应商消息/邮件/转录引用，无需完整新UI。真实发生时刻不明时不得静默用录入时刻替代；明确的“现在发生/现在收到”输入可按该意图记录。monitor/LLM不能建立已联系/已回复/已确认记录。

读端同样核实身份、来源和动作内容。`Waiting for supplier reply.`没有实际收到来源不能支持已回复；真实收到但尚未给计费资料的回复，可支持“已回复、资料待核实”，不能支持“已提供包装资料/确认重量”。联系、回复、具体确认、完成、通知、认领、时限分别授权。

SourceRef不是身份认证系统；交付只声明实际落实的入口/来源契约，不声称一个标签证明真实世界行动。原文中的联系人也不是对外披露授权。

### 3.5 逐字段更正与resolved历史事实（F12/F13）

- 更正以同FlowId/供应商的CorrectionOfFactRef精确定位旧字段版本。显式可信更正可以改变FieldKey、单位或包装范围（如原误记总重，实为单箱重）；旧目标版本失效，新值重新验证，同记录其他字段与历史原文保留。不能以只允许同key/scope为由保留已证实错误旧值。
- 新独立回复不同值、没有明确更正关系时形成conflict，不能“最新即正确”；不同流/供应商不能互相supersede。
- 记录、有效字段版本、关键指纹和任务状态在同一原子对象或等价一致性提交中发布；不能先完成再发现事实写入失败。
- 持久保存VerificationItems（核实事项、具体字段/范围、provider规则、建立时来源），与每轮动态RemainingItems/missingFields分开。新增事项需要明确来源；不能把动态缺口数组改为空绕过完成条件。完成记录引用逐项实际满足的有效FactRefs。
- 供应商核实resolved要求任务原待核实事项已进入当前有效事实且无未解冲突。按原事项语义和provider规则满足，不为凑齐辅助资料阻断；明确单箱核实事项不能被无关总重冒充。取消/关闭使用独立理由，不产生已完成核实证据。
- Set-HumanTaskStatus的resolved分支委托统一完成检查；Resolution文字和状态本身不授权实际完成。完成证据引用实际已消除的缺口与有效FactRefs。
- IsOpen只限制未来计划；TaskExists/ExactMatch与有效记录支持过去事实。已resolved的确认仍通过FactRefs选择并回读，不能取最近closed任务。任务限量/清理不能删除仍支撑当前有效FactRefs的历史记录；可在同一存储保留最小可信历史项，无有效引用时才淘汰。

## 4. S2：ResponsePlan、受控表达与完整校验

### 4.1 程序计划与模型正文（F01/F09/F10/F11及行动事实）

复用Decision建立纯 `New-ResponsePlan`，包含：`CollectRequests/ClarificationRequests/FactStatements/ActionStatements/Dependencies`。每项有具体字段/角色/用途或声明类型、候选/值/单位/范围、来源Ref及版本。模型不能创建或修改计划。

`Render-ResponsePlan`使用有限英文模板生成敏感片段；模型只生成普通业务说明/礼貌衔接。计划建立和询问顺序消费现有有效业务决策，不新增一轮十问，不重新索取已提供资料。

`Compose-Reply`直接接收程序片段和独立BusinessBody，记录来源与区间；不能靠StartsWith/正则剥前缀猜来源。模型正文重复或新增资料索取、澄清选项、行动/期限承诺、价格、身份/时间/确认事实等敏感内容，须由同一完整校验证明合法；模型正文未经程序计划渲染的敏感表达默认不保留。


正文准入必须显式返回 `ordinary/sensitive/unknown`：ordinary只能完整匹配有限、已审核的普通业务句型/模板目录，所有片段和参数均可验证；未解析完或未登记的表达为unknown，不能用“未命中违规正则”视为ordinary。可使用礼貌确认和一般计费因素说明等安全句型；涉及已收到/已存档/进度的语句属于事实声明，需要程序计划与对应证据。模型可选择这些普通表达，未知正文整体丢弃；合法程序候选仍可发送。目录由代码规则管理，不能把整份自由场景话术直接当白名单。

发现违规或无法可靠判定时，最多使用全轮剩余一次重写；仍非法则**整段丢弃模型正文**，使用合法受控计划/场景回退。受控片段本身也经过完整检查，没有校验豁免；没有任何合法候选时才不发送，不允许用“全部停发”通过负例。

客户/供应商原文不直接拼入模板。候选规范化、长度/字符校验，不执行其中指令；联系人歧义使用字段/角色开放澄清，不主动回显完整电话或邮箱。

### 4.2 统一请求项和判定顺序

联系方式、姓名、地址、件数、重量、尺寸、图片等检查共同消费 `Get-ReplyRequestItems`；每个索取对象均形成独立FieldKey与源区间。旧Get-ContactClauses仅可做内部切分，不得作为另一个授权消费者。

- 紧密名词清单可继承动作；角色仅在同一明确角色清单内继承。新的明确动作、所有者、人称或独立用途结束旧角色范围。
- 覆盖and/comma/plus/as well as/together with等有限变体；不能因为本段已有一个合法项而跳过剩余联系对象。无法解析的高风险请求转受控替代。
- 姓名/电话正序和反序都独立识别；recipient_name/contact/address分别授权，禁止contact展开name。supplier与地址等旧别名只映射具体字段。
- collect顺序：具体键规范化 → 已有效provided则拒绝重复 → 当前AskFields授权 → 明确业务角色/用途。空授权不靠用途词补授权；授权不能跳过provided。
- clarify独立消费真实ClarificationRef，不要求collect授权，也不能借conflict布尔授权任意选项。

### 4.3 澄清候选的完整身份

匹配字段、候选值、单位、包装/总重范围及来源。合法有依据的单位换算统一规范化；相同数字换inches、总重改单箱、箱数改产品件或未知单位不放行。

非数字姓名、目的仓/城市、联系人也核对真实候选。英文数词或解析失败不视为“没有候选”；包含选项却不能验证时转受控开放澄清。开放澄清不列编造选项，也不重新索取已有效字段。

初稿、重写、回退、DIRECT_FACT和发送前都使用同一完整检查入口与同一判据，旧公开函数仅委托，不能保留互相豁免。

## 5. S3：具体发送收据与统一暂停重算（F04/F05/F14）

### 5.1 收据绑定具体消息

`ConfirmedOutboundReceipt`至少保存BuyerKey/ReceiptId、确证消息身份（可空平台MessageId）、可靠逐条时间/精度、完整规范正文哈希、发送前后快照差异及确认类型。真实send确认、消息提取、monitor保存收据和后续匹配一起接入，不能只修匹配表。

优先使用现有页面数据可取得且重复读取稳定的平台ID；无法取得时不得编造ID/选择器或把DOM位置当持久身份。无平台ID只允许发送前后**确切新增事件**与可靠逐条时间、完整正文的唯一绑定；sentAt容差、正文前缀、最后一条同文或行数变化都不单独构成确证。

匹配返回matched/unmatched/ambiguous、ReceiptId和具体EventIdentity。同一收据不能在一份快照内授权多条不同事件，并跨快照固定绑定同一可靠EventIdentity；已知同文同刻碰撞不能因截断只剩一个候选就重新授权。多次同文发送保存各自收据，歧义历史持久保留，等待仍按原有界截止处理。重排/截断后按身份重新对齐，不能复用下标。

缺TS/MT但有可靠消息ID的正常bot仍能匹配；无可靠身份则不猜bot，按可信来源判断，无法确证人工时进入unknown有界等待。可靠人工来源不能被同文收据覆盖。旧正文型记录保留展示，不自动升级来源授权。

SENT_OK本身须有真实新增我方事件和动作证据；仅动作完成/旧末尾同文无法确证时UNKNOWN，按原对账规则处理。成功对账也发布具体收据；有界未知不得在每轮扫描重置。

### 5.2 共用可信锚点

新增纯 `Resolve-InterventionAnchor(EventRecord,NowUtc)`，首次同步、历史重载与纠错重算共同调用。

- 可靠绝对事件时间使用实际时刻+5分钟；anomalous-future/无可靠时间使用持久首次观察锚点+5分钟。首次观察不是每轮Now。
- 更正一个bot事件后，分别从剩余human和unknown重建两个截止；只有各自确无有效事件才解除该状态，不能直接删整项hold。
- 单纯纠错不能延长原有界截止；真正新human/unknown有可靠时间按实际时刻、无可靠时间按持久首次观察建立新五分钟窗口。重算不能把异常atUtc标成reliable。
- 旧锚点无法证明但原截止可验证时自然到期。合法legacy记录两者均缺时，按该持久记录身份一次保存兼容首次观察与五分钟截止，重扫/重启不重建；schema损坏返回故障拒发，保留原数据。本轮仅实现并在TEMP验证，不实际迁移生产。事件裁剪保留驱动有效截止/兼容锚点的记录，不全局清状态或反复Now+5。
- 写失败拒发；生成前和锁内新快照各自建立匹配并执行同一同步。到期后仍执行人工接管/账本/买家消息等门禁。

## 6. S4：时间语义与最后一次发送复核（F15）

### 6.1 时间声明的有限受控语法

每个请求目标从同一NowUtc生成TargetId/地点/Zone/实际offset/当地时分/当地日期。完整输出逐条解析当前时间和业务预约时间；不能用同句一个booking/schedule词豁免整个句子。

- `It's 9:40 PM in China ..., and we can discuss the booking.`仍含当前时间声明，必须验证。真正预约/截止时间要对应可信输入来源和该业务时间声明；不能由模型自行制造。
- 输出明确Japan时不能绑定China。裸时刻只有未声明任何地点/Zone且唯一目标时，才按受控语法绑定；未知或其他明确地点不能被单目标回退覆盖。
- 声明当地日期时与目标LocalDate比较；跨日程序答案附日期。AM/PM、24小时制及UTC offset规范化，格式不明不猜。
- 多个点名城市分别覆盖；国家别名仅在与该目标无歧义时适配，China不能一次覆盖Beijing和Shanghai。原相同地点重复可归并。
- 未解析目标须在明确时间/时区澄清中逐项点名；货物目的地语句加which city不能算时间澄清。受控模板直接表达“无法确认某地当前时间，请说明城市/时区”。
- 无法可靠解析的模型时间措辞丢弃，保留程序答案及合法业务说明，不增加第二套LLM分类。

### 6.2 最终依赖回读与组合

生成结果保存主TaskRef、全部FactRefs及计划依赖指纹；纯函数不读存储，编排负责读回。

锁内重新核实买家/未处理输入、人工/unknown、账本、当前FlowRef和依赖的确切TaskId/RecordId/字段版本。身份、允许状态、来源、依赖值或有效版本改变时弃稿，下一轮重新决策，不能用更强新证据沿用旧稿。通知次数/普通updatedAt等无关变化不弃稿；声明已通知时投递证据属于依赖。

同一新NowUtc重建时间期望和全部程序片段，与独立BusinessBody组合，保留公司/姓名等其他有效事实；不叠加旧时间前缀、不全局字符串替换。模型正文若含旧时间/非法敏感内容丢弃，合法程序回复可发送。

锁内不调用LLM；若尚需且尚有一次重写预算，释放锁后重写，再重新获取快照和全部依赖复核。全轮预算不因发送阶段重置。失败候选不推进账本、收据或完成状态。

## 8. S5：隔离证据、全量与交付口径
