# 消息来源三类判定与接待恢复修复规格

日期：2026-10-07（北京时间）。状态：**执行版：业务规则已确认，可交由其他会话实施；本会话尚未修改功能代码**。

执行工作区：`C:\path\to\alibaba-auto-reply`。用户要求输出可交接执行的规格；接收明确执行指令的会话应按本规格实施、离线验证并同步文档，无需重复询问已确认业务规则。生产启停、真实消息/通知投递及新版本发布按第 7、11 节界定的独立操作范围处理。

来源：[设计交接](../消息来源三类判定_设计交接_20261006.md)、[原始观测](../消息来源三类判定_原始证据_20261006.md)，以及本次对当前磁盘源码、测试和部署记录的只读核查。本文不代表重新验证了实时页面、当前进程加载版本或通知投递效果。

## 1. 目标与已确认决策

目标是恢复可持续的自动接待，同时保持人工让路、白名单和重复发送保护。来源识别只是其中一环；本次范围包括真实消息抽取、来源证据、送达确认、持久化、调查通知及恢复调度。

| 决策 | 已确认行为 |
|---|---|
| 平台自动回复 | 不算人工介入。会话有尚未由人工或本项目处理的待回复诉求时，本项目复核并接管，不要求买家再发一条；历史平台消息本身不触发补发 |
| 人工回复 | 五分钟暂停；连续可信人工回复更新截止。白名单保留，白名单会话不自动恢复 |
| 暂停期间新消息 | 截止后重新读取会话，处理尚未回答的买家消息，不要求买家重复发送；已由人工处理的轮次不补答 |
| 未知来源 | 以 20 秒为目标周期重新取证，五分钟仍无法确认则进入人工调查。超时不是来源证明，不直接放行 |
| 调查提醒 | 先持久化待办，再通过现有企业微信通道提醒一次。同一问题重复扫描不重复通知；失败保留待办及投递状态 |
| 无法确认送达 | 进入待确认发送，停止同一回复的自动重发。确认已送达则登记真实收据；有可靠未送达证据才允许重新进入发送流程；歧义转人工调查 |

20 秒是调度目标，实际受串行扫描与页面读取耗时影响，不是平台端到端 SLA。现有回复内容政策、业务事实、去重键语义与真实发送适配器保持各自职责；调整的是它们前后的来源、收据、状态和调度闭环。

## 2. 当前缺口与事实边界

1. `monitor.ps1` 的消息抽取清洗掉自动接待标签，只输出角色、时间、正文、附件和卡片标记，没有可信三类来源或平台消息 ID。
2. 实际来源判定支持 buyer/bot/human/unknown，没有独立 platform 类。时间戳不证明发送者；当前无标记人工推断也不能外推为通用规则。
3. 收据 DOM 适配器纳入全部 wrapper，平台 MessageId 固定为空。发送前任一事件身份缺失可令收据拒绝；因此卡片和真实消息没有统一抽取边界会影响确认。
4. 已有补发对账补丁在页面发送阶段成功且会话随后离开待回复列表时，可推进 replied 去重状态，但明确不发布收据或 sent_records。这缓解重复补发，不能证明消息来源。
5. 生产入口先同步历史人工/unknown，再判断尾部。有效等待不因买家新发言消失；截止后尾部仍为 human/unknown 时仍拒发。恢复必须同时核对当前待回复事件与其他门禁。
6. 现有任务按买家、业务流、供应商等合并，没有来源/收据调查的事件幂等键和完成契约。通知仅接在成功回复分支，未知来源阻断时没有调查提醒链。

原始采样不足以证明“去优化只属于本项目”“无标签必为人工”或“自动接待标签可区分平台与本项目”。当前硬编码空 ID 也不能证明平台没有稳定 ID。这些都是实施前必须取证的事实，不作为测试预期。

本规格按用户已确认范围修订旧交接的窄范围及验收建议：不能把所有带自动标签的消息统称 bot；不能无条件令最新买家消息绕过有效人工暂停；不能只测尾部纯函数而声称生产恢复。历史交接保留原文。

## 3. 三类来源与送达状态分别建模

### 3.1 统一消息事件

抽取层先保存逐条结构化观测，再清洗模型正文。monitor、消息规范化、来源分类与收据快照共用真实消息边界和身份构造，不再各自扫描不同集合。

必要字段：会话身份、方向/角色、原文及规范化正文、正文哈希、逐条时间及可信度、平台 MessageId（若可取得）、结构类型、附件、逐消息绑定的原始来源字段/标签、采样时刻、抽取规则版本、事件身份可信度。

- 方向以已核实的左右侧结构为依据；显示名、翻译标记不得覆盖明确方向。冲突或方向不明时显式记录。
- 明确的 flow 总结/进展卡、公共控件与结构噪声不充当买家问题、人工回复或发送事件。不能因为出现“系统自动发送”就删除所有平台真实回复。
- 图片、文件、短消息和系统自动回复中的真实消息保留。无法建立身份的真实气泡必须保留为不确定观测，不能为通过收据测试而删除。
- 优先平台 ID；缺 ID 时仅在逐条时间、方向、完整正文及上下文足以唯一识别时采用组合身份。只有正文、DOM 下标或窗口位置不构成可信事件身份。
- 来源标签作为独立元数据，不进入正文哈希、去重键或事件身份。翻译来源不是发送来源；正文里出现类似 `@@SRC` 的文本不能成为可信元数据。

### 3.2 来源结果

我方来源为 `platform / project / human / unknown`；buyer 与噪声类型另列。结果必须包含证据引用、可信度、规则版本和冲突原因。

| 来源 | 可接受依据 | 行为 |
|---|---|---|
| project | 与当前事件唯一匹配的有效本项目收据；或经独立验证、明确绑定该事件的本项目发送者证据 | 不启动人工暂停；继续按待回复和去重条件处理 |
| platform | 已验证平台原生发送者字段或确属平台自动回复的独占证据 | 不启动人工暂停；允许项目复核并接管 |
| human | 已验证人工发送者证据；或有出处、绑定确切事件的人工来源确认 | 建立或重算五分钟暂停 |
| unknown | 缺证据、仅有时间/通用自动标签、身份歧义或可信证据冲突 | 相关轮次等待、重新取证及调查 |

证据规则：

1. 强证据必须有真实出处并绑定同一事件。有效收据与可信平台字段冲突时转 `source_conflict`，不按固定优先级硬覆盖。
2. 标签只有经过来源真值对照、确认独占性和绑定范围后，才可进入分类规则。“去优化”目前仅作原始观测；不能独立认定 project。
3. 无标签、无时间或已无历史发送记录，不足以自动认定 human。旧显式 bot/human 标记仅在生产者与事件绑定可信时兼容；所有旧入口委托共享判定，消除“有时间就是 bot”的旁路。
4. 无法恢复证据的旧消息保留 unknown；不能按正文批量补发收据或把历史 unknown 批量改成 project。
5. 来源更正只更新确切事件，并据此重算暂停。更正一条误判消息不能清除其他有效人工事件。

### 3.3 送达结果

另行记录 `not_attempted / pending_confirmation / receipt_verified / not_delivered_verified / delivery_ambiguous / persistence_pending`。来源已知不等于已送达；页面点击成功、离开待回复列表、去重账本推进也不等于取得有效事件收据。

## 4. 发送收据与持久化闭环

发送流程保留实际适配器和会话锁：

1. 发送前回读会话身份、当前买家触发、来源/暂停、白名单、去重与既有待确认发送；草稿依赖变化则丢弃或重建。
2. 在隔离于生产数据的测试中验证共享真实消息抽取器；生产发送前保存规范化快照及其身份质量。
3. 先持久化唯一 AttemptId、买家触发引用、目标会话、待发送完整正文/哈希、发送前快照证明和阶段状态，再执行输入/点击。落盘失败时不执行发送。
4. 发送后读取同口径快照，确认唯一新增事件、完整正文和会话身份。先前未知真实气泡或多候选仍妨碍证明时保持 unverified，不伪造 ID 或收据。
5. 取得真实收据后，可靠保存收据，再幂等更新 sent_records 和 replied。跨文件不能假称一次原子提交；使用持久提交阶段与可恢复对账处理部分成功。
6. sent_records 写入失败或返回 false 必须显式处理。保留已送达证明与待持久化状态，暂停该会话的新增发送并生成调查，不因落盘失败再次发送已送达正文。
7. 页面看似发送但收据未确认时保留 pending_confirmation，不重发同一触发。离开待回复列表可继续使用现有合规去重对账路径，但不由此提升来源或伪造收据。
8. 后续若获得有效事件收据，补齐幂等登记，纠正该事件的 unknown 并重算等待。若可靠证据证明未送达，再核对原买家诉求是否仍有效、是否已被人工处理，以及所有发送门禁，然后允许重试。

“消息不在当前窗口”“会话不在待回复列表”或“暂时没看到正文”单独不能证明未送达。重启、超时和页面窗口截断不得触发盲目重发。

## 5. 暂停、等待与恢复调度

优先级为白名单 → 有效人工暂停 → 相关未知来源/待确认发送 → 当前待回复触发与去重 → 生成与发送复核。

### 人工暂停

- 使用可信事件 UTC 时间；无可靠时间但来源已确认时使用持久首次观察锚点。连续新人工事件更新截止，同一事件重扫/重启不延长。
- 期间保存尚待处理的买家事件和下一次检查时刻。到期主动进入重新读取队列，预览未变化也不能永久跳过；到期后处理积压的新买家消息。
- 人工回复之后没有新的未处理买家诉求时，不补答旧轮次。是否仍有未处理诉求结合事件顺序、待回复状态和已记录人工处理范围核对；不能仅因任意历史人工气泡就认定全部问题已答完。
- 白名单优先且持久。移出名单后仍完整核对当前状态，不补发过期草稿。

### 未知来源

- 相同事件有固定首次观察和截止，周期观察不重开五分钟窗口。来源有可信更正时按更正结果重算。
- 五分钟后仍无法确认，建立或更新调查；时间到期不把 unknown 改成 project、人工作答或“已安全送达”。
- 门禁说明阻断的是哪个当前事件/发送尝试，不能因任意久远 unknown 永久封锁全部后续会话。
- 若旧 unknown 已不在当前我方尾部，等待已到期，最新买家是可信新事件且无有效人工暂停、无未确认发送或其他相关冲突，可按正常判据处理新诉求；这是当前事件重新复核通过，不是因超时推定旧消息来源。旧调查保留。
- 当前相关我方尾部仍 unknown、身份冲突或关联送达仍待确认时继续拒发，并显示调查原因。

调度维护 `nextCheckAt` 与原因（人工截止、未知来源检查、发送对账），不借用“已成功发送冷却”伪装来源等待。页面读取须协调页面锁；生成时不长时间持锁，发送前再次读取并校验。

## 6. 来源与送达调查

建立独立调查契约，复用现有原子存储、锁与 dsh-im 投递适配器，不直接套用供应商核实任务的 FlowId 合并和 resolved 条件。

必要字段：InvestigationId、kind、买家/会话、EventRef 或 AttemptId、事件身份质量、原始证据引用、首次观察、固定截止、状态、下一次核查、通知尝试/结果、操作者、确认依据、审计记录。

类型至少覆盖 `source_unverified / source_conflict / receipt_pending / receipt_persistence_failed`。

- 幂等键使用会话 + 调查类型 + 确切事件/尝试，不同事件不能因同买家或同正文随意合并。身份无法唯一建立时创建显式歧义调查，不能伪造唯一关联。
- 先持久化调查，再独立于“买家回复成功”分支触发提醒。页面阻断时也能提醒。
- 一次成功提醒不再因重复扫描重发；投递失败或响应不明分开记录，支持人工显式重试。通道没有幂等确认能力时不承诺外部严格 exactly-once。
- 通道失败不删除调查、不释放发送闸门、不写成已通知。探活、配置存在、操作者认领或任务状态标签均不是投递/来源/送达证明。
- 提供项目内操作入口：列表、详情、认领、提交来源确认或送达证明、重试通知及查看审计。具体入口可为 PowerShell CLI，交付时须可用；不依赖尚未接通的 UI 或默认假定外部 DSH 已配置命令路由。
- 关闭调查必须按类型核验：来源调查提交真实出处和确切事件映射；收据调查提交有效送达或未送达证明；持久化调查完成真实回读。仅标 resolved、填写“已处理”或给出来源猜测不得解除保护。
- 人工确认来源只授权确切来源更正，不制造机器人发送收据。确认未送达也不授权发送过期或已被人工处理的回复。

活跃调查、未确认发送和它们依赖的证明不能被普通“最近 N 条”剪枝丢掉。已过期等待保留必要身份/首次观察墓碑，防止旧消息重扫重新等待。保留策略、迁移和损坏库行为纳入实现验收，不能依据当前未落实的声明值声称已有容量限制。

## 7. 兼容、日志与操作边界

- 保留当前工作区的补发对账修复和测试；不覆盖其他未提交改动。既有去重键不清空、不批量重算。
- 各存储明确版本、实际写入 schema 和可核验迁移；先备份再迁移，原子回读失败停止该会话，不以删除损坏库恢复发送。
- 旧消息格式可读取，标签与正文解耦；元数据升级不能改变既有买家正文哈希。来源字段添加须同步 pause 事件、生成/发送复核和报告消费者。
- 日志包括规则版本、事件/尝试引用、分类及理由、等待截止、下次核查、调查和通知状态、收据与持久化阶段。公开测试与文档用虚构资料；生产证据只放运行数据根，交付副本脱敏。
- 新路径登记 Get-SkillPath、配置模板、生产路径指纹与 Offline 隔离根。真实身份、凭据、客户消息不进入公开夹具或提交。
- 本次执行交接包含源码、测试、调查 CLI、迁移/回滚说明和相关文档；生产启停、真实模型/消息/通知测试、版本发布及 GitHub 更新需接收会话核对该会话中的明确授权，不能仅凭本规格自动执行。独立操作尚未授权时，继续完成可实施和离线验证的部分，列明剩余真实验收。

## 8. 实施顺序与取证门槛

### S0：对照证据与失败基线

先只读查找有可靠发送者出处的三类真实样本，核对标签绑定范围、方向、ID/逐条时间、flow 卡、图片与不同会话模板。优先既有页面/API 字段、已确认发送记录和人工/平台审计，不能拿语言、正文风格或旧推测当真值。

若无法取得某类可靠对照，将该证据规则保留未验证；必要的真实测试发送只能在后续明确授权的可控会话进行。没有证据就不宣布已经可靠三分。先保存实际抽取器、收据适配器和生产入口的失败输出，再实施对应改动。

### S1：共享事件抽取与分类

统一会话与收据抽取集合，保存来源元数据和事件身份质量；完成四态我方来源以及全部旧入口/消费者接线。规则只使用 S0 已验证证据，覆盖冲突和降级。

### S2：真实收据与待确认发送

实现发送前持久尝试、真实增量确认、部分持久化恢复、未知送达对账与不重发保护；保留当前合规去重补丁。

### S3：暂停、恢复与调查通知

实现固定锚点、到期重新读取、积压新买家处理、平台接管、事件级调查和独立提醒。操作 CLI 及其完成证明契约同时交付。

### S4：交叉回归、文档与上线验证

复跑真实抽取器和 monitor 入口的隔离矩阵、原有回复/暂停/收据/去重回归，登记分层清单；分别报告 LogicTests、IsolationChecks、ProductionPathAudit、Overall 与原生退出码。生产归因不明保留 UNRESOLVED/exit 3。

离线结果不替代真实页面与通知验收。后续部署前确认代码/配置/存储备份与回滚方案；按项目部署手册重新加载指定进程，在可控会话验证真实来源、收据、暂停恢复、对账及提醒，再观察持续运行。

## 9. 必须通过的验收矩阵

下列用例必须验证抽取、分类、状态、实际生产消费者与发送前复核，不能只构造理想 snapshot 测辅助函数。

| 编号 | 场景 | 必须结果 |
|---|---|---|
| A01 | 已验证的平台来源，当前诉求仍待回复 | platform；不启动人工暂停；本项目按正常门禁接管 |
| A02 | 只有通用自动接待或去优化标签，无独占出处 | 不猜 project/human；unknown、明确证据缺口 |
