## §0 一句话目标

**不再修判据，而是换掉"是否回复"的唯一出口**：把现在由「待回复列表 + 位置/条数/预览串」派生出的三重判据，替换为**单一半纯函数 `Test-ShouldReply`**（证据锚点 = 买家最后一条消息是否出现在我最后一次回复之后），外加**整轮硬门禁**（页面/会话名不合格 ⇒ 一条都不发）与**会话级限流兜底**（同一买家 N 分钟内至多 1 条）。

三条硬成功判据（缺一不可）：

1. **回放 213 份真实快照，`Test-ShouldReply` 判"应回"的会话，其账本 hash ≠ 该会话最后一条买家消息 hash**（0 例外）。
2. **页面缺失时会话处理数 = 0、发送数 = 0**（复现本次事故现场，新代码必须一条都不发）。
3. **同一买家在 15 分钟内不可能收到第 2 条**（可构造用例证明）。

## §3 反思：为什么这件事反复发生（老板问的就是这一节）

**不是判据不够聪明，是三个结构性错误一直没被处理。**

| # | 病根 | 具体表现 | 为什么"再修一次"必然再犯 |
|---|---|---|---|
| R1 | **判据建立在不稳定信号上** | 判据从"列表里的位置""条数""预览串"派生；这三者在同一会话上每轮都在变（§2.2） | 不稳定的输入 ⇒ 任何判据都会抖。**加 if / 加阈值只是把抖动挪到另一条分支** |
| R2 | **"是否回复"没有唯一出口** | 现至少有 3 套并存：`Test-DedupHit` / `Test-NewBuyerMessage` / `$ctx.skipCooldown`+`$already` 兜底闸门；另有 `INQUIRY-ALERT`、`QUOTE-REMIND`、`nudge`、失败补发队列 | 改一处不影响另一处；第 6 次修复改了主判据，`QUOTE-REMIND` 与回退路径照旧能发 |
| R3 | **失败不闭合：错了一条也停不下来** | 页面已 `no onetalk page found`，monitor 仍逐会话处理并刷屏 8 条/轮；8 分钟内 8 条消息无人拦 | 没有"整轮熔断"，没有"单会话次数上限"，**错了就错到底** |
| R4 | **验证方式与实际失效模式不匹配** | 每次都用"纯函数单测 + 历史快照回放"验收；`failedFiles=0` 与"线上正在误发"可以同时成立（本次就是：22 个测试文件全绿，同时 8 分钟误发 8 条） | 单测喂的是**我们自己构造的稳定输入**；真实 DOM 抖动、页面缺失、启动态从未进过测试 |
| R5 | **启动/停机状态没有安全态** | 停机 9 小时期间累积会话；重启第一轮 `savedCount=-`（账本读到空）⇒ 全部按首次问询重发 | 停机越久，重启伤害越大；**没有"冷启动只观察不发"这一档** |
| R6 | **唯一的兜底（发对人校验）本身被页面错位击穿** | `ABORT_WRONG_CONVO (expected=买家L, current=买家G)` | 兜底依赖"当前打开的会话"，页面一错位它只能报错、不能阻止前 7 条已经发出去 |

**流程层面的直接责任（规划会话自陈，必须写入 REPORT 供老板追责）**：
> 我在 11:42 执行"恢复运行"时，只验证了"有 `Scan cycle done`、进程活着"就宣布成功，**没有先验证判据在"页面缺失/列表抖动/账本读空"这三种已知状态下会不会误发**。恢复运行的验收标准必须包含"误发为 0"，而不是"循环在跑"。

**因此本 spec 的取向**：**不再增加第四条判据**。要做的是**减少出口、并把出口建在不会抖的证据上**。

## §4 修复设计

### §4.1 唯一出口：纯函数 `Test-ShouldReply`

**位置**：`scripts\reply_engine.ps1`（与既有纯函数同处，便于被 `monitor.ps1` 与测试共同引用）。
**性质**：纯函数 —— **不读文件、不碰页面、无副作用**、可单测。

```
Test-ShouldReply -ConvoLines <string[]> -LedgerKey <string> -NormLastBuyerHash <string>
                 → [pscustomobject]@{ Reply = <bool>; Reason = <string> }
```

**输入解释**
- `$ConvoLines`：该会话在快照中的原始行（含 `[BUYER]` / `[ME]` 标记与 `@@TS` / `@@OT` 标记）。
- `$LedgerKey`：账本中原样取出的字符串（形如 `HASH|5`、`HASH|1789826752752`、或 `HASH`）。**不得在此函数外解析第二段。**
- `$NormLastBuyerHash`：`Get-StableHash(Get-NormalizedMsgText(买家最后一条消息原文))`，由调用方算好（保证与账本同口径）。

**判定规则（顺序固定，先命中先返回；`Reason` 必须逐字使用下表字符串）**

| 序 | 条件 | Reply | Reason |
|---|---|---|---|
| 1 | `$ConvoLines` 中 `[ME]` 行数 ≥ 1 **且** 最后一行 `[BUYER]` 之前存在 `[ME]` 行（即我方已有一条回复排在买家最后一条消息之前） | `$true` | `BUYER_AFTER_ME` |
| 2 | 完全没有 `[ME]` 行（卖家从未在此会话发言） | `$true` | `NO_SELLER_MSG`（**新询盘**） |
| 3 | `$LedgerKey` 第二段可解析为条数 **且** 该条数 == `$ConvoLines` 中 `[BUYER]` 行数 | `$false` | `LEDGER_COUNT_MATCH` |
| 4 | `$LedgerKey` 第一段（hash）== `$NormLastBuyerHash` | `$false` | `LEDGER_HASH_MATCH` |
| 5 | 以上都不成立（无法证明是新消息） | `$false` | `UNCERTAIN_FAILCLOSED` |

> **为什么规则 3/4 是"不发"而不是"发"**：两者都表示"账本记录的最后一次回复，针对的正是当前最后一条买家消息" ⇒ 没有新东西可说。
> **规则 5 是本 spec 的取向声明**：**证明不了就不发**（fail-closed）。宁可漏回一条真询盘（会留在待回复列表，老板能看见），也不误发一条骚扰（不可撤回、且直接掉客户）。

**必须删掉的旧出口（同一次提交内完成，不得分两次）**

| 删除对象 | 位置 | 说明 |
|---|---|---|
| `Test-NewBuyerMessage` 的**回退分支**（"文本 hash 不同即新消息"） | `reply_engine.ps1` 第 627–630 行 | 第 6 次修复的漏洞所在 |
| `Test-DedupHit` 的调用 | `monitor.ps1` 去重块 | 与 `Test-ShouldReply` 语义重叠 |
| monitor 里 `$isNew / $already / savedCountSeg` 三件套及其"兜底闸门" | `monitor.ps1` 第 977–995 行 | 由 `Test-ShouldReply` 单点取代 |
| `QUOTE-REMIND` / `nudge` 的**自动发送**路径 | `monitor.ps1`、`quote_remind.ps1`、`nudge.ps1` | **改为一律只推企微/dsh-im 提醒，不自动发给买家**（老板原话："又给不需要回复的客户发消息了"——提醒不是消息） |

### §4.2 硬门禁（G1/G2/G3；不满足 ⇒ **整轮 return，零发送**）

| 门禁 | 触发条件 | 动作 | 必须留痕 |

### §4.3 会话级限流（G4，抖动兜底 —— 即使判据判错也发不出去）

| 规则 | 阈值（配置键，写 `config.json` 与 `config.json.example`） | 命中动作 |
|---|---|---|
| 同一买家最小间隔 | `reply_min_gap_min = 15` | 跳过 + `RATE-SKIP buyer=<key> gap=<m>m` |
| 同一买家日上限 | `reply_daily_max_per_buyer = 3` | 跳过 + `RATE-SKIP-DAILY buyer=<key> n=<n>` |
| 整轮发送上限 | `reply_round_max = 2` | 本轮停止处理剩余会话 + `ROUND-CAP hit=2` |
| 整日发送上限 | `reply_daily_max = 40` | 停止发送 + dsh-im 告警 `RATE-LIMIT-DAILY` |

## §7 开放问题（执行者**不得自行拍板**，命中即停下写 REPORT 并等老板回答）

1. **`[ME]` 标记的可靠性未验证**：快照里我方消息是否**始终**带 `[ME]` 且不漏行？若抽取不稳，规则 1/2 会失效。执行者必须先做一次**只读验证**（取 10 份含我方回复的快照，人工核对 `[ME]` 是否与我方回复时间线一致），把结论写入 REPORT 再继续；不一致 ⇒ **停手**。
2. **`@@TS` 已被证明是抓取时刻的合成值**，本 spec 的判据**不依赖**它。若执行者认为必须依赖时间戳才能判"谁在后"，**停手**（那是第 6 次修复前的方向，已被证伪）。
3. **待回复列表的出现/消失规则未知**：为什么 `[已读]`、甚至我方最后发言的会话仍留在列表里？本 spec 用"列表只当触发器"绕开它；若执行者发现某类会话**永不进列表**（导致漏回），记录并上报，不要自行扩大邮箱/轮询范围。
4. **是否需要对"已误发的买家"做人工补救**：本次 11:42–11:50 已对外发出 8 条（买家E×2、买家G×2、买家R×2、Fahad×1、Lena 被闸门拦下）。**补救口径（是否私信致歉/是否标记这些会话免打扰）由老板决定**，执行者只负责把清单整理进 REPORT。
