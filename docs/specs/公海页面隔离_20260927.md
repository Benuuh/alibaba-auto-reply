## §0 一句话目标

**给公海一个自己的 OneTalk 标签页,用 URL 标记把它和自动回复用的那个页永久区分开,使两个子系统可以同时运行、互不抢页。**

三条硬成功判据(缺一不可):

1. **两个 OneTalk 标签页同时开着时,`GET-SNAPSHOT`(monitor)与公海取页各自稳定命中自己的页,连续 5 轮不串。**
2. **公海发送的消息,必须落在公海自己那个页所对应的会话里**(不是"名字对上就算")。
3. **`Test-PageSelect` 全绿**:`scripts\cdp.ps1` 与 `scripts\lib\cdp.ps1` 的 `Get-Page` **逐字未改**。

## §1 为什么要做(实测事故,规划会话亲历)

### §1.1 现象:开第二个 OneTalk 页 → monitor 立刻换页

2026-09-27 14:03,规划会话用 CDP 新开一个 OneTalk 标签页做隔离可行性验证。结果:

```
新页 id=DC8C3005 被 Chrome 排在第一位
⇒ Get-Page 取"第一个匹配 onetalk 的页" ⇒ 返回新页
⇒ monitor 下一轮就改用新页了
```

`monitor.log` 随即出现 `14:05:45 RETRY-OPEN ... NOT_FOUND (list items=0)` 的连续失败,与 12:54 那次失败形态一致。

### §1.2 根因:三个取页点全都取"第一个"

| 位置 | 代码 | 行为 |
|---|---|---|
| `lib\cdp.ps1` L40-57 `Get-Page` | `$onetalk = $pages \| Where-Object { $_.url -match 'onetalk\.alibaba\.com' }` | 取**第一个** OneTalk 页 |
| `scripts\cdp.ps1` 同名函数 | 同上(必须逐字一致,`tests\page_select.tests.ps1` 锁死) | 同上 |
| `gonghai\gonghai_cdp.ps1` L55 `Get-GonghaiOnetalkPage` | `$pages \| Where-Object { $_.url -match $script:OnetalkUrlPattern }` | **也是第一个** |

**⇒ 开两个页不是"各用各的",而是"互相抢第一个"。**

### §1.3 已实测到的风险(必读)

规划会话打开新 OneTalk 页时,该页 URL **没有** `activeAccountId`,页面**自行选择**账号,三次读取拿到三个不同的 `activeAccountId`(1673884852 / 948732968),**都不同于正页的 285965039**。

**老板已裁决:卖家账号只有一个,不为此加防护。** 但本 spec 仍要求 **§5-P10 的双重校验**必须实现 —— 理由:它是"发对人"的最后一道,成本极低,且不依赖"账号只有一个"这个前提长期成立。

> ⚠️ **在本次修复上线之前,禁止手动开第二个 OneTalk 标签页。** 一旦被 monitor 选中,可能以非预期账号对外发言。

## §2 方案:URL 标记 + 各自按标记取页

### §2.1 标记形态(已确认可行)

标记加在 **query string**,**不要**动 hash(该站用 hash 路由,URL 以 `#/` 结尾,动 hash 有路由风险):

```
公海专用页: https://onetalk.alibaba.com/message/weblitePWA.htm?<原有参数>&dshgh=1#/
monitor 正页: https://onetalk.alibaba.com/message/weblitePWA.htm?<原有参数>#/     ← 不变
```

- 公海取页:`url -match 'onetalk\.alibaba\.com' -and url -match 'dshgh=1'`
- monitor 取页:**保持现状**(取第一个 OneTalk 页,不加标记判断)

**为什么 monitor 侧不改**:`Get-Page` 被 `tests\page_select.tests.ps1` 逐字锁死,且 monitor 是生产主链路,改它风险远大于收益。**只要公海永远只用带标记的那个页,monitor 用哪个页都不会干扰公海。**

### §2.2 公海页的生命周期

| 时机 | 行为 |
|---|---|
| 公海首次运行 | 若不存在带标记的页 ⇒ **新开一个**(CDP `PUT /json/new?<url>`),而不是复用无标记的页 |
| 页已存在 | 直接复用 |
| 页被关掉 | 下次运行时重新新开 |
| Chrome 被重启 | 见 §3.4(`chrome_ensure` 需保留标记) |

## §3 代码改动位置

### §3.1 `gonghai\gonghai_cdp.ps1` —— 新增标记常量与建页能力

1. 新增常量(与 `$script:OnetalkUrlPattern` 并列):
   ```powershell
   $script:GonghaiTabMarker   = 'dshgh=1'
   $script:GonghaiOnetalkPattern = 'onetalk\.alibaba\.com.*dshgh=1'
   $script:OnetalkBaseUrl     = 'https://onetalk.alibaba.com/message/weblitePWA.htm'
   ```
2. 新增函数 `Get-GonghaiOnetalkUrl`(返回带标记的完整 URL)。
3. 新增函数 `Ensure-GonghaiOnetalkTab`:
   - 先 `Get-GonghaiPage -UrlMatch $script:GonghaiOnetalkPattern`,命中即返回;
   - 未命中 ⇒ 用 CDP `PUT http://127.0.0.1:<port>/json/new?<url>` 新开,轮询等待页面就绪(最多 N 次 × 间隔);
   - **绝不**返回无标记的页。
4. `Get-GonghaiOnetalkPage` **改为只认带标记的页**(`$script:GonghaiOnetalkPattern`)。
   ⚠️ 这会改变该函数语义,`Open-OneTalkSearchPanel`(L349)等调用点随之自动变严 —— 这是**期望行为**。

### §3.2 `gonghai\gonghai_lib.ps1` —— 调用点换默认匹配串

所有 `-UrlMatch 'onetalk\.alibaba\.com'` 改为 `-UrlMatch $script:GonghaiOnetalkPattern`。受影响调用点(逐条核):

| 行 | 函数 |
|---|---|
| L318 | `Find-OneTalkConversation` |
| L328 | `Open-OneTalkSearchPanel`(参数缺省值) |
| L349 | `Open-OneTalkSearchPanel`(`Get-GonghaiOnetalkPage`) |
| L404 | `Invoke-OneTalkSearch` |
| L427 | `Assert-OneTalkConversationName` |
| L252 | `Restore-OneTalkList` |

> `Restore-OneTalkList` 必须一起改 —— 否则"恢复页面"会去动 monitor 的页。

### §3.3 `lib\send.ps1` —— 支持指定页面(公海发送落点)

**现状**:`Send-OneTalkMessage` 内部全部用 `Invoke-CdpEval`(→ `Get-Page` → 第一个 OneTalk 页)。
**后果**:即使公海读页用标记隔离了,**发送仍会落到 monitor 的页上** —— 隔离等于白做。

**改法**(保持向后兼容,monitor 一行不改):

1. 新增可选参数 `-Page`(默认 `$null` = 现状行为)。
2. 内部 JS 执行改走一个本地辅助函数,例如:
   ```powershell
   function Invoke-SendEval([string]$Js) {
       if ($script:SendPageOverride) { return Invoke-GonghaiEvalOnPage -Page $script:SendPageOverride -Script $Js }
       return Invoke-CdpEval $Js
   }
   ```
   (或用 `-Page` 参数逐层传递;两种实现都可,**但必须保证不传 `-Page` 时行为与现在逐字一致**)
3. `gonghai_probe.ps1` 调用时传 `-Page`(取 `Ensure-GonghaiOnetalkTab` 的返回值)。

> ⚠️ `tests\should_reply.tests.ps1` 有白名单断言:**允许的 `Send-OneTalkMessage` 调用点 = `lib\send.ps1`(定义)+ `monitor.ps1` + `gonghai\gonghai_probe.ps1`**。改动不得新增第四个调用点。

### §3.4 `scripts\chrome_ensure.ps1` —— 重启后保留标记

**现状**(L147):重启 Chrome 后固定导航到
`https://onetalk.alibaba.com/message/weblitePWA.htm`(**无标记**)。
**后果**:Chrome 一重启,公海页的标记就没了 ⇒ 下次公海运行要重新开页(可接受),但**更糟的是**:重启后 monitor 与公海可能又变成共用一个无标记页。

**改法(最小)**:`chrome_ensure` **不需要**知道公海 —— 只要保证
**重启后不存在无标记的 OneTalk 多开**即可。具体:

- 导航目标 URL 不变(monitor 需要它);
- 但**若发现存在带标记的页,不得关闭/覆盖它**;
- 并在 `Restore-OneTalkList`/`Ensure-GonghaiOnetalkTab` 中,于 Chrome 重启后**检测标记页是否还在**,不在则重开。

> 即:**以公海侧自愈为主**,`chrome_ensure` 只做"不破坏"。**不得**为此在 `chrome_ensure` 里写公海逻辑(会造成反向依赖)。

## §5 P10:发送前双重校验(**必须做**,理由见 §1.3)

公海发送前,除既有的"会话名 == 期望名"外,还要**确认这条会话出现在公海自己那个页上**。

**判据(任一不满足 ⇒ `ABORT_WRONG_PAGE`,不发送、记日志、清锁)**:

1. 发送所用页的 `url` 匹配 `$script:GonghaiOnetalkPattern`(带标记);
2. 会话打开后,该页 DOM 里能读到与期望名**精确相等**的会话名。

**为什么不是"校验账号"**:老板已裁决账号只有一个;而"页对不对"是本次真正引入的新风险,必须校验。

## §8 编码铁律(踩过的坑,逐条照做)

1. **改完 `.ps1` 必须复验前三字节 = `239,187,191`**(UTF-8 BOM)。编辑工具会**静默去掉 BOM**,已有 `runtime\tools-local\ensure_bom.ps1` 可用。
2. `monitor.ps1` 只在启动时 dot-source 一次 ⇒ 改 `lib\*.ps1` 后**必须重启 monitor**(走 `Start-ScheduledTask -TaskName 'AlibabaAutoReplyWatchdog'`,**禁止** `Start-Process`)。
3. **改动前备份**:`scripts\cdp.ps1`、`lib\cdp.ps1`、`lib\send.ps1`、`gonghai\*.ps1`、`chrome_ensure.ps1` 各留逐字节副本。
4. **不要动 `Get-Page`**。它是被测试逐字锁定的共享函数,任何改动都会同时影响 monitor / 公海 / okki / waimao 四条链路。
5. **禁止在排查过程中手动开第二个 OneTalk 标签页**(§1.3),除非本 spec 已合入。
6. 进程排查时注意**命令行自匹配陷阱**:用 `Where-Object { $_.CommandLine -match 'gonghai' }` 查进程时,查询命令自身也会命中。用精确匹配(如 `-match 'gonghai_probe\.ps1'`)。

## §10 已知风险(如实登记)

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 公海页与 monitor 页**同时 Active** 时,只有一个是可见的(Chrome 每窗口一个活动标签) | 两个子系统都靠 CDP 求值,不依赖焦点;但**若发现后台页 `innerText` 为空**(规划会话怀疑过此现象,未定因),E2/E3 会暴露 ⇒ 届时改用 `textContent` |
| R2 | 公海建页会**新开一个标签页**,占用内存 | 一次性,可接受 |
| R3 | `chrome_ensure` 重启后标记页消失 | §3.4 由公海侧自愈 |
| R4 | `Send-OneTalkMessage` 加参数可能影响 monitor 发送 | §6-C 要求"不传 `-Page` 时行为逐字一致",并有全量测试 + 实机 E2 兜底 |
| R5 | 老板已裁决"账号只有一个" ⇒ 不再做账号级校验 | §5 的**页级**校验仍做,它覆盖同一个风险面且成本更低 |
