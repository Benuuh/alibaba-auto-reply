## 1. 用户确认的业务规则与问题

用户明确确认：客户给出作为亚马逊收货仓的代码（本次为 FTW1）即可确定报价目的地，不需要为报价再索要一次街道地址。

截图中的回复已经复述了“DDP to Amazon FTW1”，却继续问 delivery address。截图展示的是我方回复，本身不能替代原始买家证据；实现必须从规范化的买家原文确认目的地，不能从机器人自己的复述推导“客户已提供”。测试使用虚拟买家和另编货物数字，不复制真实客户资料。

当前链路存在多套地址判断：`msg_norm::Get-ConversationFacts` 生成 `HasAddress`，`reply_policy::Get-AskableFields` 据此决定是否问地址，`reply_gen::Get-FactEvidenceTable` 独立用正则标记地址证据，而 `goods::Get-GoodsDataStatus/Get-GoodsDetails` 又独立决定资料齐全及展示地址，`quote::Get-QuoteReadyBuyers` 依赖其 `addr`。只改提示词或只加一个 FTW1 正则，其他环节仍可能追问或不触发报价提醒。

## 2. 目标与边界

“完整邮寄地址已提供”与“报价目的地已足够明确”是不同事实。明确的 Amazon/FBA 收货仓代码属于后一类。

修正后，买家提供足够明确的亚马逊目的仓代码且现有其他必要货物信息齐全时：不再问街道地址、城市、州、邮编或重复问目的仓代码；资料判断可进入人工报价准备，内部提醒展示仓库代码。

本任务不实现自动计算价格或自动发报价、不放宽报价禁令，不补造仓库的街道地址、国家、邮编、营业状态或送仓规则。FTW1 的业务可用性依据本次用户确认；其他代码的“客户已指明目的地”不等于系统已查询验证其真实存在或当前可送达。

无需联网仓库目录才能停止重复问地址。后续实际下单、预约或出运所需的运输文件地址由相应业务阶段处理，不能把它变成本轮报价的前置追问。对无法识别或歧义代码可询问准确的亚马逊仓库代码，不能默认要求完整街道地址。

## 3. 一个共享的目的地解析结果

建立或复用纯函数，从规范化、顺序可信的会话消息获得目的地结果。回复事实、证据表、快照资料判断及报价提醒都消费这一处结果，不复制多套仓库正则。现有普通地址提取可以保留兼容，但仓库代码的识别、选择和冲突处理必须只有一份实现。

建议结果字段（名称可按现有风格调整，语义必须保持）：

| 字段 | 语义 |
|---|---|
| `Kind` | `amazon_warehouse` / `postal_address` / `unknown` / `ambiguous` |
| `WarehouseCode` | 单一已选中的规范化代码，如 `FTW1`；歧义时不得随意选一个 |
| `DisplayName` | 如 `Amazon FTW1`，只含有证据的信息 |
| `QuoteUsable` | 当前目的地是否足够进行人工报价准备 |
| `HasPostalAddress` | 是否确有完整地址证据；代码本身不能使它为 true |
| `Evidence` / `Source` | 哪条买家原文或明确人工确认支持该结果；机器人复述只可作为未确认信息 |
| `Candidates` / `Reason` | 多候选、否定、撤销、来源不足等原因，供决策与日志说明 |

原 `Facts.HasAddress` 不应因代码存在而谎称完整地址存在。可增加 `Facts.HasQuoteDestination` 和 `Facts.Destination`，让可追问字段中的兼容键 `address` 消费“报价目的地是否足够”。`Get-FactEvidenceTable` 的输出也需区分“仓库代码已提供”与“街道地址未知”，避免上下文一边写 FTW1、一边写报价目的地 unknown。

快照消费者通过同一规范化入口解析角色、原文和传输标记，不用机器人的 `[ME]` 回答或文件名、产品 URL、`@@OT` 编码串凑出目的地。历史快照缺可靠消息时间时不得自创排序来解决多个仓库冲突；仅有单一无冲突仓库声明时可保守识别，冲突则待确认。

## 4. 识别与更新规则

### 4.1 正面证据

- 支持 `Amazon FTW1`、`DDP to Amazon FTW1`、`deliver to FBA warehouse FTW1`、`亚马逊 FTW1 仓`、大小写和合理标点差异。代码统一大写。
- 可使用明确 Amazon/FBA 送仓对话上下文承接买家的单独代码回答，例如前文确认是送亚马逊，买家后文回答 `FTW1`。这只是解释回答的语境，具体代码仍须由买家提供或由人工明确确认。
- 不能以代码形状作为全球仓库数据库。可定义可维护的候选词法规则并说明适用范围；不得用只支持 FTW1 的硬编码，也不得把任意“字母+数字”当仓库。
- 英文及中文业务表达至少覆盖。若原文有可靠代码而翻译遗漏，优先使用已解码买家原文；翻译与原文是同一消息，不能把它们计成两个冲突目的地。

### 4.2 不构成目的地的情况

- 单独出现疑似型号、SKU、订单号、产品链接或文件名，没有亚马逊收货目的地语境。
- `Our model is FTW1`、`not FTW1`、`we used FTW1 before`、`pickup from Amazon FTW1` 等型号、否定、历史仓库或提货地点。提货仓不能自动充当收货仓。
- 系统卡片、机器人复述、机器人自行猜测；仅有模型推测而无可核对的买家/人工证据。
- 仅说 `Amazon warehouse` 或 `FBA`，没有准确仓库标识。

### 4.3 变更与冲突

- 明确的更改语句（例如“不是 FTW1，改送 TEST2”）按可信消息顺序更新当前目的地，保留证据，不能继续使用旧仓。`TEST2` 在测试里仅为虚拟候选标识，不声称是实际仓库。
- `FTW1 or TEST2`、同时列多个仓但未分配货物、旧新代码冲突且未表达替换：标记 ambiguous，问一个明确的问题“Which Amazon warehouse should I quote for?”。
- 已选择单仓后，后续无关消息不撤销它；明确取消亚马逊送仓或改送私人地址时，按新目的地重新判断。不能因历史中曾出现 FTW1 就永久停止询问。
- 仓库代码与普通地址同时提供、关系清楚时保持两项信息，不重复追问；若明显对应不同送达目标且无法消解，不擅自选一个。

## 5. 生产消费链

1. `msg_norm` / 共享目的地函数：生成上述目的地事实与证据；保留现有消息身份和顺序保护。
2. `reply_policy`：目的地 `QuoteUsable=true` 时，`AskFields` 不得包含兼容键 `address`；歧义时问仓库选择，未知且明确为亚马逊送仓时优先问仓库代码。其他缺失字段仍按既有次数和优先级处理。
3. `reply_gen`：事实区明确列出 `quote destination: Amazon FTW1 (buyer provided)`；街道地址可注明未提供但不是本轮报价所需。固定话术和匹配场景示例消费同一事实，附件解析失败、尺寸帮助等回退也不能重新索要已满足的目的地。
4. 生成输出检查：增加有针对性的上下文检查（可为 `Test-ReplyCompliance` 增加可选 Decision/Facts 参数），阻止在已确认可报价仓库目的地下重新要求收货街道地址/邮编或重复仓库代码。覆盖正常生成、一次重写、最终回退和实际发送前检查。不能只依赖模型自觉遵守提示词。说明确定性检查的覆盖边界，不宣称能理解所有自然语言。
5. `goods`：资料齐全度将“完整地址或有效报价目的地”作为目的地项。返回明确的目的地类型和代码；若保留 `addr` 兼容布尔/字符串，文档标明它代表报价目的地，不代表街道地址，展示值可为 `Amazon FTW1`。
6. `quote`：有重量、尺寸及可用目的地时进入原有人工报价候选逻辑；提醒显示“报价目的地：Amazon FTW1”。内容去重包含当前目的地，改仓能触发更新提醒，同一内容仍受原有去重约束。通知失败不能写成提醒成功。
7. `summarize` 及其他已发现消费者：统一标签和齐全度语义，不能出现回复不问地址、报告却写“缺地址”的矛盾。不要顺带重写重量、尺寸、货名等其他业务规则。

不能把报价候选状态误写成“已报价”或“已通知团队”。单纯代码准备完成也不能解除人工接管名单。现有通知调用时机保持原约束；无法完成真正通知的路径要在报告中说明。

## 6. 回复示例（虚拟货物资料）

买家原文：“20 cartons, 50 x 40 x 30 cm each, 200 kg gross, DDP to Amazon FTW1.”

若目的地与其他必要资料已明确，可回复：

> FTW1 works for the destination. I can use the details you've sent to prepare the quote.

此句不提供具体价格、期限或通知成功承诺。若还缺重量，则仅追问重量，不能顺带问完整地址。

仓库不确定：“Amazon FTW1 or TEST2, not sure yet.”

> Which Amazon warehouse should I quote for?

## 7. 离线验收

先加入至少能复现“事实或 AskFields 仍缺地址”和“报价候选漏收仓库代码”的失败回归，再实现。使用虚拟快照、模拟通知和模型，隔离数据目录与提醒状态。

| 编号 | 情景 | 期望 |
|---|---|---|
| B1 | 完整虚拟货物资料 + 买家 `DDP to Amazon FTW1`，无街道地址 | 目的地可报价，AskFields 无 address，模型上下文证据一致，进入人工报价候选 |
| B2 | B1，但模型输出“please send the delivery address” | 输出检查阻断；至多一次重写或合规回退，最终不追问地址 |
| B3 | B1，模型不可用 | 固定话术不问街道地址/邮编，不编造价格或期限 |
| B4 | 大小写、标点、中英表达；翻译遗漏代码但原文有代码 | 规范化到 FTW1，识别结果一致 |
| B5 | 明确 Amazon/FBA 对话后买家单独回复 FTW1 | 承接语境，代码证据来自买家 |
| B6 | 只有机器人说 FTW1，或产品型号/URL/附件名含 FTW1 | 不构成已提供报价目的地 |
| B7 | 亚马逊送仓但没仓库代码；未知候选格式 | 询问准确目的仓代码，不默认索要街道地址 |
| B8 | 否定 FTW1、历史仓、提货仓、取消送仓 | 不继续使用旧目的地；依当前目标决策 |
| B9 | 明确由 FTW1 改成虚拟仓 TEST2 | 当前目的地、模型上下文、goods 展示与提醒 hash 同步变更 |
| B10 | 同时有两个未选定目的仓，或仓库与地址冲突 | ambiguous，不自动选仓，不标记资料齐全，单次询问选择 |
| B11 | FTW1 已确定，但缺重量或尺寸 | 只问确实缺失且可问的字段；不能因有仓库就声称全部资料齐全 |
| B12 | 普通私人收货地址或非亚马逊送货，确实未提供目的地 | 保留原有合理地址追问和地址归属澄清 |
| B13 | 报价提醒 | 展示 FTW1 而非“地址未知”；相同内容不重复提醒，改仓可更新；失败不推进成功状态 |
| B14 | 系统卡片、消息顺序不可信、人工接管、人工插话 | 保留原阻断；不从机器人补全资料，不自动发价格 |
| B15 | 三条消息分批提供货物信息、仓库代码、再催报价 | 当前完整事实可用，无重复地址追问；催价仍受现有报价权限约束 |
| B16 | 报告及资料齐全度消费者 | 与回复链一致；没有完整地址仍可展示可报价仓库目的地，但不伪造地址已提供 |
| B17 | 附件解析失败/尺寸帮助等回退，当前已明确 FTW1 | 回退也不重复索要地址；其他必要缺失信息保持原规则 |

至少一条回归必须走真实生成检查链（模型桩故意索要地址），至少一条走真实 goods → quote 候选与模拟提醒链，不能只断言新解析器识别 FTW1。后续实现不得破坏前置时间门禁 spec 的入口验收。
