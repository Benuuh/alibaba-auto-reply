### 1.1 最高优先级红线：联系方式

用户明确指出这是此前红线说明遗漏的最重要一条：不能主动提供自己的联系方式，或主动询问对方的联系方式；应询问收货人的业务联系资料。

1. 不主动提供、推荐或邀请客户使用我方电话、邮箱、微信、WhatsApp 等联系方式。即使模型上下文中有我方联系资料，也不得顺带发送或用它引导客户更换聊天渠道。
2. 不主动笼统询问客户本人的电话、邮箱、微信或 WhatsApp；禁止以“your contact / your phone / your WhatsApp”代替收货资料的明确询问。
3. 允许按运输业务索取收货人的名称、收货联系方式及地址；明确使用 consignee / recipient 等角色措辞。
4. 允许按已确认的供应商核实流程索取供应商联系方式；明确使用 supplier 等角色措辞。
5. 即使买家本人也是收货人，询问也必须明确是收货用途，不扩展为询问其私人聊天账号或转移对话。
6. 不因为一句回复提及供应商或收货人，就豁免整句话中的其他联系请求；混合包含我方联系邀约或对买家个人联系方式索取时仍阻断。

此规则覆盖模型初稿、重写、固定回退和实际发送前检查，不依赖提示词自觉遵守。客户主动询问我方联系方式时如何处理尚未在本轮明确，不能从“不得主动提供”推导为已授权自动披露或一律禁止回应。

## 2. 自动接待与人工介入

### 2.1 暂停和恢复的建议语义

1. 可信地识别人工新回复后，记录人工回复时间和暂停截止时间，建议截止时间为该人工回复时间加 5 分钟。
2. 暂停期间可以读取消息、整理资料和记录待处理输入；不自动向买家发送。
3. 每一条新的人工回复重新计算暂停截止时间；扫描到同一条历史人工消息不能反复延长暂停。
4. 截止时间到达只解除临时暂停，不直接触发一条问候、催促或旧回复。
5. 恢复时重新读取会话。只有存在尚未处理的买家诉求，且待回复、身份、去重和时间门禁通过，才生成并发送。
6. 暂停期间的多条买家消息作为一个当前请求处理，避免逐条补发。人工已经答复的部分不再补答。
7. 暂停状态持久化；程序重启不能提前解除暂停，也不能重新从零计时。
8. 显式人工接管名单继续优先于临时暂停。到期不得擅自移除名单条目。

例：12:00 人工回复，暂停至 12:05；12:03 又有新的人工回复，则暂停至 12:08。12:04 再扫描同一条 12:03 的人工消息，截止时间仍为 12:08。到期仍需通过正常待回复及去重判据。

### 2.2 人工来源必须有证据

当前 msg_source 和 msg_norm 存在通过 @@TS 推断我方消息是机器人消息的逻辑；页面抽取又为具有逐条时间的我方消息加 @@TS。时间字段不能独立证明发送者身份。

建议按证据识别：明确的页面/API 发送者信息，以及本系统已确认发送记录。无足够证据时保留 unknown，不能默认归为机器人。未知来源的阻断及恢复策略需要独立设计，不把每次扫描 unknown 都当作一条新的人工回复。

### 2.3 独立的状态维度

- 接待权限：自动接待、人工临时暂停、显式人工接管。
- 业务进度：收集资料、待人工报价、待人工核实、已完成。
- 发送结果：准备发送、已确认发送、已确认失败、结果未知。

三个维度分别记录。待人工报价不自动等同于永久人工接管；人工临时暂停也不清空货物资料。

## 3. 货物事实与报价准备

### 3.1 单一事实模型

回复策略、报价提醒、摘要和报告消费同一份事实结果，停止各自用关键词独立判断资料是否齐全。现有共享目的地解析保留，并作为其他字段统一的参考。

字段至少包含：值、单位、适用范围、状态、来源消息和更新时间。

| 状态 | 含义 | 建议行为 |
|---|---|---|
| unknown | 没有可核对的值 | 必要字段才补问 |
| promised | 买家说稍后提供 | 保留缺口，避免下一轮立即重复追问 |
| provided | 明确给出了值与含义 | 可进入相应业务判据 |
| needs_confirmation | 有候选值，但单位、范围或含义不明 | 针对歧义问一个问题 |
| conflict | 多个有效值无法解释为替换 | 请求确认，不任意取第一个或最后一个 |

例：“I do not have dimensions yet”不能被判为尺寸已提供。20 kg 必须区分总重量、每箱重量和商品本身重量；尺寸必须区分运输外包装、商品本身和整批。用户已确认收集清单中的单件以运输外包装（箱或托盘）为单位，不能用商品规格替代包装规格。数量乘单箱重量等推导值需标记为计算结果，保留公式和源证据，不伪装成买家原话。

明确更正可以替换旧值，同时保留历史证据。没有更正含义的不同数值不得静默覆盖。机器人复述不能增加事实可信度。

### 3.2 标准收集清单与最低报价条件

用户确认：“要的时候先要这些，实际上只要件数、重量、尺寸和收货地址也能报。”因此标准收集范围与报价必填范围分别维护。

| 资料 | 标准收集 | 基本报价必需 | 说明 |
|---|---|---|---|
| 货物名称 | 是 | 否 | 用于识别货型，缺少时提示人工资料未完整；不单独阻挡基本报价准备 |
| 参考图片 | 是 | 否 | 可辅助识别货物，不因缺图重复阻挡报价准备 |
| 件数 | 是 | 是 | 运输外包装的箱数或托盘数，与重量和尺寸对应；商品数量不能直接代替 |
| 单件重量 | 是 | 重量信息必需 | 每箱或每托盘重量；区分包装单件与总重，已明确提供的总重不再机械重复索要单件重量 |
| 单件尺寸 | 是 | 尺寸信息必需 | 每箱或每托盘的长宽高与单位；商品本身尺寸不能直接代替 |
| 供应商地址 | 是 | 否 | 作为供应商/提货资料，不能误当成收货地址 |
| 供应商联系方式 | 是 | 否 | 与收货人联系方式分别记录 |
| 收货人名称 | 是 | 否 | 未提供时资料尚不完整，但不阻挡基本报价准备 |
| 收货人联系方式 | 是 | 否 | 收货业务资料，按最新用户要求纳入标准收集 |
| 收货地址/可用报价目的地 | 是 | 是 | 保留明确亚马逊目的仓代码可满足报价目的地的既有规则 |

建议收集行为：

1. 需要索取资料时先按上述标准清单说明所需资料；买家已经提供的项目不重复索取。
2. 买家回复部分资料后，优先补问最低报价条件中实际缺少或有歧义的项目。
3. 四项基本资料满足后即可进入人工报价准备，图片、供应商资料、收货人姓名及联系方式的缺失作为未完整项展示，不继续挡住报价。
4. 完整度与可报价性分别返回，避免“不是全套资料”被误写成“不能报”。
5. 已知特殊货型的额外要求独立配置和说明；未识别货型不能自动制造新的通用必填字段。缺少货名或图片不单独把基本报价准备改判为失败。
6. 客户明确无法提供件数、重量或尺寸时，优先转向供应商核实路径，索取尚未提供的供应商联系方式；不继续要求客户自行取得同一项资料。若已有联系方式则直接建立或更新核实待办，不重复索取。
7. 客户没有供应商，或也无法提供供应商联系方式时，保留资料缺口给人工处理，不编造数据，也不反复索取不存在的联系人。

### 3.3 按业务条件配置规则

货物属性、包装形态、运输方案和计费依据分别建模，避免只用一个“货型”字段承载所有含义。基本判据包含用户确认的件数、重量、尺寸和目的地；特定类别的额外要求及替代资料组合另行细化。

每个规则配置：适用条件、必要字段、替代资料组合、合理性检查、必须人工判断的情况。明确区分提醒人工进一步核对与阻挡进入报价准备，不因辅助资料缺失混用二者。

输出建议为：

- Ready：是否足够进入人工报价准备；不代表已经报价或通知成功。
- MissingFields：本次实际缺少的关键资料。
- OptionalMissingFields：标准清单中尚未提供、但不阻挡基本报价的资料。
- CollectionComplete：标准清单是否收集完整，与 Ready 分开。
- Clarifications：需确认的单位、适用范围或冲突。
- Reasons：判据依据，供回复和内部提醒共同使用。
- RuleVersion：使用的资料要求版本。

混合多种规格时分别保存各组数量、重量和尺寸，不用一个“单件”值代表所有货物。数据归属不明或相互矛盾时先澄清；运输方案及特殊货型的业务问题可标记给人工处理。

同规格汇总示例：10 箱、每箱 20 kg、每箱 50 × 40 × 30 cm，可计算总重量 200 kg、总体积 0.6 m³。箱数和单箱数据必须属于同一包装组；商品净重或商品尺寸不得被直接当作包装重量和包装尺寸使用。不同规格分别计算后汇总；已给总重时不再乘一次箱数。

### 3.4 联系方式按业务角色与用途处理

按 §1.1 区分禁止的主动联系交换与允许的运输业务资料收集。当前生产规则允许供应商联系方式，但对买家本人的联系方式存在禁令；同时通用联系方式模式可能误拦收货资料。实施时同步修改代码判据、提示词、规则消费和验收，既保留不主动提供我方联系方式的红线，也准确允许收货人与供应商资料收集，不能只改收集列表。

收货人即买家本人时，也按收货资料用途处理，询问明确指向收货人，不能因为角色相同就拒绝已授权的收集。供应商、收货人和买家会话身份分别保存；联系方式用于对应运输业务，不因此生成转移会话到其他渠道的要求。

允许示例：

- Could you share the consignee’s name, contact number and delivery address?
- Could you share your supplier’s contact details so we can confirm the packing information?

主动发送时禁止的示例：

- What’s your WhatsApp number?
- Send me your phone number or email.
- Here’s my WhatsApp number. You can contact me there.
- Add me on WeChat and we can discuss the shipment.

内部字段建议区分 RecipientContact、SupplierContact 与 BuyerConversationIdentity；AskFields 明确指向业务角色，不能用一个泛化 contact 字段混合判断所有联系方式。

## 4. 人工任务与对外表述

### 4.1 供应商核实流程（用户已确认）

客户无法给出包装件数、重量或尺寸时，索取供应商联系方式，并说明我们会直接向供应商询问，方便客户。执行联系的是后续上线的人工，机器人负责资料收集、记录待办和交接。

建议闭环：

1. 确认客户无法提供哪些资料，仅记录实际缺口，不把已知数据清空。
2. 创建或更新供应商核实任务；尚无联系方式时标记 awaiting_contact。
3. 向客户索取供应商联系方式。已经提供时跳过此问，继续使用已验证的联系资料。
4. 收到联系方式后补齐任务，状态变为 pending_human，供人工上线后查看和认领。通知失败时任务继续保留。
5. 人工联系供应商，核实任务中列明的缺失信息，如箱数/托盘数、每箱/托盘包装重量和长宽高。机器人不代替人工向供应商发送消息。
6. 人工记录联系结果；无响应时保持待跟进，不伪装为资料已确认。取得资料后记录为人工从供应商核实的事实，带来源与确认时间。
7. 所有消费者使用更新后的同一份事实，重新判断基本报价条件；满足后进入人工报价准备。

同一会话、同一批货物和同一供应商的未完成任务持续更新，客户重复催问不创建重复任务。人工上线时应能看到待办列表；上线识别与认领入口属于实施细节，尚未接通的通知或检测机制不能当作已经存在。

建议对外话术：

> No problem — could you share your supplier’s contact details? Once you send them, we’ll check the packed weight and dimensions directly with your supplier, so you don’t have to gather everything yourself.

按实际缺口选择 carton count / packed weight / dimensions，已知项目不再次要求核实。此话术表达后续计划，不宣称已经联系，不许诺未经确认的具体时间。客户面前使用 we / our team 表达服务方；内部任务明确由人工负责执行。

### 4.2 表述证据与旧规则调整

人工任务与接待权限独立。需要查询物流状态、核实供应商资料、处理投诉或报价时，先落盘任务，再尝试通知。

任务记录：会话身份、触发消息、任务类型、资料快照、处理状态和通知结果。首次可做到任务持久化、通知重试和人工标记完成；同一任务的重复催问更新既有任务。

对外表述必须对应实际证据：任务创建不等于人工收到；通知投递不等于人工完成；报价候选不等于已报价。现有 ActionEvidence 门禁继续使用，后续由真实任务结果提供证据。

最新用户授权允许在供应商核实流程中表达未来联系计划。实施时将旧“禁止说将联系供应商”的规则调整为按状态判断：

- 联系方式未提供、核实任务已记录：允许条件式“收到联系方式后，我们会直接核实”。
- 联系方式已提供、核实任务已记录：允许“我们会直接与供应商核实这些资料”。
- 已联系/已取得回复：必须有人工记录的实际执行证据才能这样表述。
- 具体完成期限：仍需真实负责人和已确认期限，不从“人工会上线”推导时间。
- 任务未成功记录：不能发送无支撑的联系承诺；保留故障待处理并采取中性表述。

同步修改 reply_rules、reply_policy、生成器及固定话术的生产消费链，避免客户要求供应商协助时被旧规则阻断，或回退为“I can’t check with your supplier from here”。当前讨论稿未实施这些代码修改。

## 5. 发送与状态可靠性

1. 页面锁采用原子获取，释放前验证归属；测试两个竞争进程最多只有一个获得锁。
2. 状态文件临时写入、校验后原子替换，保留有效备份。区分不存在、有效空数据和损坏。
3. 输入框清空只证明页面动作的一个阶段。发送结果应进一步核对会话内的新我方消息或可获得的发送回执。
4. 结果未知时先对账，再判断是否重试；不得直接当成失败盲目补发。
5. 在生成后、发送前再次检查会话身份、当前输入与人工介入。输入发生变化时重新决策。
6. 新状态存储和发送记录格式先做兼容设计与迁移方案；不在当前讨论中改写或清空既有 HASH|count 生产账本。

## 6. 模块边界建议

| 层 | 职责 | 边界 |
|---|---|---|
| 页面/网关适配 | 会话定位、消息提取、发送回执 | 不决定货物资料齐全度 |
| 消息规范化 | 顺序、原文、消息身份、来源证据 | 不创建人工任务或发送 |
| 事实与报价规则 | 资料值、冲突、目的地、缺失字段 | 不直接读写页面 |
| 业务决策 | 接待权限、当前诉求、允许追问、所需动作 | 返回结构化决策 |
| 回复生成 | 依据事实与决策措辞、一次可选重写、回退 | 不修改业务状态 |
| 任务与发送服务 | 执行动作、记录结果、提供执行证据 | 不自行放宽策略 |
| 状态存储 | 去重、暂停、发送记录、任务、重试 | 统一路径和持久化方式 |
| monitor | 扫描、安排会话处理、恢复和预算控制 | 逐步抽离领域判断 |

保留 PowerShell 与现有浏览器入口，按行为逐项迁移。生成器和发送器返回结构化结果，逐步替代 script:lastReplyDecision 等跨调用隐式状态。

### 6.1 规则消费与统一输出检查

规则职责明确分为三类：代码负责可执行业务判据和发送约束；提示词负责语言与语气；场景文件负责经审阅的表达示例。业务规则发生变化时同步修改实际消费方，不能仅向 JSON 文本数组追加一句话就宣称行为已生效。

建立规则清单，每条生效规则记录 RuleId、适用阶段、消费函数、需要的证据、规则版本和验收样例。配置中尚无消费方的字段标记为未接入或历史字段，不能在操作说明及建议应用结果中描述为已生效。新增拟生效规则应有消费和行为验证后再启用。

统一检查函数消费本轮 Text、Decision、Facts 和 ActionEvidence。具体检查：

0. 首先执行 §1.1 的最高优先级联系方式红线：阻断主动提供我方联系方式及索取客户个人联系方式；收货人和供应商资料仅在角色、用途及本轮追问范围明确时允许，不给整个场景联系方式白名单。
1. 所问字段符合当前收集阶段和 AskFields；已提供的项目不重复索取，最低报价条件满足后不强迫补齐所有辅助项。
2. 报价目的地明确时不重复索要地址；包装件数、重量与尺寸的适用范围不混用。
3. 未来供应商联系计划按 §4.2 的任务状态允许；已联系、已通知和已确认分别需要对应的执行证据。
4. 具体完成期限需要真实已确认的期限，不能从模型措辞或一般通道可用性推导。
5. 保留报价、责任承诺、可信接待身份、真实时间、未替换模板标记等既有约束；收货人联系方式按本轮授权的业务用途调整。

模型初稿、最多一次重写、固定话术和实际发送前均调用同一组检查。最终检查失败时优先选择合规回退；回退也失败时阻断发送并记录原因，不能通过无校验的兜底文字绕过约束。

模式匹配用于可确定识别的违规表达，不宣称覆盖所有自然语言。对难以确定的语义记录不确定性，使用受约束话术或交给人工；允许和阻断样例均纳入回放。

### 6.2 页面锁范围与输入新鲜度

页面操作保持串行，将可能耗时的资料整理、附件处理和模型生成移到页面锁之外：

1. 锁内读取：确认浏览器与会话身份、抓取消息、保存已验证快照及其消息版本，释放页面锁。
2. 锁外处理：根据快照构建事实、做业务决策、持久化必要待办、生成和检查回复。任务与状态存储使用自身的并发保护，不借长期持有页面锁代替存储锁。
3. 锁内复核与发送：重新定位目标会话，检查当前人工接待权限、待回复状态、去重和时间判据，并核对买家输入及我方新消息。
4. 快照与当前输入不一致、有人工作答或进入人工暂停时，丢弃旧草稿；基于新输入重新决策，不能只替换买家名后发送旧内容。
5. 发送确认后保存结果与成功发送时间，释放页面锁。所有出口通过 finally 释放持有的锁，按真实发送结果处理对账和重试。

复核基于已验证的消息身份和内容，不依赖列表预览或会话渲染时间。客户新消息、撤回/改动、顺序不可信和人工消息均需要明确处理；不能为了通过复核而降低身份保护。

初期保持会话处理串行，仅缩小锁范围。需要增加生成并行度时，先消除隐式共享状态，并设置任务数和请求预算；不同时切换或写入同一浏览器页面。

记录页面锁持有时间、单会话处理时间、模型耗时、过期草稿次数和重试原因。使用实际测量验证改善，不用模拟时钟或旧轮次数据声称生产响应速度。

### 6.3 配置、测试隔离与版本记录

配置加载支持显式传入 ConfigPath 与 RuntimeRoot，代码位置和运行数据根分别解析。测试传入临时配置和临时运行目录；日志、状态、暂停记录、人工任务、提醒去重、锁与 PID 文件统一经路径接口定位。配置解析和模块导入不启动生产循环、不通知或恢复进程。

逐步将测试分为：

| 层 | 范围 | 默认运行行为 |
|---|---|---|
| 纯逻辑 | 消息规范化、事实、决策、时间判据、输出检查 | 不访问浏览器、模型或通知通道 |
| 隔离集成 | 真正的会话入口、临时存储、竞争进程、模拟适配器 | 只使用测试配置与临时目录 |
| 真实验收 | 真实模型、指定浏览器会话、通知投递与发送确认 | 独立明确运行，不混入默认离线套件 |

默认测试入口只运行纯逻辑和隔离集成。测试不得通过备份后改写生产 config.json、账本或接管名单来获得隔离；隔离模式意外解析到生产根或调用真实发送适配器时立即失败。

将入口组装/依赖加载做成无运行副作用的 bootstrap，并验证函数导出和依赖顺序；隔离集成实际调用会话处理服务，防止子模块测试通过而主入口接线错误。原 AST 抽取测试可保留过渡，不能作为整个入口已验收的唯一证据。

运行与验收记录区分：工作区代码版本、进程实际加载的代码版本、规则版本、消息 schema 版本、配置标识以及验证时间。配置标识不包含凭据；源码更新但进程未重新加载时明确记录这种差异。

文档分别说明已设计、工作区已实现、离线通过、真实验收通过和生产已加载。历史快照保留日期；新的结论明确替代的范围，避免同一现状同时被写成待修复和已修复。

## 7. 验收样例

| 情景 | 期望 |
|---|---|
| 人工回复后，买家立即补充信息 | 记录资料，暂停期内不发送 |
| 12:00 人工回复 | 暂停截止 12:05 |
| 12:03 人工再次回复 | 仅这条新人工消息将截止延长到 12:08 |
| 重复扫描同一条人工消息 | 暂停截止时间不变 |
| 暂停到期，没有待处理买家诉求 | 不主动发消息 |
| 暂停到期，买家有多条未处理消息 | 重新读取后合并处理 |
| 暂停期间人工已经回答最新问题 | 不补发过期答案 |
| 程序在暂停期间重启 | 保留原截止时间 |
| 显式接管名单中的买家到达临时截止时间 | 继续尊重显式接管 |
| 买家表示没有尺寸或稍后发尺寸 | 不标记尺寸已提供，不连续重复追问 |
| 单箱重量与总重量、单箱尺寸与总体积 | 保存不同范围，按已确认报价规则判定 |
| 件数、重量、尺寸和收货地址齐全，其余标准清单资料缺失 | Ready=true，CollectionComplete=false；缺失辅助项展示给人工，不阻挡报价准备 |
| 标准清单齐全但没有件数 | 不按旧重量+尺寸+目的地三项判据误判为可报价，优先补问件数 |
| 买家只提供供应商地址 | 不当作收货地址，仍需确认报价目的地 |
| 收货人姓名或联系方式未提供 | 记录缺失，但不阻挡基本报价准备 |
| 收货人即买家，索取收货联系方式 | 按已授权收货资料用途处理，不被旧买家联系方式禁令误拦 |
| 主动提供我方电话、邮箱、微信或 WhatsApp，或邀请客户联系/添加我方账号 | 阻断发送，即使来自固定回退也不豁免 |
| 主动询问“your phone / your WhatsApp / your email”且没有明确收货业务角色 | 阻断，改为针对收货人的业务资料询问 |
| 本轮需要收货资料，明确询问 consignee/recipient 的名称、联系号码和地址 | 允许，不误封为主动索取客户私人联系方式 |
| 本轮需要供应商核实，明确询问 supplier contact | 允许，不扩大为索取买家个人联系方式 |
| 同一句索取供应商联系方式并询问买家 WhatsApp | 仍阻断，供应商角色不豁免其他禁止请求 |
| 客户已给收货人联系方式，模型补充我方邮箱或微信 | 阻断我方联系方式披露，不因收货资料场景放行 |
| 件数、重量和尺寸属于不同规格且无法对应 | 请求确认归属，不错误相乘或汇总 |
| 10 箱、每箱 20 kg、每箱 50 × 40 × 30 cm | 推导总重量 200 kg、总体积 0.6 m³，记录计算来源 |
| 买家给出 100 个商品，未说明装几箱 | 商品数量保留为商品数量，包装件数仍缺失 |
| 10 箱、总重量 200 kg | 不把总重量再乘以 10 |
| 目的地为明确亚马逊收货仓代码 | 不重复索要街道地址 |
| 买家更正重量或目的仓 | 回复、准备状态与提醒使用一致的新事实 |
| 生成期间有人工作答或买家改变诉求 | 旧草稿不发送 |
| 点击发送后回执不明确 | 结果未知，先核实再重试 |
| 通知失败 | 任务保留并重试，不声称人工已经收到 |
| 客户无法提供包装资料，供应商联系方式未知 | 索取供应商联系方式，记录待核实缺口和 awaiting_contact 任务，允许条件式未来核实表述 |
| 客户无法提供包装资料，供应商联系方式已知 | 不再索取联系方式，更新 pending_human 待办 |
| 人工尚未上线或通知失败 | 保留任务；不说已联系供应商，不许诺完成时间 |
| 人工上线并联系供应商 | 人工记录实际联系结果，任务进入已联系/待供应商回复状态 |
| 供应商资料经人工录入确认 | 保存来源证据并更新同一份事实，重新判断报价准备 |
| 同一供应商核实事项被客户反复催问 | 更新同一个未完成任务，不重复建单或重复索取联系方式 |
| 客户没有供应商或联系方式 | 保留缺口给人工，停止重复索取不存在的联系人 |
| 两个进程同时竞争同一页面锁 | 最多一个获取成功，失败者不能释放成功者的锁 |
| 原子状态替换前进程中断 | 原有效账本可读取；不把损坏状态当作新建空账本 |
| 新增规则写入 JSON 但没有生产消费方 | 标记未接入，不声称生效；规则接通后通过行为回放验证 |
| 模型重问已知字段、超出本轮 AskFields 或无依据承诺期限 | 统一检查阻断，重写或回退仍遵守相同判据 |
| 固定话术未通过最终检查 | 不借无校验的中性兜底发送 |
| 生成过程中外部页面写者请求锁 | 模型生成不持有页面锁；发送重新取得锁并复核 |
| 隔离测试尝试访问生产配置根或真实发送通道 | 测试失败，生产文件和外部会话无写入 |
| 单独模块正常但入口引用错误 | bootstrap 与会话服务隔离集成发现错误 |
| 工作区更新而运行进程尚未加载 | 运行状态明确区分工作区版本和实际加载版本 |

## 8. 分阶段实施建议

1. 以已确认的 5 分钟暂停、报价基本四项和运输外包装计量范围为基线；完善人工来源证据、联系方式用途和事实模型的验收样例。
2. 修复原子锁、发送结果和状态持久化；建立可隔离的测试入口。
3. 实施人工临时暂停与恢复、统一资料和报价准备判据。
4. 接通人工任务闭环，并将执行证据接入既有对外表述检查。
5. 在以上行为有测试保护后抽离 monitor 模块，缩短页面锁占用。

验收分别记录纯逻辑、隔离入口、真实模型、页面发送和通知到达证据。离线通过不等于生产上线；文档记录工作区版本和实际加载版本。
