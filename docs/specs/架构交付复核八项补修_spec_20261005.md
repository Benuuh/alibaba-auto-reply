## 2. F1：联系方式识别不再依赖冠词，角色必须属于联系请求（P1）

定位：`scripts/lib/contact_rules.ps1::ContactGenericAskPatterns`、`Test-ContactAsk`、角色判据及 `reply_policy.ps1` 的重复检查。

### 2.1 实现方案

1. 联系请求先按“索取动作 + 联系渠道/资料对象”识别。`a/an/the/your/any` 是可选修饰语，不能成为进入检查的必要条件；支持 `contact details`、`contact information`、`phone number`、`email address` 等单复数表达。
2. 将识别结果绑定到该请求实际索取的对象：供应商、收货人、客户本人或未明确。不能仅因同句出现 supplier/recipient 就放行；例如“请给你的电话，以便联系供应商”索取的仍是客户电话。
3. 我方联系邀约/渠道披露、客户私人联系请求及没有明确业务角色的请求阻断。物流用途不能代替角色。
4. 供应商和收货人的合法请求仍需符合业务用途、AskFields 和已提供事实。客户就是收货人时，使用明确收货角色及用途措辞。
5. 保持联系方式检查为统一输出检查的第一项，覆盖模型初稿、一次重写、固定回退与最终发送。难以确认对象时选择经检查的明确角色话术或阻断，不通过泛化放行绕过。
6. 非请求的资料叙述与正常平台内沟通不应因包含 contact/details 被误拦；不新增客户主动询问我方联系方式时的自动披露授权。

### 2.2 必须验收

| 用例 | 期望 |
|---|---|
| `Please share contact details for delivery updates.` | 完整检查阻断，发送桩为 0 |
| `Please provide contact information so we can reach you.` | 完整检查阻断，发送桩为 0 |
| 原 `Please leave a phone number...`、`You can email me...` | 继续阻断 |
| 未提供、已授权的 supplier/consignee 联系请求 | 明确角色与用途后通过 |
| 私人电话请求用于“联系供应商” | 阻断，供应商提及不成为豁免 |
| 已提供的角色联系人再次索取 | 阻断重复询问 |
| 供应商已提供联系人等非索取叙述 | 正常通过 |

模型桩先返回违规初稿、再返回合规重写，验证重写能通过；初稿和重写均违规时，只能发送经相同检查的合规回退或不发送。最终发送入口不得绕过。

## 3. F3：人工暂停按回复绝对时间计算，历史重扫不推进状态（P1）

定位：`scripts/lib/human_pause.ps1::Update-HumanPauseFromLines`、`Start-HumanPause`、持久化结构及注入时钟。

### 3.1 实现方案

1. 统一比较口径为 UTC，内部使用明确的 UTC datetime 或带偏移的 DateTimeOffset。可靠 epoch 毫秒用绝对时间转换；可靠明确偏移时间按偏移解析。显示时才转换当地时间。
2. 可靠人工回复的 `untilUtc = replyAtUtc + 5 minutes`。严禁将最大消息时间映射到每次 Now，也不能按历史消息与最大值的相对差值重造回复时刻。
3. 每条人工事件保留稳定身份、来源、原消息时刻、时间可信度。优先真实平台消息 ID；其次使用稳定的规范化原文、角色与可靠逐条时间组成身份。位置下标、扫描时刻及易变 UI 文本不能作为身份主体。
4. 持久化已见事件及最新可信人工事件；按可靠事件时间排序/比较。旧事件、相同事件、窗口截断后重新出现的事件，不更新截止时间。原文相同但 ID 或可靠时间不同的新人工回复应能识别。
5. 没有可靠时间时可用首次观察时刻建立一次保守窗口，但该观察时刻必须随事件身份持久化并标记来源；同条重扫、重启或位置变化不能重新赋时。
6. 可靠但明显异常的未来时刻不改成“人工刚刚回复”。记录异常并按有界保守策略处理，不能因异常时间把暂停无限延长。正常延迟扫描的过去时刻按真实时间处理。
7. 已过期历史人工消息不能重新开始五分钟暂停。暂停到期只解除临时门禁；仍须存在未答买家请求且正常发送条件通过。
8. 兼容旧 pause v1/v2：不清空已有状态。若旧记录的错误时间可由同一可信消息的原始时间验证，可做有日志的一次纠正；无法验证时保留既有有效记录及原截止，不在重启时改成 Now+5。迁移仅在隔离夹具验收，本轮不手工迁移生产文件。
9. 状态读取、保存或事件同步失败时，本轮不发送；不能只记录异常后当作无暂停。

### 3.2 必须验收

注入 `NowUtc` 与真实对应的消息 epoch，不能保留“2030 消息 + 2026 时钟”夹具后改变生产语义迎合它。

| 时间/事件 | 期望 |
|---|---|
| 12:00 人工回复，12:04 首次扫描 | 截止仍为 12:05 |
| 历史人工 11:59、12:00，12:06 扫描 | 不活动；不能变为 12:11 |
| 同一两条历史消息连续扫多次，改变行号或截断窗口 | 截止保持，旧消息不重新暂停 |
| 12:03 新人工回复 | 截止推进到 12:08 |
| 原文相同但真实 ID/逐条时间不同的两次回复 | 第二条按新事件处理 |
| 同条无可靠时间消息重扫、重启 | 使用同一首次观察时刻，不延长 |
| 已确认机器人发送 | 不触发人工暂停 |
| 不同宿主时区、UTC 注入时钟、时间异常或存储失败 | 不错算时区；异常有记录；存储失败不发送 |

同时保留显式人工接管名单优先、人工已答范围与到期后正常回复门禁。

## 4. F2：所有新我方介入事件先同步，再判断末尾买家（P1）

定位：`monitor.ps1` 读取后的 unknown 分支及发送前复核；`msg_source.ps1`、`human_pause.ps1`。

### 4.1 实现方案

1. 建立共用编排接口，例如 `Sync-ConversationInterventionState(Conversation, SentRecords, NowUtc)`，内部使用 §3 的事件身份、时间与持久化能力。返回 HumanPauseActive、UnknownHoldActive、UntilUtc、SyncOk、Reason，供读取和发送前共用。
2. 顺序固定为：规范化当前快照与来源 → 同步全部新可信人工/unknown 我方事件 → 检查暂停/等待 → 再判断最新买家请求及其他回复门禁。不能把同步放在 `unknown-me-tail` 或 `human-last` 条件内。
3. unknown 仍是来源未证实，不能根据时间戳、缺发送记录或缺 bot 标记强制转成人工/机器人。明确 sender/API 信息与已确认发送记录才作为对应来源证据；页面适配保留可得到的真实证据。
4. 新 unknown 我方事件建立独立 `source_unknown_hold`，持续五分钟。可靠新消息时刻可作为锚点；没有可靠时间时用持久化首次观察时刻。买家补充、重扫、位置改变或重启不得提前取消或延长同一等待。
5. 历史基线用稳定事件身份及时间保存，取消“我方消息最大行号”的新事件判据。消息窗口固定长度或截断时，新事件仍可识别；旧事件换位置不能成为新事件。
6. 首次加载/重启规则明确：可靠时间在近期窗口中的 unknown 不能一概按历史忽略；已过窗口的可靠历史事件不重新等待。没有足够新旧证据时可作一次有界保守等待并持久化，禁止每次重启重新等五分钟。仍保留尾部 unknown 的不抢话门禁。
7. 发送锁内重新读取快照后先调用同一同步接口，再复核门禁。生成期间出现 unknown 或人工回复，即使紧接着又有买家消息，旧草稿也不能发送。
8. 同步或保存失败返回 SyncOk=false，本轮不发送。状态文件更新遵循现有原子写入/锁契约，避免两个写者互相覆盖 pause 与 hold。

### 4.2 必须验收

必须使用实际页面格式 `[ME] ... @@TS:... @@MT:...`，不能只用测试专有 human 标记证明生产来源路径。

覆盖：历史 unknown 建基线；新 unknown 后同一扫描出现买家补充；unknown 在生成期间出现后买家再补充；同条重扫；相同文字的新 ID/时刻；窗口截断/换行号；重启；近期与已过期的首次窗口；存储失败。断言真实入口的持久化状态、截止及 Sends。等待内 Sends=0；到期只在未答请求及全部门禁通过时允许发。

## 5. F5：供应商身份按实际联系人保存，避免同域误合并（P1）

定位：`scripts/lib/human_tasks.ps1::Get-SupplierTaskKey`、`New-OrUpdate-SupplierVerificationTask`、联系人提取与更新。

### 5.1 实现方案

1. 已有明确供应商 ID 时优先使用该身份；否则完整规范化邮箱或电话作为联系人身份键。邮箱域名不能独立代表供应商，`factory-one@mail.example.invalid` 与 `factory-two@mail.example.invalid` 必须不同。
2. 保存原始联系人及来源、规范化值、业务角色、身份可信度。规范化只做无歧义处理；电话不能凭缺失国家码猜补或误合并，邮箱不能去掉账号部分。
3. 任务键由 Buyer + CanonicalTaskKind + SupplierIdentity 组成；任务有独立稳定 TaskId。只有来源明确说明同一供应商换联系人时，才在同一供应商任务里更新/增加联系人；不能因同域或同名自行归并。
4. awaiting_contact 任务补充联系人时：只有明确归属或本轮唯一可对应的未定供应商任务才更新同一任务；多个候选时保留各自任务并请求归属确认，不取最近一条随意合并。
5. 不把相互独立供应商信息压成会话级单个通用联系人。事实状态为 conflict 或未明确归属时，不从全会话挑第一个邮箱覆盖现有任务。
6. 旧 email-domain 键兼容读取。可根据已存完整联系人建立明确的新键映射并保留 TaskId 与历史；已经被覆盖的联系人无法可靠恢复时标记待人工核对，不编造旧数据。本轮仅实现及隔离测试兼容，不重写生产任务表。

### 5.2 必须验收

同买家两个同域邮箱得到两个任务、两个不同键，两个实际联系人均保留；不同域同样成立。重复同一联系人不增生任务；明确同供应商换联系人保持任务与历史；未定供应商唯一待办补联系人更新同条，多待办不误合并。旧域名键、联系方式冲突及状态保存失败必须有可核对行为。

## 6. F4：供应商证据按确切任务回读，不按任意类型/最近任务借用（P1）

定位：`monitor.ps1::Get-TaskContextForConvo`、生成/发送证据读取、`human_tasks.ps1::Get-ActionEvidenceForBuyer`、供应商承诺检查。

### 6.1 实现方案

1. 建立唯一任务类型映射，例如 `Resolve-HumanTaskKind`：决策的 `supplier_handoff` 映射到持久化 `supplier_verification`。创建、查询、通知及规则登记均消费该映射，不各自散落字符串替换。
2. 生产回复改为按确切 TaskId + Buyer + CanonicalTaskKind + SupplierIdentity 回读持久化证据，例如新增 `Get-ActionEvidenceForTask`。会话级列表/摘要可保留旧查询接口，不能在缺确切任务时退回“取该买家最近一条”。
3. 建立/更新任务后，检查实际落盘结果及身份匹配，再提供 TodoPersisted、TaskId、TaskKind、SupplierIdentity、TaskStatus、UpdatedAt 等证据。缺失、类型错误、其他买家/供应商、不兼容状态或写失败均不给联系计划授权。
4. 生成前使用确切证据；发送前重新回读同一任务，发现任务关闭、归属变化或关键事实变化时重新决策或弃稿，不继续使用 script 中旧证据。不同会话不能共享 turnActionEvidence。
5. 有实际联系人且 pending_human 时，允许未来“我们会直接向供应商核实，省去您来回询问”；awaiting_contact 时允许条件式计划。客户明确无法提供资料时，不降级为继续让客户提供 rough size/rough weight。
6. 任务记录、通知投递、人工认领、实际联系、供应商回复、确认期限分别取证。OwnerAccepted 不能授权“已联系”；NotificationDelivered 不能授权“已确认”。同步修正现有将认领当已联系的检查，避免任务证据接通后错误放宽过去行动声明。
7. 任务保留独立于发送结果；FAILED/UNKNOWN 不删任务，不推进已回复账本。通知失败保留任务和失败记录，未来核实计划依据任务事实判断，不谎称通知成功。

### 6.2 必须验收

原输入：`My supplier's contact is supplier@example.invalid, but I don't know the dimensions.`；模型桩返回 `We'll contact your supplier directly.`。

必须同时断言：

- 在第一次模型调用前已落盘正确 pending_human 任务，真实联系人/缺失字段/资料来源存在。
- 模型实际收到的证据 TodoPersisted=true，TaskId、类型及供应商与落盘记录相等。
- 该模型计划通过生成与最终检查，发送桩收到直接核实供应商的计划，未回退让客户提供大概尺寸。
- 发送前回读的是同一任务，成功后账本按原规则推进。

不能仅断言“没有 share the dimensions”。另外覆盖 awaiting_contact、类型别名、其他任务/供应商证据、写失败、生成后任务关闭/改变、通知失败、FAILED/UNKNOWN、人工认领但未联系、实际联系记录，以及两个会话轮流处理。

## 7. F6：时间问题保留范围和目标列表，业务前置不覆盖（P2）

定位：`reply_policy.ps1::Get-TimeQuestionScope/Get-TimePlaceInfo`、当前未答消息范围、`seller_context.ps1` 渲染、`reply_gen.ps1` 与最终检查。

### 7.1 实现方案

1. 从规范化未答买家消息识别每个时间问题的起点、结束与消息边界。业务句位于问题前方时，从时间问句起点提取其修饰语；不能将范围截成空后再搜索整段文本。
2. 句界和范围解析不依赖下一句首字母大写；口语逗号、并列句及大小写变体均纳入边界。公司、供应商、仓库、目的地的非时间位置不能覆盖时间目标。
3. 每个时间请求至少保存 RequestId、MessageId、QuestionSpan、PlaceRaw、PlaceState、TimeZone/解析失败原因。区分 unspecified、explicit_resolved、explicit_unresolved；已指定但未知不能降成未指定。
4. 增加 TimeRequests/TimeTargets 列表供决策、受控渲染、模型上下文、重写、回退及发送检查消费。旧单个 RequestedPlace 可作为兼容展示字段，不能让生产检查只校验第一处而漏掉其他请求。
5. 可靠支持的多个目标逐项渲染，必要时去重相同目标；未解析/多时区目标逐项澄清。若超出现有处理能力，应明确说明/澄清待处理目标，不能静默丢弃第二问。多个地点共用同一次 NowUtc。
6. 无指定地点仍按卖家时区，there 的默认、here/my local time 的澄清、美国/澳大利亚多时区、纽约/悉尼及 hamburg 大小写规则保留。
7. 发送前用同一目标列表和新鲜时钟重新渲染，并检查整个回复的时刻/地点/身份。正文中的错误时间不能被正确前缀掩盖；请求变化重新决策。DIRECT_FACT/FALLBACK 不免检。
8. 不引入全球城市库或联网推测；未知地名安全澄清。混合公司/姓名问题仍由已验证身份内容回答，不漏答。

### 7.2 必须验收

注入 UTC `2026-10-05T06:05:00Z`，卖家 Asia/Shanghai，虚构完整公司名与多词接待名。

## 8. F7：摘要直接显示统一报价结果（P2）

定位：`scripts/summarize.ps1` 的资料表格与结论；统一 goods/readiness 适配、其他摘要/报表状态消费方。

### 8.1 实现方案

1. 统一读取 Ready、MissingFields、OptionalMissingFields、Clarifications、CollectionComplete、RuleVersion、Error。若兼容 goods 返回哈希表，使用支持哈希表与对象的取值接口，不依赖 PSObject.Properties 判键。
2. 摘要结论取 Ready，不再自行组合重量/尺寸/地址/货名。表格补充外包装件数及必要缺口，解释文字改为当前事实模型规则。
3. Ready=true 显示“可进入人工报价准备”；CollectionComplete=false 的辅助缺口另列，不改判不能报价。Ready=false 显示必要缺口及确实存在的澄清；Error 非空显示“资料判定失败，需核对”，不能因缺口数组为空而写齐全。
4. 外包装件数、重量、尺寸、可用目的地是基本报价条件。货名、图片、供应商资料、收货人姓名/联系方式是辅助项；Amazon 目的仓代码可满足目的地。
5. 摘要状态不代表已通知、已联系或已报价。保持表格转义及现有展示内容，不引入自动价格输出。
6. 核对其他报价摘要/报表消费方，确保本次调整没有保留第二套 Ready 判据；旧 goods 布尔值可用于逐项展示，不能再决定结论。

### 8.2 必须验收

运行实际 `summarize.ps1`，不是只抽取几行重写成测试逻辑；显式临时 LogFile、OutDir、StateFile 和 RuntimeRoot。

- 货名 cable、总重 200 kg、每箱 50×40×30 cm、FTW1、缺箱数：报告不可进入报价准备并列缺件数。
- 四项齐全、无货名/图/联系人：可进入人工报价准备，辅助项未完整另列。
- 件数/单位/尺寸存在冲突或未确认：显示实际澄清，不写齐全。
- 事实模型错误、Amazon 目的仓、明确更正及合法完整资料：报告与回复/报价候选结果一致。

断言实际生成文件的结论、缺口及 RuleVersion 与统一结果一致，不能只断言调用了 goods/readiness 函数。

## 9. F8：澄清必须有字段证据，which 不再免检（P2）

定位：`reply_policy.ps1::PolicyAskClarifyGuard`、`Test-AskFieldConformance`、决策 Clarifications 与生成字段标签。

### 9.1 实现方案

1. 删除“句中匹配 which/whose/is this/do you mean 就 continue”的免检路径。这些词仅是可能澄清的语气线索，不代表该句实际被授权。
2. 对请求/问句识别实际字段与动作：收集、确认候选、解决冲突等。每个请求对象分别核对 AskFields 或本轮结构化 Clarifications，不给整个句子豁免。
3. 合法澄清应绑定字段、已有候选/来源、单位/范围歧义或冲突及允许的问题。没有这类证据的 quantity/address 等请求仍是新字段索取，按未授权处理。
4. 已 provided 且不存在相关澄清的字段重复索取仍阻断；需要确认单位/归属时允许对应的具体澄清，不机械重复索要整个字段。
5. 继续区分每箱/每托盘重量尺寸的单位修饰语和真正数量请求。混合“合法澄清 + 未授权请求”分别判断，定语从句不能改变实际索取对象。
6. 身份与时间的合法地点澄清按对应结构化未解析时间目标授权，不通过全句免检来避开货物 AskFields。联系方式红线等检查继续独立适用。

### 9.2 必须验收

AskFields 只有 weight：`Could you share the packed weight per carton?` 通过；`Could you share the carton count?` 与 `Could you share the carton count, which we need for the quote?` 均阻断 ASK_OUT_OF_SCOPE。

另测：带 which/whose/is this/do you mean 的未授权请求、已给资料的重复请求、真实单位/范围/冲突澄清、合法澄清加未授权箱数、未知时间地点澄清。通过完整生成/重写/回退及发送前检查证明没有免检出口。
