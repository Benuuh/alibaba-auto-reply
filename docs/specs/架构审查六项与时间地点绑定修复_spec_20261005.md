## 1. A1：最高优先级联系方式红线漏拦（P1）

### 1.1 已复现

完整 `Test-ReplyCompliance` 会放行：

- `You can email me if that is easier.`
- `Please leave a phone number for delivery updates.`

第一句主动邀请客户使用我方联系方式；第二句笼统索取联系方式，没有明确收货人或供应商身份。业务用途“delivery updates”不能代替联系人的业务角色。

定位：`scripts/lib/contact_rules.ps1` 的 `Test-OurContactDisclosure`、`Test-ContactAsk`、`Test-ContactRedline`；以及 `reply_policy.ps1` 中的重复联系方式检查。

### 1.2 必须实现

1. 先识别联系邀约、联系渠道披露及索取行为，不能因缺少 `your`、实际号码或 `at/on/via` 后缀而跳过检查。
2. 主动提供、推荐或邀请使用我方电话、邮箱、微信、WhatsApp 等渠道，均阻断；单纯 `email me/us`、`call me/us` 等邀约也适用。
3. 索取时必须把该请求绑定到明确的 `supplier`、`consignee`、`recipient` 等业务角色，并符合用途及当前 AskFields；没有角色的 `a phone number`、`contact details` 等请求不得因物流语境而放行。
4. 明确允许本轮获准的供应商核实或收货资料收集；买家本人是收货人时，仍使用明确收货角色与用途的措辞。
5. 一个小句提及供应商或收货人，不得豁免其他小句的我方邀约或客户私人联系方式索取。避免不同检查器产生相互矛盾的允许/阻断结果。
6. 模型初稿、一次重写、固定回退、最终发送共用同一判据；不得仅修改提示词，也不得给某个场景或输出来源加免检白名单。
7. 客户主动询问我方联系方式的自动披露规则仍未由用户确认；本轮不新增自动披露授权。单纯解释“供应商已给出联系人”等非索取叙述不应误判为联系邀约。

### 1.3 必须验收

两条原失败句及其不含 `your` 的同义变体在完整检查中被阻断，并无法到达发送桩。允许：`Could you share the consignee's contact number for delivery?`、`Could you share your supplier's contact details so we can confirm the packing information?`，前提是对应字段确实获准且未提供。混合“供应商请求 + email me”仍阻断；已提供的角色联系方式不重复追问。

## 2. A2：人工回复后买家补充消息绕过 5 分钟暂停（P1）

### 2.1 已复现

真实 `Invoke-ConvoItem` 入口的隔离发送桩中，会话末尾为“可信人工回复 → 新买家消息”时，`PauseUpdates=0`、`Sends=1`。原因是仅在最新消息闸门返回 SKIP 后更新暂停；末尾买家消息直接进入 SEND 分支。

实际页面抽取给我方行添加时间戳，却未提供可验证的人工来源，单有时间戳的消息又被判 unknown；买家随后发言就恢复发送，也无法保证人工介入后的五分钟让路。

定位：`scripts/monitor.ps1` 页面抽取、`Get-HumanInterjectionGateEx` 前后的编排、发送前复核；`msg_source.ps1`、`sent_records.ps1`、`human_pause.ps1`。

### 2.2 必须实现

1. 在决定是否响应最新买家消息前，扫描当前快照中的新可信人工回复，更新并检查持久化暂停；不依赖最后一条消息是否为人工。
2. 暂停截止为最近可信人工回复时间加 5 分钟；有新的人工回复才延长。同一消息重复扫描、买家消息、普通冷却及程序重启均不能重置或取消暂停。
3. 从页面/API 的可核实发送者信息和本系统已确认发送记录建立来源证据。不能凭时间戳判机器人，不能凭“没匹配到发送记录”判人工，不能对所有我方行硬加 `human` 标记。保留原始消息身份、来源证据及可核对的时间。
4. 来源仍无法证明的新我方消息保留 `unknown`。对可能刚发生的未知我方介入，设置独立、持久化、去重的保守等待状态（`source_unknown_hold` 或等价状态，5 分钟），不伪称可信人工回复；买家补充消息不能立即解除该等待。等待有界、相同消息重扫不延长；首次加载历史消息的处理及恢复判据必须明确写入交付报告，不把整个历史窗口每次当作新介入。
5. 读取阶段和最终发送阶段均核验当前暂停与来源等待状态；生成期间新发生的人工回复或未知我方介入使旧草稿失效。最终检查要更新新发现的状态，不能只查生成前的旧状态。
6. 到期只解除临时等待；重新读取并通过未答请求、人工已答范围、身份、顺序、去重及新消息时间门禁后才发送，不主动发送到期问候或催促。
7. 显式人工接管名单仍优先，暂停到期不删除名单。暂停状态读取/保存失败不能默认为可发送，应记录故障并跳过本轮发送。

### 2.3 必须验收

注入时钟：12:00 人工回复，12:01 买家补充，12:04:59 不发送；12:05:00 后仅在存在未答诉求且门禁通过时允许发送。12:03 新人工回复延至 12:08；同条重扫、程序重新加载、买家多次消息均不延长。覆盖生成期间人工插话、实际页面消息格式到来源分类的适配、unknown 新消息后买家补充、历史 unknown 消息基线与等待恢复。已确认机器人消息不触发人工暂停。

## 3. A3：供应商任务创建顺序错误且缺少可执行资料（P1）

### 3.1 已复现

买家：`My supplier's contact is supplier@example.invalid, but I don't know the dimensions.`

模型：`We'll contact your supplier directly.`

真实入口隔离复现：生成时任务数为 0，发送后任务数为 1；联系计划被旧承诺规则拦截，最终回退为让客户提供大概尺寸。任务中的所谓联系方式是字面量 `supplier-contact-provided`，而非实际联系人；MissingFields、FactsSnapshot 未传入。

定位：`scripts/monitor.ps1` 生成前动作证据读取、SENT_OK 后的任务创建；`human_tasks.ps1`、供应商计划措辞检查、`reply_gen.ps1` 和固定话术。

### 3.2 必须实现

1. 编排顺序调整为：读取并验证会话 → 事实/业务决策 → 幂等创建或更新本轮任务 → 回读持久化结果与 ActionEvidence → 生成/重写/回退 → 最终复核 → 发送 → 只推进发送相关状态。
2. 任务动作由编排/任务服务执行，纯决策和生成器不自行写业务状态。任务存在不依赖回复发送成功；暂停期间可以整理资料、保存待办，但不能向买家发送。发送失败或 UNKNOWN 不删除已经成立的供应商核实任务。
3. 任务保存真实供应商联系方式及其来源消息、业务角色、缺失的件数/重量/尺寸字段、当前资料快照、触发消息与身份、创建/更新时间及状态。触发文字不能仅保留截断的最后一句作为唯一证据；必要时引用隔离/运行态中可读取的完整来源。
4. 使用真实供应商身份生成稳定去重键，保留实际联系人数据；禁止用通用占位符代替联系人，也不能把不同供应商都合并为一个键。未有联系方式的 awaiting_contact 任务，在收到联系方式后更新为同一流程中的 pending_human，避免重复悬挂任务。
5. 同一会话、同一供应商、同类核实请求幂等更新。ActionEvidence 绑定本轮任务类型及供应商，不能取同一买家最近任意任务作为联系承诺的证据。
6. 措辞按事实状态放行：已落盘 awaiting_contact 可说“收到供应商联系方式后，我们会直接核实”；已落盘 pending_human 且有实际联系方式，可说“我们会直接向供应商核实，省去您来回询问”。任务持久化失败时不得承诺联系，记录故障并使用经检查的中性回复或跳过发送。
7. TodoPersisted、NotificationDelivered、OwnerAccepted、Contacted/实际联系记录、Deadline 是不同证据。保存任务足以支撑未来核实计划，通知失败不否定任务存在；不得把未来计划、通知送达或人工认领说成“已联系供应商”。已经联系、已经收到回复以及具体期限各自需要实际记录，不凭短语长度或任意正则窗口放宽。
8. 用户明确拿不到包装资料时优先走供应商路径；已有供应商联系方式不再追问，也不回退为继续让客户自行问尺寸/重量。联系动作留给人工，不自动外联供应商。
9. 提供最小可用的人工待办读取入口或复用已有入口，让人工能看到实际联系方式、缺失资料、来源和状态，并能按现有任务接口记录处理结果；不要求新建管理后台。通知失败保留任务及失败记录，不谎称通知送达；本轮验收用通知桩。

### 3.3 必须验收

上述原场景中，生成前已有完整 pending_human 任务，联系计划通过全链校验，发送桩收到供应商核实回复。无联系方式时只索取供应商业务联系方式并落盘 awaiting_contact；补充联系人后更新同一任务；缺失字段在更早买家消息中时也保存。重复扫描/重试不增生任务，换供应商不误合并。模拟任务写入失败、通知失败、发送失败、UNKNOWN、人工认领与实际联系，分别核对任务状态、证据及允许措辞；`We'll check the missing packing details directly with your supplier.` 这类较长计划也不得绕过证据校验。

## 5. A5：不足 100 字节的损坏账本被当作不存在（P1）

### 5.1 已复现

账本为 UTF-8 BOM 加 `{"replied":{`（15 字节）时，`Read-JsonDocument` 返回 corrupt，`Get-RepliedState` 丢弃读取状态并返回 null，`Test-RepliedStateUsable` 按文件小于 100 字节判 Ok=true、Reason=no-ledger-yet。

定位：`scripts/monitor.ps1` 的 `Get-RepliedState`、`Test-RepliedStateUsable`、修复/保存及首次创建调用方；`state_store.ps1`。

### 5.2 必须实现

1. 在整个账本读取与门禁链保留 missing/empty/valid/corrupt 状态及必要诊断，不能压成 null 后用文件大小猜测。
2. 主文件确实 missing、有效备份也不存在时，才允许首次初始化。合法 JSON 的空 replied 集合属于有效空账本；空白文件、零字节文件或无法解析的文件不等同于合法空集合。
3. corrupt、不可读或结构不合法时停止本轮生成/发送及普通账本写入，保存证据；不清空、不覆盖、不伪造首次运行。大文件和小文件采用同一规则。
4. 如使用已有备份恢复流程，只允许经解析与结构验证的备份，显式记录恢复结果并在继续前重新核验；损坏备份不能放行，普通首次创建不能隐式抹掉损坏主文件。
5. 所有入口及发送前检查按同一状态判断；账本在生成期间损坏时不能继续发送。保留历史 HASH|count 格式兼容，不在本轮迁移或清空生产数据。

### 5.3 必须验收

临时根中测试 15 字节原样例、其他不足/超过 100 字节损坏、空白/零字节、合法空账本、缺失主文件与有效/损坏备份、正常历史格式及模拟读取失败。通过真实 monitor 入口断言损坏时 Sends=0、账本字节及有效备份不被普通流程改写；生成中损坏也不能发送。原子写入失败仍保留原有效文件。

## 6. A6：“每箱重量/尺寸”被误判为额外询问箱数（P2）

### 6.1 已复现

Decision.AskFields 仅允许 weight 时，`Could you share the packed weight per carton?` 在完整检查中被判 ASK_OUT_OF_SCOPE，因为 count 组匹配任何 `carton` 词。

定位：`scripts/lib/reply_policy.ps1` 的 `PolicyAskFieldGroups`、`Test-AskFieldConformance`，以及固定话术字段标签。

### 6.2 必须实现

1. 字段校验判断实际索取对象，区分“箱数”与“重量/尺寸的每箱单位”。`per carton`、`per pallet`、`each box` 等修饰语不单独产生数量请求。
2. 真正的 `how many cartons`、`carton count`、`number of pallets` 仍需要数量授权；“每箱重量 + 一共有多少箱”的混合请求必须分别检查，不能因一句允许的重量请求豁免箱数。
3. 同样保护每箱尺寸、每托盘重量/尺寸的合法问法。仍阻断未授权字段、已提供字段重复索取、单位或范围不明却被直接当成事实。
4. 不以出现 `which`、澄清措辞或包装词为整句免检理由，不删除 AskFields 校验。

### 6.3 必须验收

只允许 weight 时，“packed weight per carton”和“weight of each pallet”通过；只允许 dimension 时，“dimensions of each carton”通过。只允许 weight 时询问 `How many cartons are there?` 或“weight per carton and how many cartons”仍阻断。已给重量时再次索取仍阻断。覆盖生成、一次重写、固定回退和发送前检查。

| T2 | `What time is it in China? My company is in Tokyo.` | 后句 Tokyo 覆盖时间目标 | 回答中国 2:05 PM / UTC+8 |
| T2 对照 | `What time is it now? My company is in Tokyo.` | 取公司所在的 Tokyo 为时间目标 | 未指定时间地点，默认卖家中国时间 |

定位：`reply_policy.ps1::Get-RequestedTimePlace`、当前未答请求/消息边界与时间意图识别、`seller_context.ps1` 受控时间渲染、`reply_gen.ps1` 与 monitor 的最终复核。

### 7.2 必须实现

1. 至少区分三态：未指定时间地点；已明确指定但无法可靠解析；已解析为有效时区。保留地点原文、所属请求/消息、来源及解析失败原因。解析失败不能变成“未指定”并默认中国。
2. 从当前未答请求中识别时间问题的范围，再解释该问题的地点修饰语；不得遍历整段输入所有 `in/at` 并选最后一个。明确的未知地名不因全小写而丢失。
3. 不同句子和消息中的公司、供应商、仓库位置与运输目的地不得覆盖时间目标。保留规范化原文与消息边界，不把多个短消息直接拼成地名；并列子句同样要按问题归属处理。
4. 支持现有合理口语变体：`What time is it now in Tokyo?`、`What time is it in Tokyo now?`、`What's the current time in Tokyo?`，不能退化为只支持一种句尾形状。
5. 未指定地点答卖家所在地；无明确其他指代的 there 按卖家所在地；here / my local time 缺买家时区时澄清。美国、澳大利亚等多时区国家缺城市时保留澄清；明确纽约/悉尼时可靠转换。
6. 未知地点只问一个明确的地点/时区问题，不附带货物资料追问、不输出估算时刻。明确问多个地区时按既有支持能力逐项回答或澄清，不任意选最后一个。
7. 不要求全球城市数据库、联网查时区或根据姓名猜买家所在地；未知地名允许安全澄清。T1 若新增可靠 Hamburg 映射可以准确答当地时间，但绝不能退回卖家时间。
8. 决策、受控渲染、模型上下文、重写、固定回退和最终发送检查消费同一结构化时间目标结果。发送前可用新时钟刷新时刻，但地点解析依据和问题归属必须一致；请求变化时重新决策。
9. 不给 DIRECT_FACT、DIRECT_FACT_REFRESH 或 FALLBACK 加免检白名单。正确时间前缀不能掩盖模型附加正文中的错误时刻、时区或身份；最终检查仍阻断。
10. 保留完整公司名、多词接待名、混合请求对公司名的回答以及已通过的身份规则。不重写已验收的功能来回避本问题。

### 7.3 必须验收

| 场景 | 期望 |
|---|---|
| hamburg / Hamburg / 另一未知地名 | 明确指定状态一致，解析不了就澄清，不答卖家时间 |
| 中国时间问题后接公司在东京 | 中国 2:05 PM / UTC+8，后句不覆盖 |
| 无地点时间问题后接公司在东京 | 卖家中国时间，后句不覆盖 |
| 时间问题后接供应商、仓库、运输目的地句 | 业务地点不改变时间目标，业务问题仍交原策略处理 |
| 多条未答消息：问中国时间，后续说明公司在东京 | 保留消息边界，仍答中国时间 |
| 多条短消息的地名/业务位置 | 不意外拼成地名或用无关消息覆盖目标，歧义时澄清 |
| 东京三种口语变体；时间与公司名同句/并列子句 | 东京转换正确；属于公司问题的地点不覆盖时间，混合请求不漏公司名 |
| there、here、my local time；美国/澳大利亚；纽约/悉尼 | 默认、澄清和转换规则保持 |
| 明确问多个时间地点 | 逐项回答或澄清，不能只选最后地点 |
| 正确时间前缀加模型正文错误时刻/时区/身份 | 完整最终检查阻断，发送桩无调用 |

至少覆盖纯函数、实际生成链和 AST 提取真实 monitor 入口的发送桩。T1 不得以中国时间到达发送桩；T2 中国时间能正常发送，账本只在 SENT_OK 后推进。修正 `docs/接待基础问答修复交付_20261005.md` 中“全小写生僻地名会走澄清”的旧边界说明，并保存 T1/T2 失败→通过证据。

## 8. 通用集成与验收方法

### 8.1 防止“模块通过、入口没接上”

1. 新增测试先覆盖原失败输入与预期可观察行为，不以源码包含正则、函数存在、手工打印通过日志或替换被测逻辑为通过证据。
2. 三层验收：纯事实/规则函数；实际生成链（模型可用桩，但真实决策与全部检查保留）；真实 monitor 函数入口（通过 AST 提取或现有无副作用引导入口，页面、发送、通知、时钟及文件失败用适配桩）。
3. 入口集成测试不得 stub 掉本次被修的来源识别、暂停更新、任务持久化、合规判断、报价判据或账本门禁。桩只替换外部 IO/模型和故障注入点，断言实际调用次序、落盘内容及发送/提醒行为。
4. 所有用例使用虚构买家、`.invalid` 联系地址、虚构公司和多词接待名、注入时钟。实际本机身份、买家数据和凭据不得写入夹具、日志证据或提交文件。
5. 每个测试有独立临时 RuntimeRoot、隔离标记及锁/账本/暂停/任务/发送记录/提醒路径。真实 CDP、客户发送及真实通知出口在隔离模式下拒绝；新增测试登记 `tests/layers.json`。

### 8.2 执行与生产路径保护

先运行新增专项及相关回归，再运行经过副作用核验的 Offline 套件。原时间补修稿“不运行未隔离 runner”的要求保留：先确认当前 runner 每个子测试均注入独立运行根、外部出口已阻断、新增测试没有偷偷读写生产数据；不能只凭名称 Offline 就视为隔离。不得运行 Live/All。

确认上述隔离条件后，Windows PowerShell 5.1 的统一回归命令为：

```powershell
powershell -ExecutionPolicy Bypass -NoProfile -File tests\run_tests.ps1 -Layer Offline -KeepTemp
```

使用 KeepTemp 保留证据并避免未经路径核验的递归清理。后续若清理，必须逐个核对解析后的绝对路径处于本次专属临时目录，使用同一 PowerShell 与 LiteralPath；不要删除生产运行根。

记录测试前后生产路径指纹及本轮实际写入路径。生产进程可能同时写日志，不能只因进程存在或路径位于日志/data 根，就把变化自动宣称为本轮无写入的证据；分别报告未解释变化、运行中写者变化和隔离出口保证。如隔离条件不足，先修测试隔离，再执行；不通过停生产来制造测试环境。

覆盖相关回复链、联系方式、货物事实、报价/目的地、人工来源/暂停、人工任务、原子状态、发送结果、顺序/去重、新消息冷却、锁范围与接待基础问答回归；变更 `.ps1` 后核验 BOM 与 PS 5.1 解析，更新文档后运行 docs_consistency。不要降低既有断言或删掉失败用例使套件全绿。

### 8.3 必须保留的业务保护

- 不主动提供我方联系方式，不笼统询问客户个人联系方式；业务角色资料按本轮授权收集。
